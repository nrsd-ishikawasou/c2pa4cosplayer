## 调查 I-01、I-02：C2PA证书、本人性、权利性（2026-09-29，2026-09-30修订）

- 本资料是在设计计划书第1版阶段所调查事实的记录。设计计划书第2版（2026-09-29）决定，本系统不确认使用者，不收集使用者的信息，C2PA签名的证书根据使用者输入的信息在终端上制作（不需要认证机构）（D-5-1“本系统不确认使用者，不收集使用者的信息。使用本系统不要求登记”、D-5-2“C2PA签名的证书，根据使用者输入的信息在客户端应用内生成。不需要认证机构”）。因此，第2节“对设计的归结”中第1版阶段的选项（NRSD的私设认证机构、取得合规并接受设备证书的方案、身份的汇集者）不予采用。所采用的设计放在基本设计 第2章 3“证书”中。

### 1. 确认的事实（附出处）

#### 1.1 C2PA的声明签名证书是发给“生成产品”的

- C2PA Trust List是“向合规的生成产品（generator product）发行证书的认证机构”的一览。验证产品以此一览判断签名是否出自有效的证书。［S1］［S2］
- 合规的生成产品必须从Trust List上的认证机构购买签名证书。［S3］
- SSL.com：“只向通过C2PA合规的工具与设备发行”。免费额度：Level 1证书1张（1年）与每年2,500次可信时间戳。收费额度中有设备证书（device certificates）、API。［S4］
- Trufo：C2PA证书每年600美元。需要OV（组织验证）与PV（产品验证）。测试用证书免费，但不被验证产品信任。［S5］
- Trust List（C2PA-TRUST-LIST.pem）中的证书在2026-09-30获取时为30张，发行者的组织为Adobe、Castlabs、DigiCert、Encypher、Google、Huanyu Trust、Huawei、Irdeto、SSL.com、Snowball Technology、Tauth Labs、Trufo、TrustAsia、Verimago、Whole Earth Labs、Xiaomi、vivo共17个（2026年4月时点的记载为DigiCert、SSL.com、Tauth Labs、Trufo共4个）。［S3］［S12］
- 临时信任列表（ITL）于2026年1月1日冻结。没有新的追加。［S2］
- 不在Trust List中的签名显示为“Valid（在密码学上正确，但签名者未获生态系统保证）”，不会成为“Trusted”。［S6］Adobe的验证网站显示“未知的发行者”。［S2］

#### 1.2 合规的手续与密钥保护的水准

- 手续：表示关注，其次与C2PA的法律合同，其次技术、安全评估（构成图、文件），其次发行证书。费用与期间在公开信息中没有记载。［S3］［S7］
- 保证水准（Assurance Level）记录在证书的扩展中。［S3］
- Level 1：加密保存签名密钥。可以使用操作系统的密钥存储（macOS Keychain、Linux kernel keyring等）。“分发的二进制文件中不得包含用于认证的机密”。［S8］
- Level 2：在比声明生成部分特权更高的环境（操作系统的密钥存储服务或KMS）中生成、保管、使用密钥，并以源自硬件的密钥封装。远程签名时，在验证硬件信任根的证明之后签名。［S8］
- 有Edge（在使用者终端上运行的产品）、Backend（在服务器上签名）、Distributed的区分。［S8］

#### 1.3 个人的身份以CAWG identity assertion承载（与C2PA签名分开的信号）

- CAWG身份记录（identity assertion）的现行版本为1.3（于2026-09-30在cawg.io确认。本资料的调查依据1.2）。元数据（cawg.metadata）的现行版本为1.1。
- CAWG identity assertion证明资格持有者控制着数字身份，并将其与C2PA的断言相结合。不需要与声明签名者相同，是独立的追加信任信号。［S9］
- 资格的种类：X.509证书（cawg.x509.cose）与身份主张的汇集（identity claims aggregation，W3C可验证凭证）。［S9］
- 汇集的种类：cawg.social_media（账号的控制。username必须，uri推荐）、cawg.document_verification（公共身份证件。name必须）、cawg.web_site、cawg.affiliation、cawg.crypto_wallet。［S9］
- 汇集者按资产制作并签署凭证（按资产的签名）。［S9］因此，汇集者在每次签名时都参与（判断为需要在线参与。规范中没有明记）。
- 角色（role）：cawg.creator、cawg.contributor、cawg.producer等。也可以使用独有的值。［S9］
- 规范上没有规定X.509的主体必须是法定姓名。［S9］
- SSL.com的CAWG证书：也向个人发行。经身份确认后放入“已确认的姓名”。个人每年49美元，个人与组织每年69美元，组织每年99美元。［S10］

#### 1.4 已有的同类服务

- Adobe Content Authenticity（免费、测试版）：以LinkedIn确认姓名，在Content Credentials中显示Behance、Instagram、LinkedIn、X的账号。对JPG/PNG至多50张、每张至20MB批量套用。［S11］

### 2. 对设计的归结（至第2章、第3章、第8章）

#### 2.1 设计计划书第2版中的替换（所采用的设计）

- 在使用者的终端上制作个人根证书与签名用证书，进行C2PA签名。不在Trust List中，在一般的验证网站上为“Valid”而不是“Trusted”（基本设计 第2章 3“证书”、3.3“在验证器中的显示”）。
- 权利性的线索，是揭示在声明所在账号上的声明码（由个人根证书公钥的指纹制作）（基本设计 第2章 DD-2-3“权利性的线索是发布在声明所在账号上的声明码”、2.4“声明码的生成方法”）。
- 身份的记录以X.509（`cawg.x509.cose`），以签名用证书附加在`cawg.identity`中。不进行第三方的身份确认（基本设计 第3章 3.1“记录的项目”）。

#### 2.2 第1版阶段的研讨（作为记录保留。不采用）

- “使用者本人持有C2PA声明签名证书”的构成无法实现。声明签名证书是发给产品的。
- 声明签名的选项
  - A：Trust List之外的签名（NRSD的私设认证机构或按使用者的自行发行）。没有费用，没有合规手续。在验证网站上为“Valid”但不是“Trusted”。
  - B：本应用作为Level 1的Edge生成产品取得合规，按安装从Trust List上的认证机构接受设备证书。需要法律合同、评估、证书费用、发行的机制（注册时的认证）。
  - C：NRSD设置签名服务器（Backend）。服务器会成为攻击对象，违反“不放到Web上”方针（设计计划书 D-6-2“本系统不作为网站构建”）的宗旨。不采用。
- 身份的选项
  - X.509的CAWG证书（个人）：载入经身份确认的姓名。因此，正面触及审查项目A-15“C2PA签名中出现真实姓名的风险”。
  - 身份主张的汇集（social_media）：可以载入网名（username）与声明所在账号。但汇集者按资产签名。因此，NRSD若成为汇集者，就需要常时运行的服务。
  - 本系统独有的比对：在声明所在账号上揭示密钥的指纹，以本系统的比对手段与公开页面确认（设计计划书 5.3的方案）。是C2PA生态系统之外的信号。
- 在第1版阶段，以分阶段的构成（先A与独有比对，将来B）为有力方案。在第2版中，采用了A中的“按使用者的自行发行”与独有比对，不采用NRSD的私设认证机构与B、C（2.1）。

## 调查 I-03：在发布网站与云端C2PA的保留

### 1. 确认的事实

|服务|C2PA、EXIF的处理|出处|
|---|---|---|
|Instagram、Facebook、Threads|上传时读取C2PA并用于“AI info”的显示，从分发、重新下载的文件中删除EXIF与C2PA|［S1］［S2］|
|X|删除EXIF与C2PA。没有来历的显示|［S1］［S2］|
|TikTok|读取C2PA并自动显示。对AI内容附加独有的水印|［S1］［S2］|
|LinkedIn|读取C2PA，显示CR图标与来历面板。作为文件的保留不确定|［S1］［S2］|
|YouTube|视频因重新编码而失去嵌入的信息|［S1］|
|WhatsApp|通常的发送会删除全部元数据。“作为文件发送”保留原来的字节|［S1］［S2］|
|Pinterest|读取IPTC并显示AI标识。保留情况未公布|［S2］|
|微博|单张图片超过30MB时，即使指定原图也会压缩。优化图片格式（文件大小大幅减小）。官方帮助中没有关于EXIF的记载。报道、解说称EXIF会被删除|［S3］［S4］|
|小红书|读取上传图片的EXIF（用于截图判定等）。在分发文件中是否保留没有公开信息|［S5］|
|Patreon|发布图片以多个分辨率的版本分发（可能重新编码）。附件（attachments）以创作者上传的原格式分发|［S6］|
|Google Drive|下载时不改变原文件而返回。文件夹的zip也不改变内容（二手信息）。Google相册有时在共享链接中删除GPS（与Drive不同）|［S7］［S8］|

### 2. 对设计的归结

- 在主要的社交平台（Instagram、Facebook、X、TikTok、YouTube、微博）上，按发布图片的C2PA不会保留进行设计。社交平台用的流程以可见签名与隐形水印保护（与设计计划书7.4一致）。
- LinkedIn会显示，但保留不确定。作为本系统对象的发布网站，重要度较低。
- Patreon在“发布图片”与“附件”上处理不同的可能性很高。在交付中使用Patreon的附件时，假设原来的字节会被保留。因此，实际上传进行确认（不收发就无从得知。假设：附件保留，发布图片不保留）。
- 本表的出处全部是二手的（解说文章、使用者的报告），在各服务的官方文件中未能确认关于C2PA处理的记载。
- 关于Google Drive，有多条二手信息称其返回原来的字节。因此，上传到NRSD的Drive再取出，比较SHA-256加以确定（假设：保留）。
- 水印的强度需要经得起上述社交平台的重新编码（缩小、JPEG再压缩、转为WebP）（第3章的要求）。

## 调查 I-04、I-05等：GitHub的限制、从中国大陆的连接、代码签名（2026-09-29，2026-09-30修订）

- 本资料的一部分是在设计计划书第1版阶段（把图片与证据放在私有仓库、由应用以REST API写入的构成）调查的。设计计划书第2版（2026-09-29）决定不设私有仓库，把记录与证据放在使用者的终端上（D-12-1“设置公开仓库。不设置私有仓库”、D-12-3“权利人信息、签名密钥、作品数据、台账及证据保存在使用者的终端，NRSD不收集”）。因此，第2节中REST API、个人访问令牌的事实，以及对把图片与证据积累在1个仓库中这一构成的归结，在当前的设计中不使用（作为记录保留）。在各节的末尾写明第2版中的替换。

### 1. 从中国大陆访问GitHub（I-04）

- 根据GreatFire的观测，截至2026年8月3日，https://github.com 在中国大陆受到60%的妨碍（最近35次判定中有60%受到干扰）。［S1］
- raw.githubusercontent.com在部分ISP被阻断、DNS污染。大文件与二进制发布的下载很慢。即使HTTPS失败，SSH的git有时也能通。［S1］［S2］［S3］
- 对设计的归结（第1版阶段）：以中国大陆的使用者无法稳定地从GitHub获取、更新、登记为前提进行设计（“登记”在第2版中已不存在。见下项）。替代的途径在第8章、第9章中规定。替代途径的实效性，从中国大陆的线路实际获取来确认（不收发就无从得知。假设：仅GitHub不够）。
- 第2版中的替换：替代的途径为香港地域的对象存储（阿里云的OSS。不需要ICP备案），用于更新与参考信息的获取，以及从README中文节的直接获取（基本设计 第8章 DD-8-5“为中国大陆设置香港镜像”、第9章 5“获取途径”）。第1版阶段所列的“登记”（应用向GitHub写入），由于在第2版中登记在终端中完成，已不存在。

### 2. GitHub的限制（第8章）

- 仓库的大小：理想为不足1GB，强烈推荐不足5GB。［S4］
- 文件的大小：超过50MiB时警告，超过100MiB时拒绝。从浏览器至25MiB。1次push至2GB。1个目录3,000项，深度至50。［S4］［S5］
- Git LFS：Free、Pro包含存储10GiB、传输10GiB，Team、Enterprise各包含250GiB。超出部分按用量计费。［S6］
- GitHub Actions：Free的组织在私有仓库中每月2,000分钟、成果物500MB，Team为每月3,000分钟、2GB。公开仓库的标准运行器免费。［S7］
- REST API：个人访问令牌、GitHub App的安装令牌每小时5,000次请求。Actions的GITHUB_TOKEN每个仓库每小时1,000次。制作内容的请求限于每分钟80次、每小时500次（二次限制）。［S8］
- 细粒度的个人访问令牌：可以限定于特定的仓库，细致地授予权限。组织可以要求批准，并施加最长的有效期限。［S9］
- 发布：1个发布的文件至1,000个，各文件不足2GiB。发布的合计大小与传输量没有上限。［S14］
- 不可变的发布（immutable releases）：公开之后，不能变更、删除分发物与标签（标题与说明可以变更）。自动生成发布的证明（标签、提交、分发物）。［S15］
- GitHub Pages：公开的网站至1GB，传输量的参考为每月100GB（超过时可能收到通知）。［S16］
- 第1版阶段的归结（记录）：持续把图片与证据积累在1个仓库中的构成，很快会触及容量的推荐值（1至5GB）。
- 第2版中的替换：公开仓库中只放置源代码、发布（分发物）、公开页面、参考信息，不放置使用者的图片与证据（基本设计 第8章 3“公开仓库”）。不使用REST API与个人访问令牌。分发物放在发布中（各约200至300MB。在上限2GiB之内），参考信息与更新的说明放在公开页面上（在1GB之内）。

### 3. 代码签名（I-05）

- macOS：Apple Developer Program每年99美元。App Store之外的分发依据Developer ID证书与公证（notarization）。［S10］macOS Sequoia以后，未签名、未公证的应用无法以Control点击打开，需要从系统设置的“隐私与安全性”中允许。［S11］
- Windows：Azure Artifact Signing（原Trusted Signing）每月9.99美元，至5,000次。组织的公共信任证书在包括日本在内的国家可以使用。个人仅限美国、加拿大。需要付费的Azure订阅。不发行EV证书。SmartScreen的警告，即使已签名，在下载的实绩积累之前也会出现。［S12］［S13］
- 对设计的归结：NRSD（日本的法人）可以作为组织使用Artifact Signing。macOS需要Developer Program。Linux没有操作系统的签名机制，因此在第9章中规定分发物的签名（另外的验证手段）。以SmartScreen在初期会出现警告为前提，在首次的指引（第10章）中说明。

## 调查：签名处理的技术要素（第3章的前提）（2026-09-29，2026-09-30修订）

- 2026-09-30的修订：接受外部的审查，修改了c2pa.metadata的记述、PDQ的语句、可信时间戳信任的处理。所采用的设计放在基本设计 第3章“签名处理”中。

### 1. C2PA的断言（规范2.4）［S1］

- 与内容的绑定（硬绑定）：c2pa.hash.data、c2pa.hash.boxes、c2pa.hash.bmff.v3
- 软绑定：c2pa.soft-binding（水印、指纹的标识符）
- 操作的履历：c2pa.actions.v2。必须有c2pa.created或c2pa.opened。其他有c2pa.edited、c2pa.watermarked、c2pa.resized、c2pa.published、c2pa.placed、c2pa.converted等
- 素材：c2pa.ingredient.v3。元数据：c2pa.metadata在规范2.x中限于附录B.2允许的项目（拍摄日期时间、设备、位置等固定的项目），不能持有著作者名、著作权、使用条件的项目。这些放在CAWG的`cawg.metadata`中（基本设计 第3章 3.1“记录的项目”）。缩略图：c2pa.thumbnail.claim（输出的缩小）。时刻：c2pa.time-stamp
- 2.4中追加：c2pa.repository-receipt、c2pa.ai-disclosure等
- 规范强烈推荐让制作者能够控制包含哪些来历数据（对个人信息的考虑）。
- 最新版为2.4（已在设计计划书第17章中确认）。

### 2. 隐形水印（TrustMark）［S2］［S3］［S4］［S5］

- 有效载荷为100位。按纠错方式可用的数据位数：BCH_SUPER 40位（纠正8位的错误）、BCH_5 61位（5）、BCH_4 68位（4）、BCH_3 75位（3）。［S3：datalayer.py］
- C2PA已认可的软绑定一览中载有TrustMark的variant Q、C、P（B未载入）。［S5］
- 使用方法：把随机的标识符放入水印，并把相同的标识符记录在C2PA的软绑定断言中。即使C2PA丢失，也能以水印的标识符为键查到清单的副本（Durable Content Credentials）。［S4］
- Rust版：支持全部variant在二值模式下的嵌入、读出。文本模式与水印的删除尚未实现。使用ONNX运行时（ort），模型另行获取。支持的环境：Windows 10/11、glibc 2.35以上（Ubuntu 22.04以后等）、macOS 10.15以上。［S6］
- 许可：MIT（代码与模型）。［S2］
- 在示例图片中PSNR约为50.4dB。［S2］
- 运行速度、对再压缩的耐受性的数值不在公开的README中。因此，以对象图片（数千万像素）与对象社交平台的再压缩实测来判断（不运行代码就无从得知。假设：在CPU上每张数秒以内，经社交平台的缩小、再压缩后也能以BCH_5读出）。

### 3. 比对用哈希（PDQ）［S7］［S8］

- 有pdqhash（Rust，Apache-2.0，纯Rust）、pdq-rs（封装原版C++）、yume-pdq（速度优先）。
- PDQ一致判定的参考为汉明距离31位以下（256位中）。［S8］
- PDQ不耐裁切、旋转（算法的性质。原版文件hashing.pdf［企划草案的参考文献12］）。对裁切的耐受性以水印补充。90度为单位的旋转与翻转，可以通过计算并对照8种哈希来处理（基本设计 第3章 6“比对用哈希”）。

### 4. 可信时间戳（RFC 3161）

- 免费的TSA：DigiCert（timestamp.digicert.com）、GlobalSign、FreeTSA（无保证）。［S9］
- SSL.com的C2PA免费额度中包含每年2,500次可信时间戳。［对设计的注记：调查资料“C2PA证书与本人性”的S4］
- C2PA另外持有TSA的信任列表。验证者通过能追溯到TSA信任列表的可信时间戳，即使在证书吊销、过期之后，也能确认签名时点的有效性。［调查资料“C2PA证书与本人性”的S2］但上述免费的TSA（DigiCert的通用TSA、GlobalSign、FreeTSA）不在C2PA的TSA信任列表中，C2PA 2.x的验证器会忽略其可信时间戳，按核验时点的时刻检查证书的期限（规范2.4的15.8.2。于2026-09-30以原文确认）。因此，把证书的有效期取长（基本设计 第2章 DD-2-11“证书有效期的长度使任何图片自签名起20年内都显示为有效”）。
- 中国：联合信任时间戳服务中心（由国家授时中心与联合信任构建，RFC 3161、GB/T 20520-2006）。截至2025年4月，以可信时间戳为证据的裁判文书超过10万件，涉及1,221个法院。［S10］
- 日本：总务大臣的时间戳认定制度（2021年开始）。Amano时间戳服务3161于2023年2月获得首个认定，2025年2月更新。［S11］
- 费用：联合信任、日本的认定事业者都未能在公开信息中确认价格。因此，取得估价后判断（假设：收费。研讨只在登记（证据保全）时的可信时间戳中使用，签名时使用免费TSA的构成）。

### 5. 自我更新（采用Tauri时）［S12］

- 更新的签名验证为必须，不可关闭。把公钥嵌入应用，以私钥对成果物签名。失去私钥就无法向已有的使用者分发更新。
- 可以指定多个更新的获取来源，应答不是2xx时前进到下一个（可以持有替代途径）。
- 支持放在GitHub Releases中的静态JSON。
