本書は、設計計画書を受けてシステム全体の構成と方式の大枠を定め、範囲を定義する。各章の詳細は基本設計書（第1章「全体構成」〜第13章「設計の検証」）で定める。

各章の書き方：

- 受ける決定：設計計画書の決定（D-）、要調査（I-）、未決（O-）、項目割りの監査（A-）
- 定義すること
- 範囲：扱う／扱わない（なければ「なし」）
- できなければならないこと：要件。番号 R-章-機能-連番。13章の検証と試験文書はこの番号で参照する
- 基本設計で詰めること
- 依存：依存する章と依存される章。互いに依存する章には「互いに依存する」と書き添える
- 法務へ：法務の文書群で調べ、ここからリンクする点

## 本書の位置付け

### 本書の役割

- 設計計画書を受け、システム全体の構成と方式の大枠を定義する。範囲の定義は本書で行う。
- 各章の詳細は基本設計書に譲る。本書で全体を閉じてから詳細に入る。
- 試験は、本書および基本設計書と対になる別の文書群で扱う。
- 法務は別の文書群で調べ、本書からはリンクする。

### 本システムが守るもの・守らないもの（全章の前提）

- 守るもの：利用者（画像の権利者とその承認を受けた者）の、自らの写真に対する権利［D-2-1「本システムが守るものは、権利者が自らの写真に対して有する権利（著作権および肖像権）とする」］
- 守らないもの：コスプレの原作（キャラクター等）に関する著作権その他の権利。原作の権利者との関係、利用者が原作について起こすライセンス上の問題を、本システムは解決しない。
- この線は、利用規約と画面の案内（第10章「画面とデザイン」）で利用者に明示する。

### 用語

- 設計計画書1.5「用語の定義」の用語をそのまま使う。本書で加える用語は次のとおり。

|用語|意味|
|---|---|
|作品データ|作品ごとの識別番号、照合用ハッシュ、日時、許可範囲との紐付けの記録|
|台帳|登録された転載の記録の集まり（利用者の端末に置く）|
|公開ページ|公開リポジトリに置く、閲覧のみのページ|
|参照情報|窓口の一覧、文面の例、各国法の参照先、同封文書の文言など、NRSDが保守し利用者のアプリに届ける情報|
|運営者機能|NRSDがリリース、参照情報の保守、指摘の受け付けに使う仕組み|
|要件番号|R-章-機能-連番|

定義すること：システムの境界、構成要素の責務、データの所在と流れ、共通の方針、運営者機能、章の依存。

範囲

- 扱う：クライアントアプリ、公開リポジトリ、利用者の端末のデータ、運営者機能、外部の組織との接点。
- 扱わない：第2段（自動検出）、販売管理、原作の権利（「本システムが守るもの・守らないもの」）、利用者の情報の収集、照合の代行（設計計画書 D-5-1「本システムは利用者を確かめず、利用者の情報を集めない。本システムを使うために登録を求めない」、D-5-5「本システムは照合の手段を提供するが、照合を代行しない」）。

できなければならないこと

- 1-1 境界と構成要素
  - R-1-1-1 各構成要素が持つもの・持たないものが一意に決まっている。
  - R-1-1-2 第2段・販売管理・原作の権利・利用者の情報の収集が境界の外にあることが明示されている。
- 1-2 データ
  - R-1-2-1 全データについて、生成元・保存先・公開/非公開・書き手が決まっている。
  - R-1-2-2 識別子の体系と、データの形式の版が決まっている。
  - R-1-2-3 秘密情報（利用者の署名鍵、NRSD の鍵）の置き場が一覧になっている。
  - R-1-2-4 保持と削除の方針が決まっている。
  - R-1-2-5 多言語のファイル名・文字を扱える。
- 1-3 データの流れ
  - R-1-3-1 署名・販売・SNS投稿・登録・更新・参照情報の配布の各流れが、始点から終点まで途切れない。
  - R-1-3-2 部分失敗しても、データの食い違いが残らない。
  - R-1-3-3 オフラインでできる作業と、接続が要る作業が区別され、オフライン時は保留できる。
- 1-4 信頼と脅威
  - R-1-4-1 信頼の境界が図で示されている。
  - R-1-4-2 脅威（なりすまし、偽アプリ、鍵の窃取、改ざん）の一覧がある。
- 1-5 外部への依存
  - R-1-5-1 TSA・GitHub・投稿先が止まったときの振る舞いが決まっている。
- 1-6 端末と人
  - R-1-6-1 端末の紛失・故障に備え、利用者が記録を書き出し、別の端末で取り込める。
  - R-1-6-2 1人が複数の端末を使える。
  - R-1-6-3 権利の移転と終了（承認の取り消しを含む）を扱える。
- 1-7 共通の方針
  - R-1-7-1 規模と性能の目安、障害時の扱い、記録（操作ログ）、版の互換性、時刻の扱いが全章で共通。
  - R-1-7-2 画面の言語と権利文書の国が別々に扱われる。
- 1-8 運営
  - R-1-8-1 NRSDの関与点、運用体制、障害時の連絡が決まっている。
  - R-1-8-2 運営費用とその負担者が決まっている。
- 1-9 図と対応
  - R-1-9-1 構成図、データの流れ図、信頼の境界図がある。
  - R-1-9-2 設計計画書の決定番号から本書の要件番号への対応表がある。
  - R-1-9-3 章の依存表と、基本設計に入る順序がある（下記）。
- 1-10 運営者機能
  - R-1-10-1 NRSDがリリース、参照情報の保守、指摘の受け付けを行える。
  - R-1-10-2 運営者機能そのものが、偽の更新・偽の参照情報の経路にならない。

基本設計で詰めること

- データのスキーマ、識別子の書式、保持期間の値、性能の数値、運営者機能の形。

基本設計での決定（要旨）

- 構成要素は、クライアントアプリ（利用者の端末のデータを含む）、公開リポジトリ、香港のミラー、運営者ツール、NRSD の鍵（更新と参照情報の電子署名に使う）とする（基本設計 第1章 4.1「構成要素」）。
- 識別番号は作品ごとに1つ発行する61ビットの値とし、企画草案の照合番号・作品番号と同じ値とする（基本設計 第1章 8.2「識別子の体系」）。
- 画面は表示と入力だけを受け持ち、描画・画像の処理・ファイル・通信・鍵の操作は Rust の中心で行う（基本設計 第1章 DD-1-8「画面は表示と入力だけを受け持ち、処理は Rust の中心で行う」）。
- 全記録は一時のファイルに書いて書き切ってから置き換える（同 DD-1-9「記録は一時のファイルに書き切ってから置き換える」）。データは同期されない場所（Windows は Local の AppData）に置く（同 DD-1-10「データは同期されない利用者ごとの場所に置く」）。1台で1つだけ起動する（同 DD-1-11「アプリは1台で1つだけ起動する」）。
- 脅威は STRIDE の6つの分類で要素ごとに洗い、T-1「権利者を装って先に C2PA署名する、または C2PA署名を付け替える」 から T-23「公開ページの「告知コードを確かめる」頁を書き換え、偽の告知コードを示す」 までの23件とした（同 11.2）。

|D-3-6|決定|権利者を装う者は排除できないことを前提とし、照合の扱いを第5章で定める|
|D-5-1|決定|本システムは利用者を確かめず、利用者の情報を集めない。本システムを使うために登録を求めない|
|D-5-2|決定|C2PA署名の証明書は、利用者が入力した情報からクライアントアプリの中で作る。認証局を要しない|
|D-5-3|決定|権利者を装う者による行為（先の署名、署名の付け替えおよび逆の申立て）は防げないものとし、照合の手がかりを示す。判定は行わない|
|D-5-4|決定|本人性と権利性を区別して扱う|
|D-5-5|決定|本システムは照合の手段を提供するが、照合を代行しない|
|I-01|要調査|C2PA署名用の証明書|
|I-02|要調査|告知先アカウントと署名鍵の照合|
|O-01|未決（基本設計 第2章 4「照合の手段と手がかり」 で決定）|照合の手がかりの示し方|
|A-4|項目割りで見つけた抜け|誤った登録の訂正、および装われた真の権利者の救済|
|A-7|項目割りで見つけた抜け|利用者の本人確認の情報の扱い（第2版で本人確認を行わないこととし、前提がなくなった）|
|A-15|項目割りで見つけた抜け|C2PA署名に本名が載る危険|

定義すること：C2PA署名に用いる情報の作り方、権利者を装う者が現れた場合の照合の手がかり、権利者情報と署名鍵の扱い。

範囲

- 扱う：C2PA署名のための情報の入力と証明書の作成、照合の手段と手がかりの示し方、承認と共同の権利、権利者情報、署名鍵。
- 扱わない：利用者を確かめること、利用者の情報の収集、照合の代行・判定（設計計画書 D-5-1「本システムは利用者を確かめず、利用者の情報を集めない。本システムを使うために登録を求めない」、D-5-3「権利者を装う者による行為（先の署名、署名の付け替えおよび逆の申立て）は防げないものとし、照合の手がかりを示す。判定は行わない」、D-5-5「本システムは照合の手段を提供するが、照合を代行しない」）。原作の権利者の確認（「本システムが守るもの・守らないもの」）。

できなければならないこと

- 2-1 本人性（誰が C2PA署名したか）
  - R-2-1-1 画像の C2PA署名から、署名者（証明書に入れた情報）を確かめられる。
  - R-2-1-2 証明書の期限・更新、および入力の誤りに備えがある。
- 2-2 権利性の手がかり
  - R-2-2-1 署名者とその写真の権利者の結び付きを、告知先アカウントとの照合で誰もが確かめられる手段がある。
  - R-2-2-2 原本の保有を手がかりに使える。
  - R-2-2-3 告知先アカウントが乗っ取られたときの備えがある。
- 2-3 権利者を装う者
  - R-2-3-1 先の署名・署名の付け替え・逆の申立てが起きた場合に、照合の手がかりを並べて示せる（判定はしない）。
  - R-2-3-2 導入前の写真について、示せる手がかりと示せない範囲が示されている（示せない部分は13章で宣言）。
  - R-2-3-3 手がかりをもとに、真の権利者がとり得る手段が分かる（第7章）。
- 2-4 入力と承認
  - R-2-4-1 非技術者が C2PA署名のための情報の入力を終えられる（判定の基準は基本設計で定める）。
  - R-2-4-2 承認の付与・範囲・期限・取り消しができる。
  - R-2-4-3 撮影者とコスプレイヤーが同じ写真を扱える。
- 2-5 権利者情報
  - R-2-5-1 画像に載る（公開される）範囲が決まっている。
  - R-2-5-2 本名が署名・画面で意図せず公開されない。
  - R-2-5-3 変更の履歴が端末に残る。
- 2-6 署名鍵
  - R-2-6-1 安全に保管され、処理中も保護される。
  - R-2-6-2 紛失・漏洩時に鍵を作り直し、告知を掲げ替えられ、過去の署名の扱いが決まっている。
  - R-2-6-3 複数端末で使える。

基本設計で詰めること

- 証明書の作り方と中身、照合の手順と手がかりの示し方、鍵の保管方式、入力の画面の流れ。

基本設計での決定（要旨）

- 告知コードと識別番号の文字の並びは Crockford の Base32 とする（基本設計 第2章 DD-2-7「告知コードと識別番号は Crockford の Base32 にそろえる」）。ハンドルネームの向きを変える文字等は受け付けない（同 DD-2-8「ハンドルネームは正規化し、向きを変える文字を受け付けない」）。
- 個人のルートの有効期間は40年とし、作ってから20年を過ぎた個人のルートでは C2PA署名を止めて作り直しを求める。署名用の証明書の期限は個人のルートと同じにする。どの画像も署名から少なくとも20年は一般の検証器で有効と示される。作り直す前の個人のルートは端末に残し、古い出力と古い告知コードの確かめに使う（基本設計 第2章 DD-2-11「証明書の有効期間は、どの画像も署名から20年は有効と示される長さとする」、3.6「過去の個人のルート」）。
- Windows の鍵は資格情報マネージャーの「この PC」の保存、Secret Service のない Linux は合言葉で暗号化した鍵のファイルとする。ハードウェアの鍵は使わない（同 DD-2-5「署名鍵は OS の鍵保管に置き、移行は控えのファイルで行う」）。

依存

- 依存する章：第1章「全体構成」、第8章「リポジトリとデータ管理」（互いに依存する。端末のデータと一体）、第10章「画面とデザイン」（互いに依存する）、第12章「法務との接点」（互いに依存する）
- 依存される章：第3章「署名処理」、第5章「権利文書」、第6章「登録と証拠保全」、第8章「リポジトリとデータ管理」、第10章「画面とデザイン」、第12章「法務との接点」、第13章「設計の検証」

法務へ：なし（利用者の情報を集めないため）。

範囲

- 扱う：入力、C2PAマニフェスト、時刻証明、不可視透かし、照合用ハッシュ、識別番号と作品データ、処理の順序、一括処理、出力。

できなければならないこと

- 3-1 入力
  - R-3-1-1 対応形式が決まっている。
  - R-3-1-2 壊れた画像、巨大な画像、既に署名のある画像を安全に扱える。
- 3-2 マニフェスト
  - R-3-2-1 記録する項目と、記録しない項目（個人情報）が決まっている。
  - R-3-2-2 準拠する仕様の版が決まっている。
  - R-3-2-3 許可範囲・可視署名の操作を記録するかが決まっている（第5章と同時に決める）。
- 3-3 時刻証明
  - R-3-3-1 TSA（中国国内のTSAを含めて検討）が決まっている。
  - R-3-3-2 不通時に保留・後付けができる。
- 3-4 不可視透かし
  - R-3-4-1 埋め込む情報と強度が決まっている。
  - R-3-4-2 図3の「外観に変更を加えない処理」との関係が整理されている。
  - R-3-4-3 GPUのない一般的な端末で動く（速さの基準は基本設計で定める）。
- 3-5 照合用ハッシュ
  - R-3-5-1 算出の対象と記録先が決まっている。
- 3-6 識別番号と作品データ
  - R-3-6-1 番号が一意に発行され、ファイル名・キャプションに表記できる。
  - R-3-6-2 作品データの項目と記録先が決まっている。
- 3-7 処理の順序と系統
  - R-3-7-1 署名を壊さない処理の順序で動く。
  - R-3-7-2 受け渡し用とSNS用の差が決まっている。
  - R-3-7-3 原本を変えない。
  - R-3-7-4 撮影情報（位置情報等）を除去する。
- 3-8 一括処理
  - R-3-8-1 中断・再開・一部失敗に対応する。
  - R-3-8-2 進捗と結果を示せる。
- 3-9 出力
  - R-3-9-1 出力の名前と構成が決まっている。
  - R-3-9-2 出力を利用者が自分で確かめられる。
  - R-3-9-3 投稿先とCloudでC2PA署名が残るかを把握し、残らない場合の扱いが決まっている（NRSD の決定により Cloud も調査の対象とする）。

基本設計で詰めること

- マニフェストの具体的な項目、TSA、透かしのパラメータ、番号の書式、作品データの記録先、2系統の差。

基本設計での決定（要旨）

- 対応形式は JPEG・PNG・TIFF・WebP。RAW・HEIC 等はファイルの指紋のみを記録する（基本設計 第11章 DD-11-5「画像の読み書きは image crate で行う」）。
- 要件 R-3-4-2「図3の「外観に変更を加えない処理」との関係が整理されている。」 の「外観に変更を加えない処理」は「見た目に分かる変化を加えない処理」と読む（基本設計 第3章）。
- O-08「識別番号の発行主体」 は設計計画書 第2版で D-7-7「識別番号は、クライアントアプリが発行し、C2PAマニフェストに自動で記録する。ファイル名の後ろに付けるかは、保存の際に利用者が選ぶ」（識別番号はクライアントアプリが発行する）として決定した。基本設計 第3章 7.1「識別番号」 で、企画草案の照合番号・作品番号と同じ値とした。O-10「作品データの記録の形式」・O-11「受け渡し用画像への可視署名」 は基本設計 第3章「署名処理」で解消した（O-11「受け渡し用画像への可視署名」：受け渡し用の可視署名はテンプレートごとに決める）。
- 著作者名・著作権表示・利用条件はマニフェストの `cawg.metadata` に置く（C2PA 2.x の `c2pa.metadata` は固定の項目のみを許す）。
- 出力のファイルには、C2PA を読まない道具にも権利者が見えるよう、IPTC の写真のメタデータの権利の項目を XMP と EXIF で書く（基本設計 第3章 DD-3-8「ファイルに IPTC の権利の項目を書く」）。
- 符号化とファイルへの記載は C2PA署名の前に終える（C2PA のハードバインディングは最終のバイトに掛かる。基本設計 第3章 DD-3-1「処理の順序を定める」）。可視署名の操作の作り方の種類は `humanEdits` とし、生成 AI の値を付けない（同 3.4）。

依存

- 依存する章：第1章「全体構成」、第2章「署名の情報と照合」（署名鍵）、第5章「権利文書」（互いに依存する）、第8章「リポジトリとデータ管理」（作品データの置き場）、第11章「開発基盤」（互いに依存する。ライブラリ・実行環境）、第12章「法務との接点」（互いに依存する）
- 依存される章：第4章「画像編集と一括適用」、第5章「権利文書」、第6章「登録と証拠保全」、第10章「画面とデザイン」、第11章「開発基盤」、第12章「法務との接点」、第13章「設計の検証」

法務へ：時刻証明の国ごとの効力。

## 4. 画像編集と一括適用

受ける決定は次の表のとおりである（設計計画書 第2版の決定・要調査・未決、および項目割りで見つけた抜け）。

|番号|種類|内容|
|---|---|---|
|D-8-3|決定|編集画面で作成したデザインをテンプレートとし、1枚ずつにもフォルダー単位にも適用できる|
|D-8-4|決定|一括適用においても、写真ごとに配置、向きおよび色を調整できる|
|A-11|項目割りで見つけた抜け|フォントのライセンス|

定義すること：可視署名を作り、画像に適用する機能。

範囲

- 扱う：可視署名、テンプレート、配置、編集の操作、一括適用、SNS向けの出力。
- 扱わない：権利表示と関係のない画像の編集。

できなければならないこと

- 4-1 可視署名
  - R-4-1-1 名前・アカウント名・日付・Overlay画像・ライセンス表記を置ける。
  - R-4-1-2 向き（縦書き・回転）と色を変えられる。
  - R-4-1-3 使うフォントのライセンスが確かめられている。
  - R-4-1-4 取り込む素材を安全に扱える。
  - R-4-1-5 要素を層として重ね、重なりの順・表示・固定・不透明度を扱える。
- 4-2 テンプレート
  - R-4-2-1 デザインを保存し、繰り返し使える。複数端末で使える。
  - R-4-2-2 既定のテンプレートを用意するかが決まっている。
- 4-3 配置
  - R-4-3-1 被写体を避けて置ける。
  - R-4-3-2 収まらない画像でも破綻しない。
- 4-4 編集の操作
  - R-4-4-1 プレビューを見ながら直せ、取り消せる。
  - R-4-4-2 原本を壊さない。
  - R-4-4-3 編集の途中の状態が自動で保存され、後で続きから再開できる。
- 4-5 一括適用
  - R-4-5-1 フォルダーに一括で適用し、写真ごとに直せる。
- 4-6 出力
  - R-4-6-1 SNS向けの大きさ・圧縮・色空間で出せる。

基本設計で詰めること

- 自動配置の有無と方式、テンプレートの形式、フォントの選定。

基本設計での決定（要旨）

- 可視署名は文字の層と画像の層を、配置の単位の「まとまり」に重ねる。文字の層には写真ごとに変わる値を差し込める（基本設計 第4章 DD-4-2「層は文字の層と画像の層の2種とし、文字の層に差し込みを使える」、DD-4-3「層をまとめたまとまりを配置の単位とする」）。
- 文字の組み立てと描画は、プレビューも書き出しも同じ Rust の仕組みで行い、縦書きの組版は自作する。OS のフォントを使わない（同 DD-4-5「文字の組み立てと描画はプレビューも書き出しも同じ Rust の仕組みで行う」、DD-4-6「文字は同梱と持ち込みのフォントだけで描き、OS のフォントを使わない」）。
- 編集の途中の状態は作業として自動で保存し、取り消しとやり直しは作業ごとの履歴（既定200段）で行う（同 DD-4-8「編集の途中の状態を作業として自動で保存する」、DD-4-9「取り消しとやり直しは作業ごとの履歴で行う」）。
- 書き出しは投稿先ごとの型から選ぶ（同 DD-4-11「書き出しは投稿先ごとの型から選ぶ」）。

依存

- 依存する章：第1章「全体構成」、第3章「署名処理」（処理の順序）、第10章「画面とデザイン」（互いに依存する）、第11章「開発基盤」（互いに依存する）
- 依存される章：第10章「画面とデザイン」、第11章「開発基盤」、第12章「法務との接点」、第13章「設計の検証」

- 輸出管理は、公開の標準の暗号のみを使い、公開・無償で配ることで扱う（基本設計 第12章 DD-12-8「公開の標準の暗号のみを使い、公開・無償で配る」）。
- NRSD の運営に関わる法の論点は法務調査に置く（基本設計 第12章 7「法務の論点（法務調査に置き、運営の判断の材料とするもの）」）。
