## 本書の位置付け

- 概要設計書 第8章を詳細化する。本章は、利用者の端末のデータの配置、端末の外に出るもの、控えのファイル（形式、作り方、戻し方、統合）、公開リポジトリと公開ページ、香港のミラー、完全性、容量、GitHub への依存を定める。第2章「署名の情報と照合」と同時に設計し、第6章「登録と証拠保全」と容量で往復する。
- 本章は検討メモ「第2章 署名の情報と照合、第8章 リポジトリとデータ管理の検討」（NRSD の内部の検討の記録であり、本書とともには配らない。設計の根拠となる事実は、本書の各節に出典とともに書いた）に基づく。第3稿で、記録の端末の中での暗号化、参照情報の包みの形、GitHub のアカウントとリポジトリの守り、ミラーの運用、控えの置き方を加えた（調べた事実は同じ検討メモの第2巡の節）。

- 全記録の書き込みは第1章 10.2「保存」の手順（一時のファイルと置き換え）による。

### 2.2 端末の外に出ないこと

- アプリが端末の外へ送るのは、第1章 4.2「外部とのやり取り」の表の相手と中身に限る。いずれも利用者の記録そのものを含まない。
- 利用者が自分で作る控えのファイル（5）と、利用者が自分で送る指摘の電子メール（第10章 9「指摘の受け口」）を除き、記録は端末の外に出ない。

## 3. 公開リポジトリ

### 3.1 構成

- リポジトリの中の配置は第11章 7「リポジトリの構成」による。

|場所|中身|
|---|---|
|README|3言語。入手の案内、公式版の見分け方（第9章 3「公式版の証明」）、照合の手順（第2章 4.1「告知先アカウントとの照合」）、出どころの証明の確かめ方（第11章 6「部品表と出どころの証明」）|
|リリース|3つの OS の配布物、更新の電子署名、部品表（SBOM）、ライセンスの一覧、出どころの証明、その版に同梱した参照情報の包みの写し。改変できないリリースとする（3.5）|
|`update/`（公開ページの下）|更新の案内（JSON。GitHub 用。第9章 4.3「更新の案内（静的な JSON）の形」）。リリースの外に置き、差し替えと1つ前の版への戻しができる（第9章 6.5「誤りのある版を出した時」）|
|`reference/<版>/`（公開ページの下）|参照情報（窓口、文面、各国法の参照先、同封文書の文言）と NRSD の記録の電子署名。アプリは公開ページ（GitHub Pages）の URL から取得する（第1章 7.5「参照情報の取得」）|
|公開ページ|3.3|

- 個人情報、利用者ごとの情報を置かない（R-8-1-1「ソフト、公開ページ、参照情報を置き、個人情報を持たない。」）。

### 3.2 改造版との区別

- 参照情報と更新は NRSD の鍵で電子署名され、アプリは公開鍵を内に持って検証する。改造版が配る参照情報・更新は、公式のアプリでは検証に通らない。
- 公式版の見分け方は第9章 3「公式版の証明」。

### 3.3 公開ページ（O-05 の決定）

|載せるもの|載せないもの|
|---|---|
|本システムの説明、入手の方法（公式の入手先の明示）|転載サイトの名前・URL|
|照合の手順（一般の検証サイトでの見え方、手がかりの読み方。第2章 4.1「告知先アカウントとの照合」）と、「告知コードを確かめる」頁（画像をブラウザの中だけで読み、C2PA署名の証明書の連なりから告知コードを計算して示す静的な頁。画像はどこへも送らない。第2章 DD-2-9「x5chain に個人のルートの証明書を入れる」）|利用者のハンドルネーム・告知先アカウント|
|参照情報の版と更新日|事件の個別の内容|
|原作の権利に関与しないこと、法的助言でないこと|—|
|障害とお知らせ（第1章 18.1「NRSD の関与点と体制」）|—|

### 3.4 参照情報の包み

|ファイル|中身|
|---|---|
|`reference/<版>/index.json`|`schema: nrsd.reference/1`、鍵の識別子（電子署名に使った参照情報の電子署名の鍵の公開鍵の SHA-256）、版の番号（1から始まる整数。鍵ごとに数え、上げるだけで戻さない）、発行の日時（RFC 3339）、期限（発行から120日。初期値。四半期ごとの見直し（第7章 2.2「追従」）に30日の余裕を足した）、アプリの最低限の版（第9章 4.2「古い版の利用者（更新の強制）」）、ファイルの一覧（パス、大きさ、SHA-256）|
|`reference/<版>/index.json.sig`|`index.json` を JCS（RFC 8785）で正規化した値への ECDSA P-256 の電子署名。鍵は NRSD のハードウェアトークン（PIV の電子署名の枠。署名のたびに PIN を入れる）|
|`reference/<版>/contacts.json` 等|窓口（第7章 2「窓口」）、文面の例（第7章 3「文面の例」）、各国法の参照先（第7章 4「各国法の参照先」）、同封文書の文言（第5章 3.7「共通部の文の下書き」）、お知らせ（第10章 G-21「お知らせ」）|
|`reference/latest.json`|最新の版の番号と `index.json` の SHA-256（どの版を取りに行くかの案内。これ自体は信頼の根拠にしない）|

- アプリの検証（第1章 7.5「参照情報の取得」の2の中身）：

|順|確かめること|通らない時|
|---|---|---|
|1|`index.json` の大きさが64KB 以下、各ファイルが一覧の大きさ以下で合計が1MB 以下（第1章 4.2「外部とのやり取り」 の上限）|取得をやめる（大きなデータで端末を妨げる攻撃への備え）|
|2|`index.json.sig` を、アプリに埋め込んだ参照情報の公開鍵で検証する|使わない。`REF` の番号で記録する|
|3|鍵の識別子がアプリに埋め込んだ公開鍵のものであり、版の番号がその鍵で数えた手元の版より大きい|手元より小さい・等しい包み、古い鍵の包みは使わない（版の戻しへの備え）|
|4|各ファイルの SHA-256 が一覧と合う|包み全体を使わない（組み合わせの偽りへの備え）|
|5|期限|期限を過ぎていても手元の最新として使うが、G-21「お知らせ」に「参照情報が古くなっています（最終の確かめ：日付）」と示す（凍結への備え）。期限から30日を過ぎたら、窓口の案内（G-17「対処の案内」）の上端にも示す|

- 同梱の包み：各リリースのアプリに、その時点の最新の参照情報の包み（目録と電子署名つき）を同梱する。初回の起動がオフラインでも、同封文書・告知の文例・ひな形を作れる。起動の後に取得した包みの版が同梱の版より大きければ、取得したものを使う（3.4 の検証の3）。
- 公開鍵の差し替え：参照情報の電子署名の鍵の差し替えは、新しい公開鍵を入れたアプリの版（更新の電子署名の鍵で電子署名して配る）だけで行う。包みの目録（`index.json`）に鍵の識別子（公開鍵の SHA-256）を持たせ、アプリは版の番号を鍵ごとに数える。新しい公開鍵を入れた版のアプリは、古い鍵の包みを受け付けず、古い鍵で数えた版の番号を捨てて、新しい鍵の包みの版を1から数える。
  - 理由：「最低限の版」は包みの中にあり、古い鍵で電子署名しないと上げられない（鍵を失った時は上げられない）。鍵が漏れた時は、攻撃者が極端に大きい版の番号の包みを出せ、手元の版の番号がその番号になると、鍵を替えた後の正しい包みを「版の戻し」として拒み続ける。鍵ごとに版を数え、差し替えを更新の電子署名の鍵の経路に委ねれば、どちらも起きない（TUF の仕様の、信頼の根の差し替えを別の鍵の経路で行う考え方と同じ）。
  - 漏れた場合、新しい版のアプリを入れるまでの間、利用者のアプリは攻撃者の包み（偽の窓口、偽のお知らせ（G-21「お知らせ」）、吊り上げた「最低限の版」（第9章 4.2「古い版の利用者（更新の強制）」。C2PA署名と登録が止まる）を含む）を受け付け得る（第13章 H-22「NRSD の鍵（更新・参照情報）が盗まれた場合、偽の更新・参照情報を配られ得る」）。手順は第1章 18.3「NRSD の鍵の事故」による。

### 3.5 GitHub のアカウントとリポジトリの守り

|対象|設定|
|---|---|

|タグ|`v*` のタグの作成・削除を所有者に限る規則|
|リリース|改変できないリリースを有効にする。下書きの状態で配布物・更新の電子署名・部品表をすべて付けてから公開する（公開の後は付け足せない）。誤りのある版は消さず題を改める（第9章 6.5「誤りのある版を出した時」）。更新の案内はリリースに入れず、公開ページの `update/` に置く（3.1。案内の差し替えと戻しのため）|

## 4. 完全性

- 改ざんの検出：作品データ・事件記録・状況の追記・承認書に利用者の鍵で記録の電子署名を付け（第1章 DD-1-5「端末の記録に記録の電子署名を付けて検証する」）、読む時に検証する。証拠のファイルは事件記録に SHA-256 を記録し、時刻証明を付ける（第6章）。
- 履歴：記録は追記のみ。訂正・取り下げも新しい記録として追記する（第6章 DD-6-5「事件記録は追記のみとする」）。
- 検証に通らない記録を読んだ時は、その記録を使わず、利用者に知らせ（第1章 10.3「エラー」 の `STO` の番号）、控えのファイルからの戻しを案内する。
- 起動の時に、全記録の記録の電子署名の検証を裏で行う（件数が多い場合は1日1回まで。初期値）。

## 5. 控えのファイル

### 5.1 形式

- 外側は age の形式（C2SP の age の仕様）。受け手の段は合言葉（scrypt）の1段のみ（age の仕様で、合言葉の段は唯一の段でなければならない）。scrypt の強さは 2^18（age の公式の Go の実装の既定。注記「現代の機械で1秒」）。
- 中身は ZIP。

|ZIP の中|中身|
|---|---|
|`manifest.json`|控えの形式の版（`schema: nrsd.backup/1`）、作った日時、アプリの版、各記録の形式の版、個人のルートの告知コード、ファイルの一覧（パス、大きさ、SHA-256）|
|`keys/`|個人のルートの鍵と署名用の証明書の鍵（PKCS#8）。鍵保管から取り出して入れる|
|`data/`|2.1 の表で「控えに含む」のもの|

- 拡張子は本アプリ専用（例：`.nrsdbak`）。
- 部品：age の Rust 版（age 0.12.1、MIT OR Apache-2.0）、zip（第11章 4.1「Rust の部品」）。

### 5.2 作り方

|順|処理|
|---|---|
|1|利用者が保存先と合言葉を選ぶ。合言葉は12文字以上（初期値）。よく使われる合言葉の一覧（初期値で1万件）にあるものは受け付けない|
|2|書き出し・登録の途中の処理がないことを確かめる（あれば終わるまで待つ）|
|3|鍵を鍵保管から読み、記録を読んで、ZIP にまとめながら age で暗号化し、一時の名前で書く（逐次に処理し、全体を記憶に載せない）|
|4|書き終えたら、ファイルを読み直して見出しを復号し、`manifest.json` の SHA-256 の一覧と照らして確かめる|
|5|正式の名前に変え、作った日時を設定に記録する（ホームの「最後の控え」の表示と、30日の勧め。第1章 13「端末と人」）|

- 保存先の案内：同じ PC の中ではなく、外部の記憶媒体（USB の記憶媒体等）か、利用者の Cloud に置くことを勧める。暗号化されているため Cloud に置いてもよいが、合言葉が弱ければ読まれ得る旨を示す。
- 合言葉を忘れると戻せない旨を、作る時に示し、確かめの押し下げを求める。
- ［要実測］証拠を含む5GB の控えの作成の時間。判定：一般的な PC（第1章 14.1「規模と性能の目安」）で15分以内（初期値）。

### 5.3 戻し方（取り込み）

|順|処理|
|---|---|
|1|利用者がファイルと合言葉を入れる|
|2|age の見出しを読み、scrypt の強さが 2^22 を超えるものは受け付けない（age の公式の Go の実装が受け入れる上限。解読に時間のかかる細工を防ぐ）|
|3|復号しながら ZIP を読み、`manifest.json` を確かめる（形式、版、ファイルの一覧）。ZIP の中のパスに `..` や絶対のパスがあれば中止する。展開の合計の大きさは一覧の大きさと一致しなければ中止する（第1章 10.6「外から入るものの確かめ」）|
|4|各ファイルの SHA-256 を一覧と照らす|
|5|個人のルートが今の端末と同じか、端末に記録がないかを確かめる（5.4）|
|6|鍵を鍵保管に入れ、記録を一時の場所に展開し、記録の電子署名を検証してから正式の場所に移す|
|7|取り込んだ件数と、検証に通らなかった記録の一覧を示す|

- 自分より新しいアプリで作った控え（記録の形式の版が新しい）は、アプリの更新を促して取り込まない。

### 5.4 統合

|今の端末|扱い|
|---|---|
|記録がない（新しい端末）|そのまま取り込む|
|同じ個人のルートの記録がある（2台で使っている）|統合する（下の規則）|
|違う個人のルートの記録がある|統合しない（DD-8-6「個人のルートが違う控えは統合しない」）。「今の記録を控えのファイルで置き換える（今の記録は先に控えを作る）」か「取りやめる」かを選ばせる|

- 統合の規則（同じ個人のルート）：

|記録|規則|
|---|---|
|作品データ（一括処理ごとのファイル）|番号が同じで中身が同じなら1つ。番号が同じで中身が違えば、両方を残し、違いを示す（通常は起きない）|
|事件記録と状況の追記|事件の番号ごとに、状況の追記を合わせ、時刻の順に並べる（追記のみの記録のため、両方を残して足りる）|
|証拠|SHA-256 の名前で合わせる（同じものは1つ）|
|テンプレート・作業|番号が同じなら、版の番号（最後に直した日時）の新しい方を採り、古い方を控えとして残す|
|承認書等|番号で合わせる|
|設定|今の端末のものを残す|
|変更の履歴|時刻の順に合わせる|

### 5.5 控えの勧め

- 初回の入力の後と、最後に控えを作ってから30日（初期値）経った時に、ホームで勧める（第10章 G-07「ホーム」）。
- 証拠を登録した後、控えを作っていない証拠があれば、ホームに件数を示す。

### 5.6 控えの置き方の案内

- 控えを作る画面（G-05「控えを作る」）と README で、一般に勧められる「3-2-1」の原則（大事なファイルの写しを3つ持ち、2種類の媒体に置き、1つを離れた場所に置く。米国 CISA「Data Backup Options」）に沿って、次を示す。

|写し|置き場の例|
|---|---|
|1つ目|この PC のアプリの記録（元）|
|2つ目|外部の記憶媒体（USB の記憶媒体、外付けのディスク）の控えのファイル|
|3つ目|離れた場所：利用者の Cloud（控えは暗号化されている）、または別の場所に置いた記憶媒体|

- 控えのファイルは作るたびに新しい名前（作った日時を名前に含む）で作り、古い控えを上書きしない。古い控えを消すかは利用者が決める。アプリは、置き場に同じ個人のルートの控えが3つ以上あれば、最も古いものを消してよい旨を示すだけとする（利用者のファイルを消さない）。

## 6. 容量

### 6.1 端末の容量の目安

|データ|見積もり（初期値からの見積もり）|
|---|---|
|作品データ|1作品2KB×年5,000作品＝10MB/年|
|証拠|1件20MB×年200件＝4GB/年|
|作業|1作業数 MB（写真の場所と手直しのみ）|
|テンプレート・素材|数十MB|
|縮小の画像（キャッシュ）|1枚約50KB×500枚＝25MB/作業（消しても作り直せる）|

- 空きが1GB（初期値）を下回ったら知らせ、古い事件の証拠を控えのファイルにしてから消すことを案内する。消す前に請求の期間を示す（第1章 8.4「保持と削除」）。
- キャッシュが1GB（初期値）を超えたら、古い作業の縮小の画像から消す。

### 6.2 中国本土

- 取得（更新、参照情報）：GitHub から取得し、失敗したら香港のミラー（DD-8-5「中国本土向けに香港のミラーを置く」）から取得する。配布物と参照情報の包みは電子署名で検証するため、ミラーでの差し替えは検出できる。更新の案内（JSON）には電子署名がないため、案内の書き換えによる古い版の押し付けは、案内の版と更新の電子署名の版の照合（第9章 DD-9-2「更新は Tauri の仕組みで取得し、案内と電子署名の版を照らす」）で防ぐ。
- 初回の入手：README の中国語の節に、ミラーの最新版の配布物への直接のリンクと SHA-256 を載せる（3.6、第9章 5「入手経路」）。README そのものに届かない場合は入手できない（第13章 H-17「中国本土では README に届かないことがある」）。
- 記録の書き込みは端末の中で完結するため、GitHub への接続は要らない。
- ミラーの候補：阿里云の OSS の香港の地域（静的な配信）。香港の地域は ICP 備案が要らない（阿里云の案内）。中国本土からの遅延は30〜50ms とする案内がある（同）。
- 費用：保管と外への転送の量で決まる。［要見積］配布物の大きさ（第11章 4.3「素材」）×取得の回数。
- ［要実測］中国本土からミラーへの到達と速さ。判定：ミラーから更新と参照情報を取得できること。満たさない場合は破れとして宣言する（第13章）。

### 6.3 ミラーの費用の見積もり

- 費用は、保管の量と外への転送の量で決まる。香港の地域の外への転送は月5GB まで無料（阿里云の OSS の案内）。単価の表は阿里云の価格のページにあり、本書の調べ（2026-09-29）では画面の取得ができなかった。［要見積］NRSD が契約の前に価格のページで単価を確かめる。
- 見積もりの式：月の外への転送量 ＝ 配布物の大きさ（第9章 2.1「OS ごとの配布物」 の見込み。各 OS 200MB 前後、Linux は同梱の部品の分だけ大きい。設計の目標は300MB 以下）×月にミラーから更新・新規の導入をする利用者の数 ＋ 参照情報（1MB 以下）×取得の回数。保管の量 ＝ 1つの版の配布物（Windows のインストーラ、macOS の DMG と更新用の `.app.tar.gz`、Linux の AppImage の4つ。各約200MB）×2つの版（約1.6〜2GB）＋ Linux の AppImage に同梱した LGPL の部品のソースの包み（2つの版の分。［要見積］大きさ）＋参照情報。
- 例：ミラーの利用者が月に200人更新する場合、約50GB/月の転送になる。

## 7. GitHub への依存

|事象|備え|
|---|---|
|GitHub の障害|更新と参照情報はミラーから取得。記録は端末にあるため作業は止まらない|
|アカウント・リポジトリの停止|ミラーと別の git のホスティングへ公開リポジトリを移し、アプリの更新で取得先を差し替える。アプリの更新の取得先を複数持つ（第9章 DD-9-2「更新は Tauri の仕組みで取得し、案内と電子署名の版を照らす」）|
|規約|公開リポジトリには個人情報・転載の情報を置かない（法務調査 L-18「GitHub の規約」）|
|リリースの容量|リリースの1つのファイルは2GiB 未満、1つのリリースのファイルは1,000まで。リリースの合計の大きさと転送量に上限はない（GitHub の案内「About releases」）。配布物の大きさの設計の目標は300MB 以下（第9章 2.1「OS ごとの配布物」）。第1章 4.2「外部とのやり取り」 の500MB は取得の上限であり、これを超える配布物は取得しない|
|アカウントの乗っ取り|3.5 の守り。乗っ取られても、更新と参照情報は NRSD の鍵の電子署名がなければ適用されない（3.2）|

## 10. 本章で宣言する破れ

- 控えのファイルを作っていない利用者が端末を失うと、記録・証拠・署名鍵を失う。
- 控えのファイルの合言葉が弱い場合、ファイルを盗んだ者に署名鍵と記録を読まれ得る（第1章 T-5「控えのファイルを盗んで読む」）。
- OS の全体の暗号化を有効にしていない端末が盗まれた場合、アプリのデータの場所の記録（証拠、事件記録、権利者情報）は読まれ得る（DD-8-7「記録の暗号化は OS の全体の暗号化に任せる」。署名鍵は OS の鍵保管にあり、この限りでない）。
- 参照情報の配布が止められた（凍結された）場合、アプリは手元の最後の包みを使い続ける。期限の知らせ（3.4）で気付けるが、新しい窓口は届かない。
- 合言葉を忘れると、控えのファイルから戻せない。
- 2台で並行して使う場合、統合は控えのファイルを介する手作業であり、自動の同期はない。
- CI・GitHub の組織が乗っ取られると、公開リポジトリのリリース・README・公開ページを書き換えられ、正しくコード署名された偽の配布物を置かれ得る（第13章 H-44「CI・GitHub の組織が乗っ取られると、正しくコード署名された偽の配布物を公式のリリースに置かれ得る」）。
- GitHub の組織の所有者が1人の間、その者が認証と回復の手段をすべて失うと組織を回復できない（第13章 H-45「GitHub の組織の所有者が1人の間、その者がアカウントの認証の手段と回復の手段をすべて失うと、組織を回復できない」）。
