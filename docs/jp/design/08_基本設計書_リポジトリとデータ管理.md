## 本書の位置付け

- 概要設計書 第8章を詳細化する。本章は、利用者の端末のデータの配置、端末の外に出るもの、控えのファイル（形式、作り方、戻し方、統合）、公開リポジトリと公開ページ、香港のミラー、完全性、容量、GitHub への依存を定める。第2章「署名の情報と照合」と同時に設計し、第6章「登録と証拠保全」と容量で往復する。
- 本章は検討メモ「第2章 署名の情報と照合、第8章 リポジトリとデータ管理の検討」（NRSD の内部の検討の記録であり、本書とともには配らない。設計の根拠となる事実は、本書の各節に出典とともに書いた）に基づく。第3稿で、記録の端末の中での暗号化、参照情報の包みの形、GitHub のアカウントとリポジトリの守り、ミラーの運用、控えの置き方を加えた（調べた事実は同じ検討メモの第2巡の節）。
- 受ける決定は次の表のとおりである。設計計画書の決定・要調査・未決の文は第13章 1.2「設計計画書の決定から概要設計書・基本設計への対応」と概要設計書の行き先表による（本章には写さず、番号と項目割りの抜けだけを載せる）。

### 2.2 端末の外に出ないこと

- アプリが端末の外へ送るのは、第1章 4.2「外部とのやり取り」の表の相手と中身に限る。いずれも利用者の記録そのものを含まない。
- 利用者が自分で作る控えのファイル（5）と、利用者が自分で送る指摘の電子メール（第10章 9「指摘の受け口」）を除き、記録は端末の外に出ない。

## 3. 公開リポジトリ

### 3.1 構成

- リポジトリの中の配置は第11章 7「リポジトリの構成」による。

|場所|中身|
|---|---|
|README|3言語。入手の案内、公式版の見分け方（第9章 3「公式版の証明」）、照合の手順（第2章 4.1「告知先アカウントとの照合」）、出どころの証明の確かめ方（第11章 6「部品表と出どころの証明」）|

- 恒久の URL：画像・マニフェスト・告知に埋める URL（`xmpRights:WebStatement`、ODRL の `nrsd:` の名前空間、確認の方法）は `https://c2pa4cosplayer.nrsd.jp/` の下とし、DNS の CNAME で GitHub Pages に向ける（GitHub Pages の custom domain。TLS は GitHub が出す）。転送を返すサーバーは要らず、NRSD が持つのは DNS の記録だけ（第1章 DD-1-2 と両立）。GitHub の組織を失ったら CNAME を別の静的な置き場に向け直す（第13章 H-45）。法人のサイトの下の転送（`nrsd.jp/c2pa4cosplayer/`）は採らない。

### 3.2 改造版との区別

- 参照情報と更新は NRSD の鍵で署名した TUF のメタデータで守られ、アプリは `root.json` を内に持って検証する（第9章 4.3）。改造版が配る参照情報・更新は、公式のアプリでは検証に通らない。
- 公式版の見分け方は第9章 3「公式版の証明」。

- 参照情報の署名の鍵は、主と予備の2本のハードウェアトークンとし、TUF の委任 `reference` の役割に2本の公開鍵をしきい値1で置く（第9章 4.3）。主の鍵の事故では予備の鍵でそのまま包みを出せる。目録には署名に使ったトークンの attestation の証明書を添える（2026-09-30 NRSD の要求）。
- RDAP のブートストラップの一覧（IANA の配る、どの窓口に問い合わせるかの表）を包みに含める。運営者ツール M-01「参照情報」 が IANA の一覧を取得して前の版との差分を示し、版を上げる。アプリは IANA に問い合わせない（第6章 5）。プラットフォームの判定の表（第2章 2.3、第6章 2.1）も包みに含め、表の全行に試験の URL を持たせて CI で回す。
- ClearURLs の追跡の引数の規則（第1章 10.10「URL と QR の形」）も包みに含め、四半期ごとに上流と照らして版を上げる。
- 自分の別の端末・確認済みの相手・Cloud の同期フォルダー・ファイルから届いた包みは、TUF の `timestamp.json` の期限（7日）が切れていても、`snapshot`・`targets` の署名が正しく版が手元より新しければ受け入れ、「確かめの日付が古い（日付）」の印を付ける（届いた包みは NRSD の署名がなければ通らないため、凍結の危険は網からの取得で解ける）。網から取得できた時に印は消える。
- 包みはファイル単位で取得でき、アプリは手元と SHA-256 が違うファイルだけを取得する。各ファイルは圧縮（zstd）して置き、目録に圧縮前後の大きさと予算を持つ。M-01「参照情報」 は予算の80%で警告する。目録は「訂正」の印（第5章 2.4）を持てる。取得の元は5つ（公開ページ、香港のミラー、自分の別の端末と「確認済み」の相手（5.4）、利用者の Cloud の同期フォルダー（控えの置き場）に置かれた包み、利用者が選んだファイル）とし、届く元から最も新しい版を取る。検証（上の表）は元に依らず同じ。利用者にはアプリの更新と同じく見せない（Windows の配信の最適化が CDN と他の PC の両方から受け取るのと同じ考え）。包みは公開の情報であり NRSD の電子署名で守られるため、経路が変わっても信頼は変わらない。別の端末・相手へ渡す時に流れるのは包みと版だけで、利用者の情報・記録は流れない（G-20「設定」 で切れる）（2026-09-30 NRSD の要求）。
- 包みの目録と更新の案内は TUF の形のメタデータ（第9章 4.3）に一本化し、tough で検証する。`index.json` の版と期限の検証は TUF の snapshot と timestamp の検証で置き換える（2026-10-01 NRSD の要求）。
- 同梱の包み：各リリースのアプリに、その時点の最新の参照情報の包み（TUF のメタデータつき）を同梱する。初回の起動がオフラインでも、同封文書・告知の文例・ひな形を作れる。起動の後に取得した包みの版が同梱の版より大きければ、取得したものを使う（3.4 の検証の3）。
- 鍵の差し替えと事故の手順は第1章 18.3「NRSD の鍵の事故」（TUF の役割の鍵の入れ替え。第9章 4.3）による。鍵が漏れた場合に偽の包みを受け付け得る期間は第13章 H-22「NRSD の鍵（更新・参照情報）が盗まれた場合、偽の更新・参照情報を配られ得る」。
- 脅威 T-7（なりすまし・改ざん）：偽の参照情報・更新を配る。攻撃する者：公開リポジトリを乗っ取った者。狙う資産：全利用者。残る破れ：署名鍵そのものの漏れ
- 脅威 T-20（改ざん）：古い正しい参照情報の包みを返し続け、または古い版に戻す（凍結・版の戻し）。攻撃する者：ミラー・通信の経路を乗っ取った者。狙う資産：アプリ（参照情報）。残る破れ：凍結の間、新しい窓口は届かない
- 脅威 T-25（改ざん）：偽の参照情報の包みを別の端末や相手から配る。攻撃する者：端末の番号を知った者。狙う資産：参照情報。残る破れ：—
- 秘密：参照情報の電子署名の鍵。置き場：ハードウェアトークン（NRSD の管理用 PC）。漏れた時：偽の参照情報を配られ得る。TUF の役割の鍵を替える（第1章 18.3）

## 5. 控えのファイル

### 5.1 形式

- 外側は age の形式（C2SP の age の仕様）。受け手の段は合言葉（scrypt）の1段のみ（age の仕様で、合言葉の段は唯一の段でなければならない）。scrypt の強さは 2^18（age の公式の Go の実装の既定。注記「現代の機械で1秒」）。
- 受け手：控えは「回復の鍵」（X25519 の鍵。文字の形は age の標準の鍵の文字列（`AGE-SECRET-KEY-1…`。Bech32）。初回に「緊急キット」（1Password の Emergency Kit と同じ形。1枚の PDF（PDF/A-2u。ISO 19005-2。長期の保存と印刷。加えて PDF/UA-1（ISO 14289-1）の構造を持ち、読み上げで読める）：回復の鍵の QR（第1章 10.10「URL と QR の形」の `recovery`）と文字、控えの置き場、戻し方、引き継ぐ人への手順。3言語）として作り、印刷して保管するよう案内する。端末には置かない。NRSD は写しを持たない）の公開鍵に対して暗号化し、回復の鍵の秘密鍵を合言葉（scrypt）で暗号化したファイルを控えに添える。合言葉で開く時は、添えた鍵を復号してから控えを開く。回復の鍵の印刷で開く時は直接開く。合言葉を忘れても回復の鍵で戻せる。age の合言葉の段が唯一の段でなければならない規則は、この二段の形で満たす（2026-09-30 NRSD の要求）。
- 回復の鍵は個人のルートに1つ。公開鍵は端末に依らない設定（第10章 10）として別の端末に揃い、どの端末の控えも同じ鍵で暗号化する。印刷を失った時の「回復の鍵を作り直す」の後は、以後の控えを新しい鍵で作り、古い控えは古い印刷でしか開けない旨を示す。
- 中身は ZIP。

|ZIP の中|中身|
|---|---|
|`manifest.json`|控えの形式の版（`schema: nrsd.backup/1`）、作った日時、アプリの版、各記録の形式の版、個人のルートの告知コード、端末の番号、`kind`（`full`・`diff`）、`chain_id`（まとめ直しごとに新しく）、`seq`（1から）、`parent_sha256`（前の控えの `manifest.json` の SHA-256）、ファイルの一覧（パス、大きさ、SHA-256）。戻す時は `full` から `seq` の順に当て、`parent_sha256` の連なりを確かめ、欠け・入れ替えがあればそこで止めて「差分 N が欠けています」と、欠けの手前までで戻す選択を示す（Duplicati・Borg のスナップショットの連なりと同じ）|
|`keys/`|個人のルートの鍵と署名用の証明書の鍵（PKCS#8）。鍵保管から取り出して入れる|
|`data/`|2.1 の表で「控えに含む」のもの|

- 拡張子は `.nrsdbak`。
- 部品：age の Rust 版（age 0.12.1、MIT OR Apache-2.0）、zip（第11章 4.1「Rust の部品」）。

### 5.2 作り方

|順|処理|
|---|---|
|1|利用者が保存先と合言葉を選ぶ。よく使われる合言葉の一覧（10万件。同梱。出典は素材の目録（第11章 6）に記す）にあるもの、強さの推定（zxcvbn の方式。第11章 4.1）で弱いもの、15文字未満のもの（NIST SP 800-63B-4 の単一の要素の合言葉の下限。緊急キットの回復の鍵を印刷した利用者は多要素の下限の8文字以上）、のいずれかは受け付けない。記号・大文字の強制などの複合の規則は置かない（同。2026-10-01 NRSD の要求）。推定した解読の時間の目安を画面に示す（2026-09-30 NRSD の要求）|
|2|書き出し・登録の途中の処理がないことを確かめる（あれば終わるまで待つ）|
|3|鍵を鍵保管から読み、記録を読んで、ZIP にまとめながら age で暗号化し、一時の名前で書く（逐次に処理し、全体を記憶に載せない）|
|4|書き終えたら、ファイルを読み直して見出しを復号し、`manifest.json` の SHA-256 の一覧と照らして確かめる|
|5|正式の名前に変え、作った日時を設定に記録する（ホームの「最後のバックアップ」の表示。5.5）|

- 保存先の案内：同じ PC の中ではなく、外部の記憶媒体（USB の記憶媒体等）か、利用者の Cloud に置くことを勧める。暗号化されているため Cloud に置いてもよいが、合言葉が弱ければ読まれ得る旨を示す。
- 合言葉を忘れると戻せない旨を、作る時に示し、確かめの押し下げを求める。
- ［要実測］証拠を含む5GB の控えの作成の時間。判定：一般的な PC（第1章 14.1「規模と性能の目安」）で15分以内（初期値）。
- 脅威 T-5（情報の漏れ）：控えのファイルを盗んで読む。攻撃する者：ファイルを入手した者。狙う資産：署名鍵、記録。残る破れ：弱い合言葉
- 秘密：控えのファイルの合言葉。置き場：利用者の記憶（アプリは保存しない）。漏れた時：控えのファイルを持つ者に読まれ得る。新しい控えを作り、古い控えを消す

### 5.3 戻し方（取り込み）

|順|処理|
|---|---|
|1|利用者がファイルと合言葉を入れる|
|2|age の見出しを読み、scrypt の強さが 2^22 を超えるものは受け付けない（age の公式の Go の実装が受け入れる上限。解読に時間のかかる細工を防ぐ）|

|4|各ファイルの SHA-256 を一覧と照らす|
|5|個人のルートが今の端末と同じか、端末に記録がないかを確かめる（5.4）|

- 取り込む時の今の端末の扱い：

|今の端末|扱い|
|---|---|
|記録がない（新しい端末）|そのまま取り込む|
|同じ個人のルートの記録がある（2台で使っている）|統合する（下の規則）|
|違う個人のルートの記録がある|統合しない（DD-8-6「個人のルートが違う控えは統合しない」）。「今の記録を控えのファイルで置き換える（今の記録は先に控えを作る）」か「取りやめる」かを選ばせる|

- 記録ごとの揃え方は 5.4「端末どうしの同期」の箇条による。
- 自分より新しいアプリで作った控え（記録の形式の版が新しい）は、アプリの更新を促して取り込まない。
- 引き継ぎとして開く：緊急キットの回復の鍵で控えを戻した端末で、利用者が「引き継ぎとして開く」を選ぶと、署名鍵を使わない読み取り専用の状態（新しい C2PA署名・登録はしない）で開き、作品・事件・証拠の閲覧、証拠一式の書き出し、同封文書の再生成だけができる（第1章 13）（2026-09-30 NRSD の要求）。
- 脅威 T-11（改ざん）：取り込むテンプレート・控えのファイルの中身を細工する。攻撃する者：ファイルを渡す者。狙う資産：アプリの中心、記録。残る破れ：—

### 5.4 端末どうしの同期

- 端末どうしの手順：つないだ後、まず互いの署名用の証明書の連なりを見せ合い、相手の乱数への署名で同じ個人のルートであることを確かめる（相互の挑戦応答）。次に連鎖ごとの先端（stream と端末の番号ごとの `seq`）を交換し、足りない行を送る。証拠・素材のような大きなファイルは iroh-blobs（BLAKE3 のハッシュで指す内容指定の転送。途中から再開できる）で受ける。手順の名前は ALPN `c2pa4cosplayer/sync/1`、メッセージは CBOR。新しい端末のリンクでは、リンクの確かめ（QR か合い言葉）の後に、既存の端末が個人のルートと署名用の証明書の鍵を同じ直接の接続（端から端まで暗号化）で渡し、新しい端末は鍵保管に入れる（控えからの戻しと同じ結果。端末の鍵は端末ごとに作る）。
- 端末どうしの同期：同じ個人のルートを持つ端末は、Signal の「リンクされたデバイス」と同じ流れでつながる（新しい端末に QR（第1章 10.10「URL と QR の形」の `link`）が出る、既にリンクした端末のどれかで読む、以後は自動。「主の端末」は置かず、署名鍵を持つリンク済みの端末はどれでも新しい端末をリンクできる（Delta Chat の「2台目を追加」と同じ。Signal の「主端末だけがリンクできる」は採らない））。裏の仕組みは Syncthing・Delta Chat と同じ（端末の公開鍵で呼び出す QUIC の直接の接続。iroh。公開の中継が NAT の穴を開け、つながった後は端から端まで暗号化した直接の通信。直接つながれば中継を離れる。中継に見えるのは IP アドレスと乱数の端末の番号だけで、中身は読めない）。どこにいても（自宅と外出先、国をまたいでも）自動でつながり、揃える単位は連鎖の行（作品データ、事件記録、状況の追記、承認書）と、テンプレート・作業・端末に依らない設定（範囲は下の表）。記録は追記のみのため衝突しない。記録ごとの揃え方は下の箇条による。端末どうしは互いの控えの置き場にもなる（5.5）。つながらない間は、差分の控えが Cloud の同期フォルダーを通って遅れて追いつく。G-20「設定」の「端末」に一覧（名前、最後に同期した時刻、「この端末を外す」。上限5台）を持つ。中継を使わない設定（同じ網と Cloud の同期フォルダーだけ）も置く。NRSD はサーバーを持たない（D-6-2「本システムはWebサイトとしては構築しない」）。DD-1-4「記録はすべて利用者の端末に置く」 が退けた「自動の同期」は NRSD 側に置き場を要するものであり、端末どうしの直接の同期はこれに当たらない（2026-09-30 NRSD の要求）。
- 合い言葉からの接続（QR を見せ合えない時。第2章 5.5 の相手の追加と、端末のリンクに共通）：合い言葉は Magic Wormhole と同じ形（番号1つと PGP の語表の2語。1回限り、10分で消える）。合い言葉から Argon2id で Ed25519 の鍵対の種を導き、始めた側はその鍵で署名した記録（自分の端末の番号と期限10分）を pkarr（BEP 44 の DHT の署名つきの記録。iroh の `discovery-pkarr-dht` と同じ仕組みで BitTorrent の mainline DHT に載せる。NRSD のサーバーは要らない）に公開する。相手は同じ鍵で引いて端末の番号を得て直接つなぎ、合い言葉で SPAKE2（RFC 9382）の鍵の合意を行い、合い言葉を知る相手だけを通す（Magic Wormhole と同じ）。記録は1回使うか10分で消す（2026-10-01 NRSD の要求）。
- 端末のリンクの手段：QR のほか、上の合い言葉でも行える（QR は任意）。
- 取り下げた証拠：取り下げ（第6章 7）は追記の行として同期される。別の端末は行を受けたら証拠を OS のごみ箱へ移す。控えには残り、次のまとめ直し（月1。5.5）で除く。
- 記録ごとの揃え方：連鎖の行・証拠・素材・承認書は第1章 8.3「形式と版」、テンプレート・作業は第4章 8.2「版」、設定は第10章 10「設定」による。控えの取り込み（5.3）も同じ規則を使う。
- 脅威 T-24（なりすまし）：利用者の端末や確認済みの相手を装い、記録や書類を流し込む、または記録を読む。攻撃する者：端末の番号を知った者。狙う資産：端末の記録、書類。残る破れ：端末の鍵が奪われた場合（T-4「利用者の署名鍵を盗んで C2PA署名する」と同じ）
- 脅威 T-26（情報の漏れ）：直接の接続の中継に、利用者の IP アドレスと端末の番号が見える。攻撃する者：中継の運営者。狙う資産：利用者の所在。残る破れ：IP アドレスは中継に見える（TSA・GitHub への接続と同じ）

### 5.5 控えの置き場と自動の控え

- 初回の入力の直後（G-05「控えを作る」）に、届く置き場（外部の記憶媒体、利用者の Cloud の同期フォルダー、同じ人の別の端末（5.4））を検出して提案し、1つ以上を決める。以後、1時間ごと（初期値。Time Machine と Windows のファイル履歴の既定と同じ）と閉じる時に、記録が変わっていればアプリが控えを自動で作る。画面の言葉は「バックアップ」とし、ホームに「最後のバックアップ：〇分前」を示す。原本そのもの（RAW・現像前）を控えに含めるかを初回に示し、既定は含める（第2章 4.2）。利用者は何もしない。置き場が届かない時は次の機会に作る（2026-09-30 NRSD の要求）。
- 原本の控え：原本は差分（新しい原本だけ）で控える。Cloud の同期フォルダーには原本を含めず、外部の記憶媒体と別の端末にだけ含める。初回に見積もり（枚数と GB）を示す。
- 初回に検出するのは外部の記憶媒体と Cloud の同期フォルダーだけ。別の端末は G-20 でリンクした時に置き場に加える。
- 置き場の検出：外部の記憶媒体は OS の取り外せる媒体（Windows `GetDriveType` の `DRIVE_REMOVABLE`、macOS は DiskArbitration の `Removable`・`Ejectable`、Linux は UDisks2 の `Removable`）。Cloud の同期フォルダーは各社の既定の場所（Dropbox は `~/.dropbox/info.json` の `path`、OneDrive は環境変数 `OneDrive`、Google Drive はドライブの名前 `Google Drive`／`My Drive`、iCloud は `~/Library/Mobile Documents/com~apple~CloudDocs`）。見つからなければ利用者が選ぶ。
- 控えは差分（前回からの新しい行と新しい証拠のファイル）を重ね、月に1度（初期値）まとめ直す。取り込みは全体と差分を順に当てる。
- 置き場ごとに、控えの一覧と最後に検証が通った日時をホーム（G-07「ホーム」）に示す。月1の戻しの確かめは、一時の場所に控えの大きさの2倍の空きがある時だけ行い、無ければ知らせる。作った直後の読み直し（5.2）に加え、月に1度、置き場の控えから一時の場所へ実際に戻して全記録の電子署名が通ることを確かめる（戻せる控えであることを失う前に確かめる）。
- 置き場が1つも届かない状態が7日（初期値）続いた時だけ、ホームに知らせる。手で控えを作る操作（5.2）も残す。

### 5.6 控えの置き方の案内

- 控えを作る画面（G-05「控えを作る」）と README で、一般に勧められる「3-2-1」の原則（大事なファイルの写しを3つ持ち、2種類の媒体に置き、1つを離れた場所に置く。米国 CISA「Data Backup Options」）に沿って、次を示す。

|写し|置き場の例|
|---|---|
|1つ目|この PC のアプリの記録（元）|
|2つ目|外部の記憶媒体（USB の記憶媒体、外付けのディスク）の控えのファイル|
|3つ目|離れた場所：利用者の Cloud（控えは暗号化されている）、または別の場所に置いた記憶媒体|

- 控えのファイルは作るたびに新しい名前（`backup-<YYYYMMDD-HHMMSS>-<seq>.nrsdbak`）で作り、古い控えを上書きしない。月1のまとめ直し（5.5）でアプリが自分で作った差分の控えを新しい全体の控えに畳み、畳んだ差分は消す（Time Machine が古いスナップショットを間引くのと同じ。利用者が自分で写した控えのファイルには触れない）。全体の控えを消すかは利用者が決め、置き場に同じ個人のルートの全体の控えが3つ以上あれば、最も古いものを消してよい旨を示すだけとする。

## 6. 容量

### 6.1 端末の容量の目安

|データ|見積もり（初期値からの見積もり）|
|---|---|
|作品データ|1作品50KB（マニフェストの写しと縮小画像を含む）×年5,000作品＝250MB/年|
|証拠|1件20MB（典型）×年200件＝4GB/年。1件の上限は第6章 2.4（1GB）による|
|作業|1作業数 MB（写真の場所と手直しのみ）|
|テンプレート・素材|数十MB|
|縮小の画像（キャッシュ）|1枚約50KB×500枚＝25MB/作業（消しても作り直せる）|

- 空きが1GB（初期値）を下回ったら知らせ、古い事件の証拠を控えのファイルにしてから消すことを案内する。消す前に請求の期間を示す（第1章 8.4「保持と削除」）。
- キャッシュが1GB（初期値）を超えたら、古い作業の縮小の画像から消す。

### 6.2 中国本土

- 取得（更新、参照情報）：GitHub から取得し、失敗したら香港のミラー（DD-8-5「中国本土向けに香港のミラーを置く」）から取得する。配布物と参照情報の包みは電子署名で検証するため、ミラーでの差し替えは検出できる。更新の案内（JSON）には電子署名がないため、案内の書き換えによる古い版の押し付けは、案内の版と更新の電子署名の版の照合（第9章 DD-9-2「更新は Tauri の仕組みで取得し、案内と電子署名の版を照らす」）で防ぐ。
- 初回の入手：README の中国語の節に、ミラーの最新版の配布物への直接のリンクと SHA-256 を載せる（3.6、第9章 5「入手経路」）。README そのものに届かない場合は入手できない（第13章 H-17「中国本土では README に届かないことがある」）。
- 記録の書き込みは端末の中で完結するため、GitHub への接続は要らない。
- 参照情報は、自分の別の端末や確認済みの相手、Cloud の同期フォルダー、ファイルからも届く（3.4、第1章 7.5）。「持ち出しキット」（アプリの配布物と参照情報の包み）を G-20「設定」 から USB に書き出せる（第9章 5）。会場で1人が最新版を持てば周りに届く（2026-09-30 NRSD の要求）。
- ミラーの候補：阿里云の OSS の香港の地域（静的な配信）。香港の地域は ICP 備案が要らない（阿里云の案内）。中国本土からの遅延は30〜50ms とする案内がある（同）。
- 費用：保管と外への転送の量で決まる。［要見積］配布物の大きさ（第11章 4.3「素材」）×取得の回数。
- ［要実測］中国本土からミラーへの到達と速さ。判定：ミラーから更新と参照情報を取得できること。満たさない場合は破れとして宣言する（第13章）。
- 危険：中国本土から届かない。影響：中国の利用者が入手・更新できない。備え：香港のミラー（README の中国語の節からの直接の入手と、更新・参照情報の取得。第8章 3.6「香港のミラーの運用」、第9章 5「入手経路」）

### 6.3 ミラーの費用の見積もり

- 費用は、保管の量と外への転送の量で決まる。香港の地域の外への転送は月5GB まで無料（阿里云の OSS の案内）。単価の表は阿里云の価格のページにあり、本書の調べ（2026-09-29）では画面の取得ができなかった。［要見積］NRSD が契約の前に価格のページで単価を確かめる。
- 見積もりの式：月の外への転送量 ＝ 配布物の大きさ（第9章 2.1「OS ごとの配布物」 の見込み。各 OS 200MB 前後、Linux は同梱の部品の分だけ大きい。設計の目標は300MB 以下）×月にミラーから更新・新規の導入をする利用者の数 ＋ 参照情報（1MB 以下）×取得の回数。保管の量 ＝ 1つの版の配布物（Windows のインストーラ、macOS の DMG と更新用の `.app.tar.gz`、Linux の AppImage の4つ。各約200MB）×2つの版（約1.6〜2GB）＋ Linux の AppImage に同梱した LGPL の部品のソースの包み（2つの版の分。［要見積］大きさ）＋参照情報。
- 例：ミラーの利用者が月に200人更新する場合、約50GB/月の転送になる。

## 7. GitHub への依存

|事象|備え|
|---|---|
|GitHub の障害|更新と参照情報はミラーから取得。記録は端末にあるため作業は止まらない|
|アカウント・リポジトリの停止|ミラーと別の git のホスティングへ公開リポジトリを移す。公開ページは独自のドメイン（`c2pa4cosplayer.nrsd.jp`。3.1）の CNAME を別の静的な置き場に向け直せば、アプリの取得先の URL は変わらない。アプリの更新の取得先を複数持つ（第9章 DD-9-2「更新は Tauri の仕組みで取得し、案内と電子署名の版を照らす」）|
|規約|公開リポジトリには個人情報・転載の情報を置かない（法務調査 L-18「GitHub の規約」）|
|リリースの容量|リリースの1つのファイルは2GiB 未満、1つのリリースのファイルは1,000まで。リリースの合計の大きさと転送量に上限はない（GitHub の案内「About releases」）。配布物の大きさの設計の目標は300MB 以下（第9章 2.1「OS ごとの配布物」）。第1章 4.2「外部とのやり取り」 の500MB は取得の上限であり、これを超える配布物は取得しない|
|アカウントの乗っ取り|3.5 の守り。乗っ取られても、更新と参照情報は NRSD のオフラインの鍵で署名した TUF のメタデータと更新の電子署名がなければ適用されない（3.2、第9章 4.3）|

- 危険：GitHub のアカウントの停止。影響：配布が止まる。備え：ミラーと別のホスティング（第8章 7「GitHub への依存」）
