## 2. 目的と品質の目標

### 2.1 目的

- 本システムは、コスプレ写真の権利者が、写真に権利を表示し（C2PA署名、可視署名、同封文書）、許可範囲を定め、転載を登録して証拠を残し、しかるべき時に対処できる状態を整える（設計計画書 第2章「目的および範囲」）。

### 2.2 利害関係者

|者|本システムとの関係|関心|
|---|---|---|
|コスプレイヤー（利用者）|写真に C2PA署名し、販売・投稿し、転載に対処する|手間が少ない、見た目が良い、写真を壊さない|
|撮影者（利用者）|同上。コスプレイヤーと共同の権利を持つことがある|クレジットが正しく載る|
|承認を受けた者（利用者）|権利者の承認で C2PA署名・投稿する|承認の範囲が分かる|
|購入者（外）|受け渡し用画像と同封文書を受け取る|何をしてよいかが分かる|
|閲覧者（外）|投稿を見て、正規の写真かを見分ける|確かめ方が分かる|
|転載者（相手）|無断で転載する|—（抑止の対象）|
|権利者を装う者（相手）|他人の写真に先に C2PA署名する等|—（照合の手がかりで対処。第2章）|
|NRSD（運営）|アプリを作り配る。参照情報を保守する|鍵を守る、費用を抑える、責任の範囲|
|法の専門家（外）|証拠一式を受け取る。文言を確かめる|証拠の検証の手順|
|投稿先・Cloud・申立ての窓口・配布と拡張の店（Flathub、Chrome と Firefox の拡張の店）・直接の接続の中継と公開の DHT（外の組織・基盤）|画像の置き場、申立ての受け手、配布の場、NAT の穴あけと中継、合い言葉からの接続の相手の照会|—|

### 2.3 品質の目標（優先の順）

|順|目標|ISO/IEC 25010:2023 の特性|理由|
|---|---|---|---|
|1|原本と記録を失わず、壊さない|信頼性、安全性|写真は利用者の収入源であり、証拠は後の請求に要る。失えば取り返せない|
|2|非技術者が迷わず使える|使い勝手|使われなければ抑止が働かない（設計計画書 8.1「見た目」）|
|3|利用者の情報を集めず、漏らさない|セキュリティ|設計計画書 D-5-1「本システムは利用者を確かめず、利用者の情報を集めない。本システムを使うために登録を求めない」 が本システムの前提|
|4|出力が第三者の検証で通り、改ざんが分かる|機能の適合性|C2PA署名の意味がなくなる|
|5|3つの OS で同じ結果になる|互換性、柔軟性|利用者が端末を替えても、出力が変わらない|

- 性能は、上の5つを損なわない範囲で満たす（14.1）。
- 目標がぶつかる時は、順の上のものを採る。例：自動の保存（目標1）のために書き込みが増えても、速さより優先する。

- 転載ページの取得では、相手のサイトに利用者の IP アドレスが見える。取得の前に一度その旨を示す（11.2 の脅威）。
- 共通の扱い：OS の代理サーバーの設定（Windows の WinHTTP、macOS のシステム設定、Linux の環境変数）に従う（利用者が VPN・代理を使う前提。第6章 2.2）。TLS の信頼の起点は OS の検証器（rustls-platform-verifier）。参照情報・更新の取得の失敗は 1秒・4秒・16秒（揺らぎつき）で3回まで再び試し（AWS の exponential backoff）、その後は回線の復帰（OS の網の状態の変化：macOS `NWPathMonitor`、Windows `INetworkListManager` の事象、Linux NetworkManager の D-Bus の `StateChanged`）と1時間ごとの再試行で続ける。保留の処理（時刻証明の後付け、参照情報と更新の取得、端末どうしの揃え、控え）はすべてこの1本の待ち行列で再開する（「接続のたび」はこの回線の復帰の事象をいう）。時刻証明は再び試さず次の TSA へ、転載ページの取得は1回だけ再び試す。転送は同じ元の中で5回まで、TSA の POST は転送に従わない。応答は流しながら書き、上限を超えた時点で切る（全体を記憶に載せない）。従量制・省データの回線の判定は OS の API（Windows `GetConnectionCost`、macOS `NWPath.isExpensive`・`isConstrained`、Linux NetworkManager の `connection.metered`。Windows Update・Chrome と同じ）で行う。
- 取得先の並び（参照情報と更新の案内に共通）：公開ページ、次に香港のミラー。取得に失敗した、または取得した中身が検証に通らなかった取得先は後ろに回し、次の確かめはその並びで行う（失敗の回数を数える）。
- 脅威 T-16（使えなくする）：転載ページの巨大な応答、転送の繰り返し、応答の遅延。攻撃する者：悪性のサイト。狙う資産：アプリの中心。残る破れ：—

### 6.2 画面と中心の間

- 画面は、許可した命令だけを呼べる（Tauri の capabilities と permissions で窓ごとに許す）。ファイルの読み書きの範囲は、アプリのデータの場所と、利用者がその都度選んだファイル・フォルダーに限る（Tauri の scopes）。
- 画面は外部の読み込みを禁じる（CSP で、アプリの内の資源以外を読み込まない）。外部の URL は、利用者が押した時に OS の既定のブラウザで開く。
- 外部から来た文字（転載ページの題、ファイル名、テンプレートの名前、参照情報の文）は、文字としてのみ表示し、HTML として解釈しない。
- 長い処理（書き出し、登録、自動配置、控え）は中心の裏の処理で行い、進みの知らせ（何枚目か、残りの見込み）を画面に送る。画面からの取り消しを受け付ける。
- 起動の時に画面から中心へ渡す値は、WebView の User-Agent、Accept-Language、画面の言語の3つだけ。中心から画面へは、命令の返り値のほかに知らせ（進み、お知らせ、保存の状態、更新の準備、起動時の確かめ、落とされたファイル、相手の端末の出来事）を送る。
- 画面から呼べる命令と、使う Tauri のプラグイン（ファイルの選択、既定のブラウザ・mailto・記録の場所を開く、OS の通知。第11章 4.1）の許可は、画面ごと・命令ごとに最小とし、その一覧を開発側の文書に置いて CI で設定との一致を確かめる（第11章 8.1）。全ブロックの境界（命令名、引き渡す型、返す型、起こり得る正常系の事象）は、実装の前に「境界の一覧」として1つの文書に定義し、画面と中心の型をそこから生成する。境界の変更はこの文書の改訂を経る（2026-09-30 NRSD の要求）。
- 脅威 T-17（権限の昇格）：画面に表示した外部の文字で画面の命令が動く。攻撃する者：外部の文字を仕込む者。狙う資産：画面、中心。残る破れ：—
- 脅威 T-18（権限の昇格）：画面から任意のファイルを読み書きする命令を呼ぶ。攻撃する者：画面を乗っ取った者。狙う資産：端末のファイル。残る破れ：—

### 8.2 識別子の体系

|識別子|書式|発行|一意性|
|---|---|---|---|
|識別番号|61ビットの乱数。不可視透かし（TrustMark BCH_5 のデータ部）にそのまま入れる。表示は、61ビットの値を上位に、その値の検査の4ビット（生成多項式 x^4＋x＋1 の CRC-4。CRC-4/G-704：初期値0、入出力の反転なし、上位のビットから）を下位に置いた65ビットを、上位から5ビットずつ Crockford Base32 の13文字にし、5・5・3文字に区切る（例：値 0x1604F408204C92C5、検査 4 は `P0KT0-G82CJ-B2M`）。1つの値の表記は1つに決まり、検査の4ビットが合わない表記は無効として「識別番号の打ち間違いの可能性があります」と示す|アプリ（書き出しの時）|下の注記|
|告知コード|第2章 2.4「告知コードの作り方」による（`NRSD-` と Crockford の Base32 の20文字。28文字）|アプリ（初回の入力の時）|100ビットで偶然の一致を無視できる|
|事件の番号|`C` に続けて UUID v7|アプリ|衝突を無視できる|
|作業・テンプレート・一括処理の番号|UUID v7|アプリ|衝突を無視できる|
|エラーの番号|分類（英字3文字）と連番3桁（例：`SIG-012`）|設計（10.3）|—|
|端末の番号|直接の接続の端末の公開鍵（Ed25519）の SHA-256 の先頭40ビットを Crockford の Base32 で8文字にしたもの。記録の行の `device`、端末ごとの連鎖のファイル名、端末の一覧の表示に使う|アプリ（初回の起動。第2章 7.1「生成と保管」）|40ビット。同じ人の端末（上限5台）の間で重ならない|

- 識別番号は、作品（書き出した1つのファイル）ごとに1つ発行する。同じ写真を X 用・Instagram 用・受け渡し用に書き出せば、それぞれ別の識別番号になり、同じ写真であることは作品データの原本の SHA-256 で分かる。識別番号は同じ値を不可視透かし、C2PA署名のマニフェスト、ファイル名（利用者が付けることを選んだ場合）、可視署名（差し込みを使った場合）、作品データ、事件記録に記録する。設計計画書 1.5「用語の定義」の「識別番号」であり、企画草案の「照合番号」（投稿に付して閲覧者が無断転載を判別する番号。第2節・第3節）および「作品番号」（報告された転載を作品と対応付ける番号。第6節）も同じ値とする。
- 一意性：61ビットの乱数どうしが重なる確率は、作品が1千万件でも約5万分の1（n²/2⁶²。10¹⁴÷4.6×10¹⁸）である。発行の時に手元の作品データと重ならないことを確かめる。他の利用者との重なりは、中央の台帳を持たないため確かめない。照合では識別番号と署名者の組で作品を区別する。
- 表示を上位の一部のビットに縮めると一意でなくなる（40ビットでは作品50万件で約1割の確率で重なる）。照合番号として閲覧者が使う番号であるため、縮めない。
- 作品登録番号（公的な登記の番号）は本システムが発行する番号ではなく、利用者が告知・可視署名に書く文字列として扱う。

### 8.3 形式と版

- 記録は JSON（RFC 8259。UTF-8、キーは英字）。各記録に `schema`（例：作品データは `nrsd.work/1`、作業は `nrsd.session/1`）を持たせる。形の定義は JSON Schema の 2020-12 の版で書く。番号の UUID v7 は RFC 9562（2024年5月）による（2026-10-01 NRSD の要求）。
- 版を上げる時は、古い版を読む処理をアプリに持たせ、アプリの更新の後の初回の起動で新しい版に移す。移す前の記録の写しは第9章 4.4「記録の形式の移行」の手順で残す。
- アプリは自分より新しい版の記録を読んだら、書き換えずに読むだけにし、更新を促す。
- 記録の電子署名は、JSON を正規化（RFC 8785 JCS）したうえで、署名用の証明書の鍵の ECDSA P-256 で行い、連鎖の各行の `sig` に置く（`x5c` に署名用の証明書と個人のルートの証明書を添える。第2章 DD-2-10「記録の電子署名は署名用の証明書の鍵で付け、証明書の連なりを添える」）。連鎖のファイルと並ぶ `.sig` は先端の記録（最後の行の `seq`、その行の保存したバイト列の SHA-256、それらへの同じ形の署名）であり、末尾の行の切り落としを検出する（git の参照が先端を指すのと同じ）。行を足すたびに `.sig` を書き直す（10.2 の手順）。ただし承認書・取り消し書・共同の権利の書面は、1つのファイルで受け渡すため、署名を JSON の中の `signatures` に置く（第2章 5.3「書類の形式」）。
- 全記録（作品データ、事件記録、状況の追記、作業、テンプレート、承認書、控えの目録、参照情報の各ファイル、設定、変更の履歴、過去の個人のルート、更新の案内、同封文書の JSON）の形は JSON Schema で実装の前に定義し、読み書きのたびに検証する。形の版ごとに検証器と移行を持つ。Schema と試験ベクトルは公開ページに載せ、第三者（専門家）が証拠一式を本システムなしで検証できるようにする（2026-09-30 NRSD の要求）。JCS の正規化は、部品（第11章 4.1）と自前の最小の実装の二重化とし、両者の出力の一致と RFC 8785 の試験ベクトル全件を CI で確かめる（第11章 8.1）。
- 記録の形式の一覧（`schema` の名前。JSON Schema は `dev/schemas/<名前>.<版>.json` に1記録1ファイル、`$id` は `https://c2pa4cosplayer.nrsd.jp/schema/<名前>/<版>`）：`nrsd.work/1`（作品データ）、`nrsd.session/1`（作業）、`nrsd.template/2`、`nrsd.case/1`（事件記録）、`nrsd.status/1`（状況の追記）、`nrsd.grant/1`（承認書・取り消し書・共同の権利の書面）、`nrsd.backup/1`（控えの目録）、`nrsd.reference/1`（参照情報の包みの目録）、`nrsd.settings/1`、`nrsd.history/1`（`identity/history/<端末の番号>.jsonl`）、`nrsd.past_root/1`、`nrsd.consent/1`、`nrsd.peers/1`、`nrsd.identity_draft/1`、`nrsd.epoch/1`、`nrsd.chain_heads/1`、`nrsd.export_queue/1`、`nrsd.ers/1`（`state/ers.json`）、`nrsd.fetch_state/1`、`nrsd.clock/1`（`state/clock.json`）、`nrsd.work_index/1`（`works/index.json`）、`nrsd.session_photo/1`（`sessions/*/photos/<番号>.json`）、`nrsd.session_snapshot/1`、`nrsd.template_local/1`（`templates/*/local.json`）、`nrsd.update_manifest/1`、参照情報の各ファイル（`nrsd.ref.<ファイル名>/1`：`platforms`・`notices`・`terms`・`tsa`・`relays`・`deadlines`・`holidays`・`laws`・`minimum_version`・`vex`・`clearurls`）。`history.log`（第4章 11.3）は1行1段の JSON Patch で `nrsd.session/1` の `history` の要素の形。期限（VTODO）は `.ics` で JSON ではない。一覧は core-store（第11章 7.1）が持ち、読み書きのたびに検証する。
- 記録の電子署名は1行（1作品、1つの状況の追記、1つの承認書）ごとに持ち、各行に前の行のハッシュを含めて連鎖にする（順序と抜けの証明）。連鎖は書き手の端末ごとに1本とし（1本に書くのは常に1つの端末。Kafka のパーティション、Syncthing の端末ごとの索引と同じ）、別の端末の行は同期で写しを受け、時計と単調な番号で並べて示す。行の形は `prev`（前の行の保存したバイト列の SHA-256。最初の行は64個の `0`）、`seq`、`device`（端末の番号。8.2）、`clock`、本文、`sig`。壊れた行は `<stream>/quarantine/` に移し、以後の行は「連鎖が切れた」印を付けたまま読める（git fsck が壊れた対象を報告して残りを読めるのと同じ）。破損した行だけを隔離し、他は使い、控えからその行だけを戻す。全記録の連鎖の先端を1日1回と接続のたびに時刻証明する（第3章 4）。起動の時の検証は連鎖の先端から行う（第8章 4）。各記録は、端末の時計の値・その時点の時計のずれ・単調な番号（端末ごとの連番）・時刻証明（あれば）を別々に持つ（10.7）（2026-09-30 NRSD の要求）。
- 別の端末・控えから来た行の揃え（第8章 5.3・5.4 から呼ばれる）：同じ stream で `device`・`seq` が同じ行は1つ（中身が違えば両方を残して違いを示す。通常は起きない）。事件の状況の追記は事件ごとに、変更の履歴は端末をまたいで、時刻の順に並べる。証拠・素材のファイルは SHA-256 の名前で合わせる（同じものは1つ）。承認書等の書類は番号で合わせる。
- 記録の電子署名の形は JWS（RFC 7515）の detached とする：本文は JCS で正規化した JSON、保護された見出しに `alg: ES256`、`x5c`（署名用の証明書と個人のルートの証明書）、JAdES（ETSI TS 119 182-1）の `sigT`（署名の時刻）を持つ。連鎖の行、承認書の `signatures`、WACZ の署名を同じ形に揃える（参照情報の包みは NRSD の TUF のメタデータで署名し、JWS は使わない。第8章 3.4）。専門家は一般の JWS の道具で検証できる。長期の有効性は ERS（第3章 4）が担う（2026-10-01 NRSD の要求）。

### 8.4 保持と削除

- すべての記録は利用者の端末にあり、利用者が削除しない限り保持する。アプリが自動で削除するのは次のものに限る：操作の記録（90日。初期値）、落ちた時の報告（送った・送らないを選んだ時に消す。未選択は10件・30日まで。Mozilla の Crash Reporter と同じ）、使われなくなった持ち込みの素材（`assets/`。どのテンプレート・作業からも参照されないものを、控えのまとめ直しの時に消す）、縮小の画像（作業を消した時と、キャッシュが1GB を超えた時の古いもの。第8章 6.1「端末の容量の目安」）、作業の版の控えのうち5つを超えた古いもの（第4章 11.4「版の控え」）、異常終了の後に残った一時のファイル（7.8）、記録の形式の移行の写し（30日。第9章 4.4「記録の形式の移行」）。利用者の記録（作品データ、事件記録、証拠、テンプレート、承認書）は自動で削除しない。
- 事件記録・証拠の削除の前に、損害賠償の請求の期間（日本・中国とも知った時から3年・行為の時から20年、米国は請求の発生から3年。法務調査 L-20「損害賠償の請求の期間（日・中・米）」）を示し、書き出しを勧める。
- NRSD は利用者のデータを持たないため、NRSD の側の保持・削除の方針は生じない。

### 8.5 秘密情報の一覧

- 秘密ごとの置き場と漏れた時の扱いは、その秘密を持つ節に「秘密：」の箇条として書く（本節には写さない。R-1-2-3 の一覧は grep で集める）：利用者の署名鍵（第2章 7.2）、控えの合言葉（第8章 5.2）、端末の鍵（第2章 7.2）、有料の TSA のアカウント（第6章 3.2）、参照情報の電子署名の鍵（第8章 3.4）、更新の電子署名の鍵（第9章 3.2）、コード署名と公証の資格（第11章 8.3）、ミラーの鍵（第8章 3.6）、GitHub と各事業者のアカウント（第8章 3.5）、TUF の鍵（第9章 4.3）。

### 8.6 多言語のファイル名と文字

- ファイル名は UTF-8（NFC に正規化）で扱う。OS で使えない文字（Windows の `\ / : * ? " < > |` 等）は `_` に置き換える。
- アプリのデータの場所の中で本アプリが作るファイルとフォルダーの名前は英数字（番号）とし、利用者の入力した名前は JSON の中に置く。書き出しの出力の名前（撮影の名前、元のファイル名を使う）は第3章 10.1「名前と構成」 による。
- 出力の名前は第3章 10.1 による（受け渡し用は ASCII の可搬の名前、SNS 用は書き出しの前の机上の検査で自動に直す）（2026-09-30 NRSD の要求）。

## 10. 横断の考え方

### 10.1 データのモデル

- データのもの・持つもの・他との関係は、第8章 2.1「配置」の表と各章の記録の項目（第3章 7.2、第6章 2.4、第4章 15、第2章 5.3）による（本章には写さない）。

### 10.2 保存

- すべての記録と出力のファイルは DD-1-9「記録は一時のファイルに書き切ってから置き換える」の手順で書く（書きかけで壊れたファイルを残さない）：

  1. 置く先と同じフォルダーに、一時の名前で書く。一時の名前は `~$<最終の名前>.tmp`（`~$` で始まるファイルは Dropbox・OneDrive が同期せず、`.tmp` は OneDrive が同期しない。各社の「同期しないファイル」の案内、2026-10-01。Google Drive は明文が無いため、同期フォルダーへの書き出しでは「完了するまで同期ソフトが途中のファイルを拾うことがある」と G-08 に1行示す。読み戻しの検証（第3章 8.1 段13）を通った後に名前を確定するため、拾われても壊れたファイルは正式の名前にならない）。

  2. 一時のファイルを記憶媒体に書き切る（Rust の `File::sync_all`）。

  3. 名前を置き換える。Windows は `MoveFileExW` に既存の置き換えと書き切りの指定（`MOVEFILE_REPLACE_EXISTING`、`MOVEFILE_WRITE_THROUGH`）を付けて行う。macOS・Linux は `rename` で行う。

  4. macOS・Linux では、フォルダーも記憶媒体に書き切る（`fsync`）。

- 出典：Rust の `std::fs::rename` の説明（Windows では `MoveFileExW` を用いる）、Microsoft の `MoveFileExW` の説明、tempfile の `persist` の説明（中身とフォルダーの同期をしない旨）、atomicwrites の実装（`sync_all` の後に置き換える）。`ReplaceFileW` は採らない。Microsoft の説明に、部分的な失敗（エラー1176）で置き換える先のファイルが無くなる場合があるとあるため。
- 連鎖に持つ記録（作品データ、事件記録と状況の追記、承認書等の書類、変更の履歴。8.3）には記録の電子署名を付ける（DD-1-5「端末の記録に記録の電子署名を付けて検証する」）。読む時に検証し、合わなければ使わずに知らせる。
- 同じ記録を2つの処理が同時に書かない。記録ごとに書き手の処理を1つに決め、他の処理は書き手に頼む。
- フォルダーの使用中の印（作業のフォルダー等）は、その中の `lock` を OS のファイルの鍵（Windows `LockFileEx`、macOS・Linux `flock`。fd-lock の crate）で開いたまま持つことで表す。プロセスが終われば OS が解く（PID の記録より確実）。鍵が取れなければ読むだけで開く。
- ZIP の読み書き（テンプレートの受け渡し、控え、証拠一式）に共通の確かめ：中のパスに `..`・絶対のパス・記号のリンクがあれば中止する。項目の数と展開の合計の上限は呼ぶ側が渡し、超えれば中止する。展開の合計が中の見出し（局所のヘッダ）の申告と一致しなければ中止する（解凍爆弾。10.6）。個々の上限は受ける節が持つ（第4章 8.3、第8章 5.3）。

### 10.3 エラー

- エラーは、分類と番号（8.2）、利用者への文、記録（ログ）への文を持つ。利用者への文は文言ファイルの鍵 `err.<番号>.what`・`.safe`・`.next`（第10章 DD-10-8 の3つの欄）で持ち、番号は台帳 `dev/errors.yaml` の1本で振る（欄：番号、正常系か異常検出か、分類、起きる条件、検出の方法、扱い、原本と記録への影響、文言の鍵、失敗するテストの名前）。分類ごとに連番とし、退役した番号は消さず `retired` の印で残して再利用しない（rustc の error codes の登録と tidy の検査と同じ）。Rust の型（分類と番号）は台帳からビルドの時に生成し、CI で型の変種と台帳、台帳と3言語の文言、台帳とテストの存在の一致を確かめる（第11章 8.1）。

|分類|中身|
|---|---|
|`IMG`|画像の読み書き|
|`SIG`|C2PA署名、証明書、鍵|
|`TSA`|時刻証明|
|`NET`|通信|
|`STO`|保存、容量|
|`REF`|参照情報|
|`UPD`|更新|
|`CAS`|登録、証拠|
|`BAK`|控えのファイル|
|`INP`|入力の確かめ|
|`SYN`|端末どうし・確認済みの相手との直接の接続と揃え|
|`AUT`|OS の本人の確かめ|

- 利用者への表示は第10章 DD-10-8「エラーの表示の型をそろえる」の型（何が起きたか、原本と記録は無事か、次にすること、番号）に従う。
- 事象は「正常系」と「異常検出」の2つに分ける（2026-09-30 NRSD の要求：あらゆるエラーを検出した上で、エラーを出さない設計とする）。
  - 正常系：起き得ることが分かっている事象（回線の不通、空きの不足、壊れた画像、鍵保管の拒否、時刻証明の保留、対応しない形式、利用者の入力の誤り等）。すべてを一覧に載せ、それぞれに定めた扱い（止める、飛ばす、保留する、再び試す、代わりの道を示す）を持ち、利用者にはエラーでなく状態として示す（第10章 DD-10-8「エラーの表示の型をそろえる」の型は正常系の知らせにも使う）。
  - 異常検出：起きるはずのないことが起きたと検出したもの（不変条件の破れ、想定に無い戻り値、記録の食い違い）。アプリの誤りであり、ゼロを目標とする。検出したら原本と記録を守る側に倒し（処理を止め、書きかけを残さない）、番号を付けて記録に残す。一覧に無い事象が起きたら異常検出として扱い、一覧に加える。一覧に加えるまでの間は、分類ごとの予約の番号 `<分類>-000`（未登録の異常検出）を付けて記録し、落ちた時の報告の `error_number` にもこの番号と検出した場所（ソースのファイルと行）を書く。
- 番号の一覧（番号、正常系か異常検出か、分類、起きる条件、検出の方法、利用者への文、アプリの扱い、原本と記録への影響、失敗するテスト）は実装の前に作り、画面の文言ファイル（第11章 DD-11-8「国際化は文言ファイルで行う」）と同じ3言語で持つ。一覧の各事象は、実際に起こして定めた扱いに落ちることを、失敗するテストで確かめる（第13章 5「実測と確認の一覧」）。
- 落ちた時の報告：異常検出と、アプリが落ちた時（OS の例外）は、Breakpad（Mozilla の Crash Reporter）と同じ形の報告（minidump と付随の情報：アプリの版、OS、エラーの番号、直前の操作の種類）を `crashes/`（第8章 2.1「配置」）に書く。minidump は minidumper（中で rust-minidump の minidump-writer を使う。第11章 4.1）で作る。写真・記録・個人の情報を含めない。報告は利用者が「送る」「送らない」を選ぶまで残し、選んだ後に消す。minidump を書くのは別のプロセス（落ちたプロセス自身は書けない）のため、アプリは起動の時に自分自身を `--crash-handler` の引数で子プロセスとして起動し、そのプロセスが書く（Firefox・Chromium の crashreporter と同じ）。異常検出（落ちていない）の時は同じ子プロセスに要求して書かせる。尋ね方と送り方は第10章 9「指摘の受け口」（2026-10-01 NRSD の要求）。

### 10.4 操作の記録（ログ）

- 目的：利用者の指摘（第10章 9「指摘の受け口」）の時に、利用者が自分で添えられる原因の手がかり。アプリは自動では送らない。
- 書くこと：時刻（UTC）、アプリの版、処理の種類、エラーの番号、件数と所要時間。形は JSON Lines（1事象1行。tracing の JSON の出力）。文は英語に固定する。既定の水準は info。詳細（debug）は指摘の時に環境変数 `NRSD_LOG=debug` で切り替える（Rust の env_logger の慣行）。
- 書かないこと：署名鍵、合言葉、証拠の中身、転載ページの中身、写真の場所の全体（ファイル名のみ）、権利者情報、URL の問い合わせの部分。
- 大きさ：1ファイル10MB で切り替え、合計50MB まで（初期値）。保持は90日（初期値）。
- 利用者は、設定から記録の場所を開ける（指摘に添えるため）。指摘の文面に添える「直近のエラーの番号」は、記録の新しい方から10件（初期値。第10章 9「指摘の受け口」）。
- 脅威 T-14（情報の漏れ）：操作の記録（ログ）に鍵・証拠・個人の情報が出る。攻撃する者：記録を見た者。狙う資産：秘密、個人の情報。残る破れ：—

### 10.5 並行処理

- 長い処理（書き出し、自動配置、登録、控え）は中心の裏の処理で行い、画面を止めない。進みを知らせ、取り消せる。
- 1度に動かす長い処理は、種類ごとに1つ（書き出しを2つ同時にしない）。利用者が始めた別の種類は並べて動かせる（書き出しの間に登録できる）。裏の自動の処理（保留の時刻証明、参照情報と更新の取得、端末どうしの揃え、控え。4.2 の待ち行列）は1本で順に動き、利用者が始めた処理の邪魔をしない（7）。
- 画像の処理の並行の数は第4章 14.4「大きな画像と並行の処理」の式による。
- 進みと取り消しの型は全ブロックで共通とする。進み：何件目か、全体の数、残りの見込み（秒）。取り消し：協調的（長い処理は区切り（1枚、1件）ごとに取り消しを確かめ、書きかけを残さずに止める。処理の途中の1件は完了させるか捨てるかを処理ごとに定め、半端な出力を残さない）。

### 10.6 外から入るものの確かめ

- 端末の外から入るもの（写真、画像の層、フォント、テンプレートのファイル、控え、参照情報、更新、転載ページ、TSA と RDAP の応答、拡張の `.wacz`、手で適用する更新の配布物、QR の画像、別の端末・相手からの記録と書類）は、それぞれを受ける節が上限と確かめを持つ（第3章 2、第4章 5・6.4・8.3、第8章 5.3・3.4、第9章 4・4.5、第6章 2.2・2.2.2、第3章 4、第6章 5、10.10、第8章 5.4）。本節には写さない。上限のない入口を作らない。
- 画像の画素数は、記憶を割り当てる前に、ファイルの見出しの縦横から確かめる（解凍爆弾への備え。Rust の image の縦横の上限は厳格に効く）。
- 脅威 T-15（使えなくする）：巨大な画像、解凍爆弾（画像、テンプレート、控えの ZIP）。攻撃する者：ファイルを渡す者。狙う資産：アプリの中心。残る破れ：—

### 10.7 時刻

- 端末の時計は信頼しない。証拠としての時刻は RFC 3161 の時刻証明で示す。
- 記録には UTC の RFC 3339（ISO 8601 の網の上の形。`2026-10-01T12:34:56Z`）で書き、表示は利用者の地域の時刻に変換し、時差を添える（例：UTC+9）。
- 時計のずれは、応答した TSA の `genTime` の中央値と要求の時刻の差として自動で学び（NTP の選択と同じく外れ値を捨てる）、直近10回を保持して最新のずれを使う。オフラインの間の記録は、保持したずれで補正した「推定の時刻」を表示して印を付け、次の接続で保留の全記録の時刻証明を取って推定を証明に置き換える。単調な時計（起動からの経過）と壁の時計を並べて持ち、壁の時計の巻き戻り・飛びを検出したら以降の記録に「時計が変わった」印を付ける。アプリのビルドの日時より前、前回の記録より前の壁の時計は異常として記録する。利用者に時計の修正を求めない（証明書の有効期間は時計に依らない。第2章 3.5）（2026-09-30 NRSD の要求）。
- 表示では、時刻証明で証明された時刻に「確認済み」の印（Signal の安全番号の「確認済み」と同じ見せ方）を付け、端末の時計だけの時刻は印なしで示す（2026-09-30 NRSD の要求）。

### 10.8 言語と国

- 「画面の言語」と「権利文書の対象国」を別々の設定として持つ（R-1-7-2）。
- 画面の文言は言語ごとの文言ファイル（第11章 DD-11-8「国際化は文言ファイルで行う」）に置き、画面に文字を直に書かない。

### 10.9 版の互換性

- アプリの版、記録の `schema` の版、C2PA の仕様の版（第3章 DD-3-7「C2PA の仕様の版は c2pa-rs の版に従う」）、参照情報の版を別々に持つ。

### 10.10 URL と QR の形

- URL の正規化（告知先アカウント、転載ページ、参照情報の窓口の URL に共通）：WHATWG URL Standard（url の crate）で解釈し、ホスト名は UTS #46（IDNA Compatibility Processing）の nontransitional で正規化して punycode で記録する。表示は Unicode の形とし、文字の体系が混ざるホスト名には注意を添える（UTS #39）。用途による違いは次の2つだけとする。(1) 告知先アカウントは問い合わせ（`?` の後）と断片（`#` の後）を除いて記録する。(2) 転載ページは入力のままの URL を記録に残し、照合と重複の判定には ClearURLs の規則（参照情報の包み。第8章 3.4「参照情報の包み」）で追跡の引数（utm_、fbclid 等）を除いた正規の形を使う。短縮 URL は展開しない（2026-10-01 NRSD の要求）。
- 投稿先の判定：正規化したホスト名と経路の型（表の `hosts` と `paths`。第7章 2.1 の行の形）を、参照情報の `platforms.json`（第8章 3.4）の表に当てる。表は呼ぶ側が渡す（本節の処理は参照情報を読まない）。当たらなければ一般のサイトとする。判定は告知先アカウント（第2章 2.3「入力の確かめ」）と転載ページ（第6章 2.1「手順」）で同じ。
- 本アプリの URL の方式：`c2pa4cosplayer://<種類>?<名前>=<値>&…`（アプリの識別子は 9.1）。種類と値は次の4つに限る。

|種類|値|使う所|
|---|---|---|
|`import`|ブラウザの拡張が保存した `.wacz` の場所（`path`。利用者の Downloads か監視のフォルダーの下だけ）|第6章 2.2.2「画面の画像の撮り方の案内」（QR には載せない。OS の URL の方式だけ）|
|`contact`|告知コード、個人のルートの証明書の SHA-256、端末の公開鍵（base64url）|第2章 5.5「相手の追加（書類の受け渡し）」|
|`link`|新しい端末の公開鍵（Ed25519）と1回限りの乱数（16バイト）（base64url。Signal の端末のリンクの QR と同じ中身）|第8章 5.4「端末どうしの同期」|
|`recovery`|回復の鍵の文字列（age の `AGE-SECRET-KEY-1…`。Bech32 のまま）|第8章 5.1「形式」|

- QR：ISO/IEC 18004。誤り訂正 M。上の URL をバイトモードで載せる。読む画像は PNG・JPEG、20MB・縦横8,000画素まで（10.6）。読んだ URL は方式と種類を確かめ、値の形が合わなければ受け付けない。

### 10.11 PDF の文書

- PDF の文書（緊急キット（第8章 5.1「形式」）、報告書（第6章 3.4「書き出し」））は krilla で作る（PDF/A-1〜4 と PDF/UA-1 の検証つきの書き出し、タグ付き PDF、埋め込みファイル。2026-10-01 に docs.rs の `Archival`（`A2_U`・`A3_U`）、`Validator::Ua`、`embed` の各項で確かめた）。書き出しの前に krilla の検証（PDF/A-2u または 3u と PDF/UA-1）を通し、通らなければ異常検出として止める（第1章 10.3）。文字は同梱のフォント（第4章 6.1「同梱のフォント」）を埋め込み、見出し・段落・表・図の代替の文を持つタグ付き PDF とする。埋め込みファイル（PDF/A-3u の報告書の `manifest-sha256.txt` と ERS の EvidenceRecord）は krilla の `EmbeddedFile`（`AssociationKind`）で関連付ける。CI では veraPDF でも検証する（第11章 8.1）。

## 13. 端末と人

- 端末の紛失・故障（R-1-6-1）：記録と署名鍵は端末にしかない。控えは初回に置き場を決めれば以後は自動で作られ、置き場が届かない時の知らせも第8章 5.5 による。新しい端末で取り込めば、署名鍵・告知コード・記録を取り戻せる。控えがない場合は鍵を作り直し、告知コードを掲げ替える（第2章 7「署名鍵」）。
- 複数の端末（R-1-6-2）：控えのファイルを別の端末で取り込み、同じ署名鍵を使う（告知コードが1つで済む）。2台で並行して記録を作った場合の統合は第8章 5「控えのファイル」 による。
- 複数の端末（続き）：同じ個人のルートを持つ端末どうしのリンクと記録の揃え、互いの控えの置き場、上限5台は第8章 5.4「端末どうしの同期」・5.5 による（本章には写さない）。
- 引き継ぎ：本人が操作できなくなった時は、緊急キット（回復の鍵と手順の1枚。1Password の Emergency Kit と同じ形。第8章 5.1）と控えで、引き継ぐ人が「引き継ぎとして開く」（読み取り専用）で閲覧・証拠一式の書き出し・同封文書の再生成を行える（第8章 5.3）。権利の帰属は判定しない（D-2-6「法的手続の代理および法的判断は行わない」）（2026-09-30 NRSD の要求）。
- 承認関係と権利の移転（R-1-6-3）：承認書の発行・取り消し（第2章 5「承認と共同の権利」）。権利者の変更は、新しい権利者が自分の情報で C2PA署名する。過去の作品データは移さない。

|1|書き出しの途中で PC の電源が落ちる|原本は変わらない。書き出し済みは記録され、続きから書き出せる。作業の変更は最後の2秒まで失うだけ|
|1|記録の保存の途中でアプリが落ちる|記録は前の版か新しい版のどちらかで残り、壊れた記録はない|
|1|控えのファイルから別の端末に戻す|署名鍵と全記録が戻り、記録の電子署名がすべて通る|
|2|初めての利用者が、説明なしで初回の入力と告知の掲示を終える|5人中4人が終える|
|3|アプリが外へ送るものを数える|4.2 の表の相手と中身だけ|
|4|書き出した画像を公開の検証サイトで確かめる|C2PA署名が有効と出る（信頼済みとは出ない。第2章 3.3「検証器での見え方」）|
|4|書き出した画像の画素を1つ変える|検証で改ざんが出る|
|5|同じ作業を3つの OS で書き出す|画素の値の差が1以内|

### 18.3 NRSD の鍵の事故

|段|すること|
|---|---|
|1 気付く|鍵のファイル・紙の控え・ハードウェアトークンの紛失、PC の乗っ取りの疑い、身に覚えのない更新の電子署名・参照情報の包み|
|2 止める|公開リポジトリの更新の案内と参照情報の包みの公開を止める（第9章 6.5「誤りのある版を出した時」 の1と同じ）|
|3 知らせる|公開ページで、事故の日時、影響（どの期間の更新・参照情報を疑うか）、利用者がすること（README からの入れ直し）を知らせる。アプリのお知らせ（G-21「お知らせ」）は参照情報の包みに載る（第8章 3.4「参照情報の包み」）ため、参照情報のトークンの鍵の事故の間は使わず、4 で鍵を入れ替えた後の最初の包みのお知らせで知らせる（root の鍵を両方失った場合だけ、新しい `root.json` を埋め込んだアプリの版の変更点で知らせる。第9章 4.1「流れと状態」 の段6）。更新の電子署名の鍵の事故では、新しい参照情報の包みのお知らせで知らせる|
|4 入れ替える|鍵の入れ替えは TUF の役割の鍵の入れ替え（第9章 4.3「更新の案内（静的な JSON）の形」）で行い、アプリの版を出す必要はない。参照情報のトークンの鍵（主・予備。委任 `reference`）は、片方の事故ではもう片方でそのまま包みを出し、両方の事故ではオフラインの PC の鍵で `targets.json` を署名し直して新しいトークンの鍵に委任する。root の鍵（2本、しきい値1）は、片方の事故では残る鍵で `root.json` の新しい版を配って入れ替え、両方を失った時だけ新しい `root.json` を埋め込んだアプリの版を更新の電子署名の鍵で配る。更新の電子署名の鍵（Tauri の更新の鍵）の事故では、既存の利用者は README から手動で入れ直す（第9章 4.5「失敗と乗っ取り」）。古い鍵で「最低限の版」を上げる手順は採らない（鍵を失った時は署名できず、漏れた時は攻撃者が大きな版の番号で先回りできるため）|
|5 記録|事故の経緯と対処を運営の記録に残す|

- 障害時の連絡：公開ページとアプリのお知らせ（第10章 G-21「お知らせ」）で知らせる。
- 脅威 T-8（権限の昇格）：NRSD の鍵を盗む。攻撃する者：内部・外部。狙う資産：全利用者。残る破れ：鍵そのものが盗まれた場合（第13章 H-22「NRSD の鍵（更新・参照情報）が盗まれた場合、偽の更新・参照情報を配られ得る」）

## 19. 運営者ツール

- クライアントアプリと同じ基盤で作る別の実行物とし、利用者には配布しない。識別子は `jp.nrsd.c2pa4cosplayer.operator`、データの場所は利用者のアプリと同じ規則（9.1）でこの識別子の下。

|番号|画面|できること|
|---|---|---|
|M-01|参照情報|窓口・文面・各国法・同封文書の文言の版の編集、前の版との違いの確認、IANA の RDAP のブートストラップの一覧の取得と前の版との差分の表示（第8章 3.4）、訂正の印（第8章 3.4）、包みの予算の80%の警告、TUF の委任 `reference` の `targets.json` への署名（主または予備のハードウェアトークン。attestation の証明書を目録に添える。第9章 4.3）と公開|
|M-02|リリースの電子署名|配布物のハッシュの確認、更新の電子署名（ネットにつながない運営者の PC で、合言葉で暗号化した更新の電子署名の鍵を使う。第9章 DD-9-4「更新の電子署名の鍵は CI の外に置き、コード署名の資格は CI の秘密に置く」）、TUF の委任 `release` の `targets.json` と root の版への署名（同じ PC のオフラインの鍵。第9章 4.3、6.1）|

- M-01 は参照情報の原稿と包みを公開リポジトリの手元の写し（clone）に書き、運営者が電子署名つきのコミットで引き込みの要求を出す（第8章 3.5 の主の枝の規則）。公開ページ（`/rights/`、規約、お知らせ）は CI が同じ原稿から生成する（第8章 3.3）。
- 鍵を使う操作は、運営者の PC でのみ行う。M-01「参照情報」は運営者の管理用 PC（ネットにつながる。参照情報の電子署名の鍵はハードウェアトークンの中にあり、署名のたびに PIN を入れる）で、M-02「リリースの電子署名」はネットにつながない運営者の PC（更新の電子署名の鍵）で行う。CI はどちらの鍵も持たない（R-1-10-2）。指摘は電子メールで受け、運営者ツールでは扱わない（第10章 9「指摘の受け口」）。

- 参照情報の原稿の形：`reference/src/` に置く。表（窓口、期限、判定、法の参照先、お知らせ）は YAML（1表1ファイル。行の鍵は番号、文は `ja:`・`zh:`・`en:` の欄）、長い文（ひな形、同封文書の文言、規約、文例）は Markdown（1文書1言語1ファイル）、RDAP のブートストラップ・ClearURLs・VEX はその形式のまま。M-01 は YAML・Markdown を項目の欄で編集し、包み（JSON、zstd）と公開ページを同じ原稿から生成する（静的サイト生成の Markdown＋YAML の慣行）。
- オフラインの PC からの持ち出し：M-02 は配布物の更新の電子署名・案内・`release` の targets を、USB に `manifest-sha256.txt` と一緒に書く。公開する PC の `tools/` の道具が全ファイルのハッシュを照らしてから GitHub Pages・ミラーへ置く（air-gap の慣行）。USB は往復で毎回消す。
