## 2. 登録

### 2.1 手順

|段|利用者|アプリ|
|---|---|---|
|1|「転載を登録」を押し、転載ページの URL を貼る|URL を正規化し、プラットフォームを判定する（第1章 10.10「URL と QR の形」。入力のままの URL も記録に残す）。判定は参照情報の窓口の一覧（第7章 2.1「初版の窓口の一覧（参照情報の初期の中身）」）と対応する。自分の端末の一覧に同じドメイン・URL があれば知らせる|
|2|転載されている画像を、自分のブラウザで保存したファイル、または画像の URL で指定する（任意）|ファイルは直ちに取り込み、透かしの読み出しと PDQ を計算し、自分の作品データと照合（4）。URL の場合は記録だけし、取得は段6（段4 の知らせと選択を受けた後）で行う|
|3|自分のブラウザでページの画面を撮り、その画像を入れる（ログインが要るページは必須。それ以外は推奨）。ブラウザの拡張「証拠を残す」（2.2.2）で作ったファイルを入れれば、この段と段4を1度で満たす|画面の画像のハッシュを計算。拡張のファイルは中の各ハッシュを確かめて取り込む|
|4|（既定で行う）ページの記録を取る。段1の URL を入れた時点で、「登録と同時にページの記録を取ります。相手のサイトにこの PC の IP アドレスが見えます」を示し、「この登録では取らない」の選択を置く（既定は取る）|段6を押した時に、スクリプトを実行しない取得（2.2）でページの HTML と主な画像を保存する（「取らない」を選んだ場合を除く）|
|5|（任意）取っておくべき証拠の入力欄（2.3）を埋める|—|
|6|「登録する」を押す（ボタン1つ）|証拠の保全（3）、次に事件記録の作成と記録の電子署名、次に端末に保存、次に時刻証明（接続がなければ後で付ける。時刻証明の応答は事件記録に書き足さず、別の追記の記録 `status/<端末の番号>.jsonl` として加える。3.2）（第1章 7「実行時の場面」）|
|（前）|転載を手で探す時は、G-12「作品」の「画像検索で探す」から Google レンズ（`lens.google.com`。`uploadbyurl` は公開の URL を要するため使わない）と TinEye（`tineye.com/search`）の頁を既定のブラウザで開き、書き出しの写しを利用者が頁に上げる|アプリは写真を送らず、頁を開いて書き出しの場所を示すだけ。自動の巡回はしない（第2段）（2026-10-01 NRSD の要求）|

- 段6の処理（証拠の保全、事件記録の作成と記録の電子署名、端末への保存、時刻証明）は、段ごとに済んだ印を `state/`（第8章 2.1「配置」）に置き、途中で止まった時は次の起動で記録した段から続ける（第1章 7.8「異常終了の後の起動」）。
- ボタン1つ（R-6-1-1）：URL と段6だけで登録でき、そのとき転載ページの記録（段4）も既定で取る。設計計画書 10.2 は「登録と同時に証拠が保全されます。利用者は、何が証拠として必要であるかを知っている必要はありません」とし、10.3 は「いつ、どこで公開されていたか（②）」の記録を登録の時点で残すことを求めるため、ページの記録を利用者の操作に頼らない。段2・段3・段5 は任意の追加であり、省いた場合は証拠が少なくなる旨を表示する。
- IP アドレスの兼ね合い：取得すると相手のサイトに利用者の IP アドレスが見える（第13章 H-26「転載ページの記録を取ると（登録の既定）、相手のサイトに利用者の IP アドレスが見える」）。既定で取り、見えることを登録の前に示し、その登録に限り外せるようにする。外した登録には「ページの記録なし（②が画面の画像のみ）」の印を付ける。
- 端末の中に記録（R-6-1-3）：事件記録は利用者の端末に置き、利用者の鍵で記録の電子署名を付ける。他の利用者の記録に影響しない。
- 脅威 T-13（情報の漏れ）：転載ページの取得で、相手のサイトに利用者の IP アドレスが見える。攻撃する者：転載サイトの運営者。狙う資産：利用者の所在。残る破れ：取得した場合は見える（第13章 H-26「転載ページの記録を取ると（登録の既定）、相手のサイトに利用者の IP アドレスが見える」）

### 2.2 スクリプトを実行しない取得

- HTTP GET（時間切れ・大きさ・転送の上限は第1章 4.2「外部とのやり取り」の表による）。応答の本文・ヘッダー・最終の URL・取得の時刻（UTC）・応答したサーバーの IP アドレスを保存する。
- HTML の中の `og:image`・`<img>` のうち大きいもの上位5件を同じ方法で取得する（HTML の解釈は html5ever。相対の URL は最終の URL で解決し、`srcset` は記述子の最も大きい候補を採る）。JavaScript・CSS・フォントは取得しない。
- 取得物は画面に描画しない。画像は第3章「署名処理」と同じ画像の基盤（Rust の image crate）で読み込む（読み込めないものはハッシュのみ）。
- ログインの画面に転送された場合は、その応答をそのまま記録し、「ログインが要るため、画面の記録（段3）が必要です」と示す。
- 要求の見出し（DD-6-8「取得の要求は本システムを名乗らない」）は第1章 4.2「外部とのやり取り」の転載ページの行による。
- 取得の前の知らせ（第1章 4.2「外部とのやり取り」）：相手のサイトに利用者の IP アドレスが見えることと、気になる場合は VPN を使えること（Berkeley Protocol 101段）を示す。本システムは VPN を用意しない。
- 脅威 T-9（権限の昇格）：転載ページの取得で悪性の中身に触れる。攻撃する者：悪性のサイト。狙う資産：利用者の端末。残る破れ：利用者自身のブラウザでの閲覧
- 脅威 T-21（情報の漏れ）：転載ページの取得の要求から、証拠を集めていることが転載者に知られる。攻撃する者：転載ページの運営者。狙う資産：事件（証拠の保全）。残る破れ：IP アドレスは相手に見える（H-26「転載ページの記録を取ると（登録の既定）、相手のサイトに利用者の IP アドレスが見える」）

### 2.2.1 WARC と WACZ での保存

- 1回の取得（ページと主な画像）を1つの WARC のファイル（`capture-<連番>.warc.gz`。WARC/1.1）にまとめる。記録の種類は warcinfo（`software`、`format`、取得の道具とその版）、request（送った要求。転送があれば各段の要求）、response（受けた応答。転送の各段の応答と最終の応答）、metadata（取得の時刻、最終の URL、応答したサーバーの IP アドレス、TLS の証明書の主体と発行者）とし、各記録に `WARC-Record-ID`（`urn:uuid:`）、`WARC-Target-URI`、`WARC-Date`、`WARC-Block-Digest`（sha256）を持たせる（ISO 28500:2017 の記録の種類と必須の見出し）。拡張が作った DOM の写し（HTTP の応答ではない）は resource の記録として入れる。WACZ の `datapackage.json` は `wacz_version` 1.1.1、`created`、`software`、`resources`（各ファイルの sha256）を持つ。
- WARC は WACZ（Webrecorder の Web Archive Collection Zipped。米国議会図書館の形式の登録 fdd000586。WARC、索引、`pages.jsonl`、画面の画像を1つの ZIP に）に包み、WACZ Signing and Verification 0.1.0 の形で `datapackage-digest.json` に利用者の署名用の証明書による署名と RFC 3161 の時刻証明を入れる。Webrecorder（py-wacz、ReplayWeb.page）と Starling Lab の道具で誰でも検証できる。ブラウザの拡張（2.2.2）の出力も同じ WACZ とする（2026-10-01 NRSD の要求）。
- 拡張の出力の署名：拡張は鍵を持たないため、`datapackage-digest.json` にハッシュだけを書く（WACZ Signing 0.1.0 の `signedData` を空にする）。アプリは取り込みの時にハッシュを確かめ、利用者の署名用の証明書で anonymous signature（`hash`、`created`、`software`、`signature`、`publicKey`）を付け、RFC 3161 の時刻証明を `timeSignature` に入れる。署名の意味は「アプリが受け取った時点でこの中身だった」。仕様の archiving tool による署名と同じ形。
- RDAP の問い合わせの記録も同じ WARC に加える（5）。
- 部品：warc の crate（0.4.0、MIT、2024-11 更新、crates.io の累計の取得数 約237万）。WARC 1.0・1.1 の記録の読み書きを持つ。［要実測］書き出した WARC を一般の道具（pywb 等）で開けること。

### 2.2.2 画面の画像の撮り方の案内

- Berkeley Protocol（155段）は、ページ全体の画面の記録（日時の入ったもの）を、URL・HTML のソースと並ぶ最低の基準に挙げる。利用者には次を案内する。

  1. ブラウザの「ページ全体の画面の記録」の機能で撮る（Firefox は画面の記録の機能の「ページ全体を保存」、Chrome は開発者の道具の「フルサイズのスクリーンショット」）。拡張はページ全体を、Firefox では `tabs.captureTab` の全体、Chrome の系統では画面を送りながら継ぎ足す方法（GoFullPage 等の全画面の拡張と同じ。`debugger` の権限は使わない）で撮る。

  2. 画面の上の URL の欄と、OS の時計が写った画面の画像も1枚撮る（ページ全体の記録には URL と日時が写らないため）。

  3. ログインが要るページは、ログインした状態で撮る。

- アプリは取り込んだ画面の画像の撮った日時を読む。ブラウザのページ全体の画面の記録は多くが PNG であり撮った日時を持たないため、その場合はファイルの更新の日時を使い、「ファイルの日時（撮った日時の記録ではない）」と区別して記録する。どちらかが登録の日時と大きく違う（24時間以上。初期値）場合は確かめを求める。日時が分からない場合は「日時なし」と記録する。
- ブラウザの拡張「証拠を残す」（Chrome の系統と Firefox。公開の拡張の店に置き、ソースは公開リポジトリの `extension/`。第9章 2）：SingleFile と同じくボタン1つで、そのページの URL・日時・ページ全体の画面の画像・表示中の HTML と画像を、拡張の中で各ハッシュを付けて1つの WACZ のファイル（`.wacz`。2.2.1 と同じ形）にまとめ、ブラウザのダウンロードの API で保存し、その場所を OS に登録した URL の方式（`c2pa4cosplayer://import?path=…`）でアプリに渡す（アプリが起動していなければ OS が起動する。受け取る場所は利用者の Downloads か監視のフォルダーの下だけとし、それ以外の場所や `..` を含む場所は取り込まず、利用者にファイルを選ばせる。渡らない時のために、利用者が選んだ保存のフォルダーの監視も持つ）。ログインが要るページも、利用者のブラウザのログインの状態のまま、本人の画面をそのまま残せる。取り込みの上限は ZIP の中のファイル200、展開後400MB（証拠1件の上限の内）、名前に `..` を含まない。拡張は本システムの名前を名乗らず、サイトに何も送らない。拡張の manifest は MV3、権限は `activeTab`・`scripting`・`downloads` だけ（`host_permissions` と `storage` は持たない。Firefox も同じ manifest）。拡張とアプリの互換は `dev/compat.yaml`（1行は拡張の版、受けるアプリの最低の版、`wacz_version`、`software` の主の版）で持ち、アプリは取り込みの時にこの表で新しすぎる拡張の出力を断る。アプリの側の保存は Perma.cc と同じ WARC と PNG（2.2.1）。拡張が無い利用者には上の案内を残す（2026-09-30 NRSD の要求）。

- 拡張の版とアプリが起動していない時：拡張は `datapackage.json` の `software` に `nrsd-capture/<版>` と `wacz_version` を書く。アプリは自分が知る `wacz_version` と拡張の主の版まで受け、新しければ「アプリを更新してください」（新しい記録の形式と同じ扱い）。URL の方式（deep-link）は OS がアプリを起動して渡す（tauri-plugin-deep-link。Linux の AppImage は起動時に `register()` で登録）。保存のフォルダーの監視は起動中だけで、起動の時にそのフォルダーの未取り込みの `.wacz` を拾う。

|欄|目的|

|項目|内容|

|schema|`nrsd.case/1`|

|source|`manual`（本章）。`auto` は第2段のために予約（R-6-1-4）|

### 2.5 収集の記録

- 形は Berkeley Protocol の附属書 IV「オンラインのデータの収集の用紙」に倣う。

|附属書 IV の項目|本システムで記録するもの|
|---|---|
|収集者|署名者のハンドルネームと告知コード（氏名は記録しない。書き出しの時に利用者が報告書に書き足せる。3.4）|
|収集の端末の IP アドレス|記録しない（端末から外に見える IP アドレスは、外部に問い合わせないと分からないため）。利用者が報告書に書き足せる|
|収集の開始と終了の日時|登録の画面を開いた時刻と、登録を押した時刻（UTC）|
|対象の URL|入力の URL と、取得の最終の URL|
|HTML のソース|WARC の中（2.2.1）|
|画面の画像|取り込んだ画面の画像（2.2.2）|
|取得したデータ|取得した画像の一覧|
|IP アドレス|応答したサーバーの IP アドレスと DNS の結果（5）|
|収集の包みのハッシュの一覧、その一覧のハッシュ|証拠のファイルごとの SHA-256 の一覧と、一覧の SHA-256（3.2 の時刻証明の対象）|

- 加えて記録するもの：アプリの版、取得の道具の版、端末の時計のずれ。時計のずれは、時刻証明の応答の時刻と端末の時計の差として記録する（Berkeley Protocol 155段(g) は、端末の時計を時刻の同期で合わせることを求める。本システムは端末の時計を直さず、ずれを記録する）。
- 拡張で撮った場合は、拡張の版とブラウザの名前と版、拡張が記録した日時も収集の記録に書く。

### 2.6 第2段からの受け口

- `source: auto` の登録は、利用者がアプリで内容を確かめて承認してから、記録の電子署名を付けて端末の事件記録に加える（自動では登録しない）。第2段の設計計画で詳細を定める。

## 3. 証拠の保全

### 3.1 後日示すべき事項との対応（設計計画書 10.3）

|番号|示すべき事項|本システムで残すもの|
|---|---|---|
|①|自らの作品であること|作品データ（原本の指紋、出力の SHA-256・PDQ、マニフェストの写し、時刻証明）を事件記録から参照|
|②|いつ、どこで公開されていたか|画面の画像、スクリプトを実行しない取得の記録（HTML、ヘッダー、最終 URL、取得時刻）、2.3 の入力、証拠一式への時刻証明|
|③|同一の画像であること|不可視透かしから読み出した識別番号、PDQ の距離（4）|
|④|誰が、どこで公開したか|DNS、IP アドレス、ASN、国、ドメインの登録情報（5）、2.3 のアカウント名|
|⑤|許可範囲の外の利用であること|照合した作品の許可範囲・同封文書のハッシュ（第5章「権利文書」）、告知の掲示（第2章「署名の情報と照合」）|

### 3.2 時刻証明

- 証拠のファイルごとの SHA-256 を並べた一覧（JSON）の SHA-256 について、RFC 3161 の時刻証明を取る（ここでの時刻証明は C2PA の検証器とは関係なく、時刻の証拠として使う）。応答した TSA すべての応答を保存する（第3章 4）（2026-09-30 NRSD の要求）。一覧と時刻証明の応答は、状況の追記（`status/<端末の番号>.jsonl`）として事件に加える。
- 証拠を補強する外部の手段（設計計画書 10.3 が参照を定めるもの）：中国の互联网法院は、電子署名・可信时间戳・ハッシュ値の検証・ブロックチェーン等の技術的な手段、または電子の取証・存証の平台の認証により真実性を証明できる電子データを確認する（最高人民法院关于互联网法院审理案件若干问题的规定 第11条）。日本では、公証人が五感で体験した事実を記す事実実験公正証書が、ウェブページの表示の状態の保全に用いられる。本システムはこれらの手続を行わず、対処の案内（G-17「対処の案内」）の「さらに備えるには」に名前とリンクを示す。証拠一式の書き出し（3.4）は、これらの手続にそのまま持ち込めるファイルの形とする（法務調査 L-24「電子署名・電子データの証拠としての扱い（日・中・米）」）。
- 有料の TSA（日本の認定事業者、中国の可信时间戳）は、利用者が事件ごとに選べる。費用は利用者の負担（NRSD は仲介しない。利用者が契約した TSA のアカウントをアプリに設定する）。接続とアカウントの置き場は第3章 4「時刻証明」による。［要見積］各事業者の個人向けの提供と料金。
- 端末の全記録の連鎖の先端の束ねた時刻証明と ERS（第3章 4「時刻証明」）が、事件記録と状況の追記の存在も証明する。オフラインで登録した事件は次の接続の1回で証明される。証拠一式の bag にはその事件に至る抜き出しの EvidenceRecord を含める（3.4）。
- 秘密：有料の TSA のアカウント（利用者が設定した場合）。置き場：OS の鍵保管。控えに含む。端末どうしで同期しない。漏れた時：そのアカウントで時刻証明を求められ得る。事業者で無効にする

### 3.3 取得の失敗

|場面|扱い|
|---|---|
|URL が既に消えている（404・410）|その応答を記録し、画面の画像があれば登録できる|
|接続できない（遮断・タイムアウト）|失敗を記録し、画面の画像で登録。後で「今の状態を確かめる」（6）で再試行|
|ログインに転送|2.2 のとおり|
|応答が大きすぎる（50MB超）|先頭の50MBとハッシュ、打ち切りの旨を記録|

### 3.4 書き出し

- `bag-info.txt` には RFC 8493 の予約の項目のうち `Bagging-Date`、`Bag-Software-Agent`（本アプリの名前と版）、`Payload-Oxum`、`External-Identifier`（事件の番号）、`Source-Organization`（署名者のハンドルネーム）を書き、氏名は書かない（報告書の欄で利用者が足す）。
- 「証拠一式を書き出す」で、事件ごとに BagIt（RFC 8493。米国議会図書館とカリフォルニア電子図書館の包みの形）の bag を作り、RFC 8493 の 4「Serialization」に従って1つの ZIP（名前 `evidence-<事件の番号>-<日時>.zip`。中は bag のフォルダー1つ）に固める（`data/` に下の中身、`manifest-sha256.txt` に全ファイルの SHA-256、`bag-info.txt` に収集の記録の要約、`tagmanifest-sha256.txt`。専門家は bagit の一般の道具で検証できる）（2026-10-01 NRSD の要求）。bag の中身は次のとおり：事件記録と記録の電子署名、証拠のファイル（WARC、画面の画像、取得した画像）、時刻証明の応答、照合した作品データ、同封文書の写し、収集の記録（2.5）、検証の手順書（TXT、日・中・英）、報告書（TXT。登録の概要、①〜⑤の対応、ハッシュの一覧）。
- 報告書には、利用者が書き足す欄（氏名、収集の端末の IP アドレス等）を設ける。書き足した内容はアプリに保存しない（書き出しのファイルにだけ入る）。
- 報告書は TXT に加えて PDF/A-3u（ISO 19005-3。長期の保存。文字が抜き出せる。作り方は第1章 10.11「PDF の文書」）でも作り、bag の `manifest-sha256.txt` と ERS の EvidenceRecord を埋め込む。1つの PDF を専門家に渡せる（2026-10-01 NRSD の要求）。
- 証拠一式には、その事件に至る連鎖の抜き出しと、束ねた時刻証明と、連鎖のたどり方（ハッシュの再計算）の手順を含める。専門家は本システムなしで「この記録はこの日時には存在した」を確かめられる（2026-09-30 NRSD の要求）。
- 検証の手順書には、ハッシュの計算方法（OS の標準コマンド）と、時刻証明の検証方法（OpenSSL のコマンド）、記録の JSON Schema（第1章 8.3）での検証の方法を載せ、Schema の写しを証拠一式に含める。専門家が本システムなしで確かめられるようにする（2026-09-30 NRSD の要求）。

## 4. 照合

### 4.1 一致度の示し方

|結果|表示|
|---|---|
|不可視透かしから識別番号を読み出せ、自分の作品データに一致|「一致（透かし）：識別番号 XXXXX-XXXXX-XXX」|
|透かしは読めないが PDQ の距離が0〜15（初期値）|「ほぼ一致（見た目の指紋）」|
|PDQ の距離が16〜31|「似ている（見た目の指紋）：加工された同じ写真の可能性」（第3章 6「照合用ハッシュ」 の照合のしきい値31以下の内）|
|透かしは読めず PDQ の距離も32以上だが、ISCC の Content-Code（第3章 6）が自分の作品データと一致|「ほぼ一致（内容の符号）」（第3章 6 の「照合は PDQ と ISCC の両方で行う」に合わせた）|
|透かしから識別番号を読み出せたが、自分の作品データにない|「他の人の番号の透かし」。権利者を装う者の手がかりの画面（第10章 G-24「手がかりの比較」、第2章 4.4「権利者を装う者が現れた場合の手がかり」）へ案内する|
|PDQ の距離が32以上、透かしなし、ISCC も一致しない|「一致を確認できません」|

- 複数の作品に一致した時：`work_refs` は、透かしの一致 → PDQ の距離の小さい順 → 新しい順に並べる。表示は原本の SHA-256 で束ね、「一致：識別番号 X（受け渡し用）。同じ写真の他の書き出し N 件」と示す（第1章 8.2：同じ写真の別の型は原本の SHA-256 で結ぶ）。
- 一致の判断と登録の責務は利用者が負う（D-10-6「照合の判断および登録の責務は、登録した利用者本人が負う」）。「一致を確認できません」でも登録はできるが、一覧で「一致を確認できない登録」と印を付け、申立ての前に確かめるよう示す。

### 4.2 何に抵触しているか

- 照合した作品の許可範囲と、転載の態様（2.3 の「有償の配布」、公開されていること）から、抵触の候補を示す。候補の規則は第5章 2.3「画像との紐付け」による。
- 候補は法的な判断ではなく、許可範囲との照らし合わせの結果として示す（第7章 7「線引き」）。

## 5. 誰が、どこで（④）

- DNS で A・AAAA を引き、IP アドレスについて RIR の RDAP で ASN・組織・国・不正利用の窓口を取る。ドメインについてドメインの RDAP（ICANN Lookup と同じ仕組み）で登録事業者・窓口を取る（企画草案［23］）。
- 中国のサイト：ICP 備案号をページの末尾から読み取れた場合は記録する。工業和信息化部の備案の照会（企画草案［22］）は利用者が行う手順として第7章「法的対応ガイダンス」で案内する（照会の画面に画像の確認があるため、アプリから自動で引かない）。
- RDAP の問い合わせは、生の要求と応答（JSON、見出し、TLS の証明書の主体と発行者）を WARC（2.2.1）に証拠として保存する。IP アドレスとドメインの両方と、IP アドレスの逆引きの結果も残す（2026-09-30 NRSD の要求）。RDAP のブートストラップ（どの窓口に問い合わせるかの IANA の一覧）は参照情報から得て、IANA には問い合わせない（第8章 3.4）。
- CDN の裏側の本当のサーバーは RDAP では分からないことがある。その場合も CDN 事業者の不正利用の窓口が申立て先になる（第7章「法的対応ガイダンス」）。

## 6. 状況確認

### 6.1 状況の記録

|状況|記録する者|
|---|---|
|登録済み|アプリ（登録時）|
|申立て済み（日時、窓口、方法、申し出た者の立場（第7章 3.4「申し出る者の立場」））|利用者の入力（第7章の流れから）|
|事業者の応答（受付、判断の結果）|利用者の入力|
|削除を確認|利用者の操作（6.2）|
|再掲載を確認|利用者の操作|
|取り下げ|利用者の入力（7）|

- 状況の種類（`nrsd.status/1` の `kind`）：`registered`、`filed`（申立て済み）、`response`（事業者の応答）、`removed`、`reposted`、`checked`（今の状態を確かめた）、`timestamped`（時刻証明の応答）、`withdrawn`。
- 「申立て済み」「事業者の応答」の行の項目：窓口（参照情報の番号）、方法（フォーム・電子メール）、送った日時、受付の番号（あれば）、申し出た者の立場、送った文面の写しの SHA-256（第8章 2.1「配置」の `filings/` に置く申立ての写し）、応答の日時、結果（受付・削除・拒否・反論の転送・その他）、メモ。これが `nrsd.status/1` の項目である。
- 申立ての写し：ひな形を写した時点の文面から、利用者が入れた欄（氏名・住所・電話・電子メール）を `[REDACTED]` に置き換えた写しを `cases/<事件の番号>/filings/<UUID v7>.txt` に保存し、状況の追記「申立て済み」にその SHA-256 を持たせる。証拠一式（BagIt）に含める。氏名は保存しない方針（第7章 3.1）を保つ。
- 申立ての後の手続の期限の計算、`.ics` の書き出し、3日前・当日の知らせは第7章 6.3「手続の期限の表示」による（事件の画面に示す）。

### 6.2 今の状態の確かめ

- 利用者がボタンを押したときだけ、登録した URL に対してスクリプトを実行しない取得を1回行う。取得した応答は 2.2.1 と同じ WARC（`capture-<連番>.warc.gz`。連番は登録の取得から続ける）として `evidence/` に加え（再掲載の証拠になる。Perma.cc・Wayback Machine が再取得のたびに新しい記録を残すのと同じ）、状況の追記に HTTP の状態・本文のハッシュ・画像の有無・WARC の SHA-256 を記録し、時刻証明を付ける。
- 定期の自動確認はしない。一覧の画面で「最後に確かめた日」を示し、利用者が思い出せるようにする。

## 7. 訂正

- 誤登録の取り下げ：利用者が理由を選び（誤り、許諾済みだった、その他）、取り下げの記録を追記する。証拠のフォルダーは OS のごみ箱へ移す（freedesktop.org の Trash Specification 1.0、Windows のごみ箱、macOS のゴミ箱。`trash` の crate。独自のごみ箱は作らない）。利用者は OS のごみ箱から戻せる。事件記録には取り下げと理由と日時を残す（第1章 8.4「保持と削除」）。一覧の件数から除く（2026-10-01 NRSD の要求）。取り下げの後の連鎖の検証は、記録の行（JSON）だけを対象とし、証拠のファイルの有無は別に確かめる。取り下げた事件は「証拠は削除済み」が正常で、無いことを誤りとしない（Git のコミットが消えた blob を指せるのと同じ：ハッシュは記録に残る）。取り下げていない事件で証拠が無ければ `CAS` の番号で知らせる。
- 自分の作品でない転載を登録した場合（R-6-6-2）：登録は端末の中にとどまり、他の利用者や事業者には届かない。害が生じるのは、利用者がその登録をもとに申立てを送った場合であり、申立ての前に照合の結果と手がかり（第2章 4.4「権利者を装う者が現れた場合の手がかり」）を示し、責務が利用者にあること（D-10-6「照合の判断および登録の責務は、登録した利用者本人が負う」）を示す。

## 8. 一覧と手段

- 一覧：登録した転載を、転載サイト（ドメイン）ごとに束ね、件数、最初の登録日、最後に確かめた日、状況（6.1）、商業的な利用の印（第7章 6.2「共同での対応と優先」）を示す。
- 手段の選択肢：各事件について、とり得る手段（投稿先の窓口への申立て、CDN・ホスティング事業者への知らせ、中国のサイトの ICP 備案の照会、専門家への相談の準備としての書き出し）を示す。どれを講じるかは利用者が判断する（第7章「法的対応ガイダンス」）。
- 共有：他の利用者と共有しない（D-10-9「登録した転載の情報は利用者の端末に一覧としてまとめ、とり得る手段の選択肢を示す。利用者の間の共有は行わない（第2段で扱う）」）。転載サイトの情報の共有と、著作者以外の者から著作者への通知は、第2段の設計計画で扱う（D-13-3「著作者への通知のための連絡先の登録は、第2段の設計計画で扱う」）。
