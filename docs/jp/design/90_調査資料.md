## 調査 I-01・I-02：C2PA 証明書、本人性、権利性（2026-09-29、2026-09-30 改訂）

- 本資料は設計計画書 第1版の段階で調べた事実の記録である。設計計画書 第2版（2026-09-29）で、本システムは利用者を確かめず、利用者の情報を集めず、C2PA署名の証明書は利用者が入力した情報から端末で作る（認証局を要しない）と決めた（D-5-1「本システムは利用者を確かめず、利用者の情報を集めない。本システムを使うために登録を求めない」、D-5-2「C2PA署名の証明書は、利用者が入力した情報からクライアントアプリの中で作る。認証局を要しない」）。このため、2「設計への帰結」の第1版の段階の選択肢（NRSD の私設認証局、適合を取り機器証明書を受ける案、身元の集約者）は採らない。採った設計は基本設計 第2章「署名の情報と照合」3「証明書」に置く。

### 1. 確認した事実（出典つき）

#### 1.1 C2PA のクレーム署名証明書は「生成製品」に発行される

- C2PA Trust List は「適合した生成製品（generator product）に証明書を発行する認証局」の一覧。検証製品は、署名が有効な証明書によるかをこの一覧で判断する。［S1］［S2］
- 適合した生成製品は、Trust List 上の認証局から署名証明書を購入しなければならない。［S3］
- SSL.com：「C2PA 適合に合格したツールと機器にのみ発行する」。無料枠：Level 1 証明書1枚（1年）と年2,500回の時刻証明。有料枠に機器証明書（device certificates）、API。［S4］
- Trufo：C2PA 証明書 年600ドル。OV（組織検証）と PV（製品検証）が必要。テスト用証明書は無料だが検証製品には信頼されない。［S5］
- Trust List（C2PA-TRUST-LIST.pem）の証明書は2026-09-30 の取得で30件であり、発行者の組織は Adobe、Castlabs、DigiCert、Encypher、Google、Huanyu Trust、Huawei、Irdeto、SSL.com、Snowball Technology、Tauth Labs、Trufo、TrustAsia、Verimago、Whole Earth Labs、Xiaomi、vivo の17である（2026年4月時点の記載では DigiCert、SSL.com、Tauth Labs、Trufo の4つ）。［S3］［S12］
- 暫定信頼リスト（ITL）は2026年1月1日に凍結。新規追加なし。［S2］
- Trust List にない署名は「Valid（暗号的に正しいが、エコシステムが保証していない署名者）」と表示され、「Trusted」にならない。［S6］Adobe の検証サイトは「不明な発行元」と表示する。［S2］

#### 1.2 適合の手続きと、鍵の保護の水準

- 手続き：関心表明、次にC2PA との法的契約、次に技術・セキュリティ評価（構成図・文書）、次に証明書の発行。費用と期間は公開情報に記載なし。［S3］［S7］
- 保証水準（Assurance Level）は証明書の拡張に記録される。［S3］
- Level 1：署名鍵を暗号化して保存。OS の鍵保管（macOS Keychain、Linux kernel keyring 等）を使ってよい。「配布するバイナリに認証用の秘密を含めてはならない」。［S8］
- Level 2：鍵をクレーム生成部より高い特権の環境（OSの鍵保管サービスやKMS）で生成・保管・使用し、ハードウェア由来の鍵で包む。遠隔署名の場合はハードウェアの信頼の起点による証明を検証してから署名する。［S8］
- Edge（利用者の端末で動く製品）、Backend（サーバーで署名）、Distributed の区分がある。［S8］

#### 1.3 個人の身元は CAWG identity assertion で載せる（C2PA 署名とは別の信号）

- CAWG の身元の記録（identity assertion）の現行の版は1.3（2026-09-30 に cawg.io で確かめた。本資料の調べは1.2 による）。メタデータ（cawg.metadata）の現行の版は1.1。
- CAWG identity assertion は、資格保持者がデジタル上の身元を支配していることを証明し、C2PA のアサーションに結び付ける。クレーム署名者と同一である必要はなく、独立した追加の信頼の信号。［S9］
- 資格の種類：X.509証明書（cawg.x509.cose）と、身元主張の集約（identity claims aggregation、W3C 検証可能資格情報）。［S9］
- 集約の種類：cawg.social_media（アカウントの支配。username 必須、uri 推奨）、cawg.document_verification（公的身分証。name 必須）、cawg.web_site、cawg.affiliation、cawg.crypto_wallet。［S9］
- 集約者は資産ごとに資格情報を作って署名する（資産ごとの署名）。［S9］このため、集約者は署名のたびに関与する（オンラインの関与が要ると判断する。仕様に明記なし）。
- 役割（role）：cawg.creator、cawg.contributor、cawg.producer 等。独自の値も可。［S9］
- X.509 の主体が法的氏名である必要は、仕様上は定めていない。［S9］
- SSL.com の CAWG 証明書：個人にも発行。身元確認のうえ「確認済みの氏名」が入る。個人 年49ドル、個人と組織 年69ドル、組織 年99ドル。［S10］

#### 1.4 既存の類似サービス

- Adobe Content Authenticity（無料・ベータ）：LinkedIn による氏名確認、Behance・Instagram・LinkedIn・X のアカウントを Content Credentials に表示。JPG/PNG を最大50枚、各20MBまで一括適用。［S11］

### 2. 設計への帰結（第2章・第3章・第8章へ）

#### 2.1 設計計画書 第2版での置き換え（採った設計）

- 利用者の端末で個人のルートと署名用の証明書を作り、C2PA署名する。Trust List には載らず、一般の検証サイトでは「Valid」であり「Trusted」ではない（基本設計 第2章 3「証明書」、3.3「検証器での見え方」）。
- 権利性の手がかりは、告知先アカウントに掲げる告知コード（個人のルートの公開鍵の指紋から作る）とする（基本設計 第2章 DD-2-3「権利性の手がかりは告知先アカウントに掲げる告知コードとする」、2.4「告知コードの作り方」）。
- 身元の記録は `cawg.identity` に X.509（`cawg.x509.cose`）で、署名用の証明書により付ける。第三者による身元の確認は行わない（基本設計 第3章 3.1「記録する項目」）。

#### 2.2 第1版の段階の検討（記録として残す。採らない）

- 「利用者本人が C2PA のクレーム署名証明書を持つ」構成は取れない。クレーム署名証明書は製品に発行される。
- クレーム署名の選択肢
  - A：Trust List 外の署名（NRSD の私設認証局または利用者ごとの自己発行）。費用なし、適合手続きなし。検証サイトでは「Valid」だが「Trusted」ではない。
  - B：本アプリが Level 1 の Edge 生成製品として適合を取り、インストールごとに Trust List 上の認証局から機器証明書を受ける。法的契約・評価・証明書費用・発行の仕組み（登録時の認証）が要る。
  - C：NRSD が署名サーバーを置く（Backend）。サーバーが攻撃対象になり、「Webに上げない」方針（設計計画書 D-6-2「本システムはWebサイトとしては構築しない」）の趣旨に反する。採らない。
- 身元の選択肢
  - X.509 の CAWG 証明書（個人）：身元確認済みの氏名が載る。このため、監査A-15（本名の公開）に正面から当たる。
  - 身元主張の集約（social_media）：ハンドルネーム（username）と告知先アカウントを載せられる。ただし集約者が資産ごとに署名する。このため、NRSD が集約者になると常時稼働のサービスが要る。
  - 本システム独自の照合：告知先アカウントに鍵の指紋を掲示し、本システムの照合手段と公開ページで確かめる（設計計画書5.3の案）。C2PA エコシステムの外の信号。
- 第1版の段階では、段階的な構成（まずAと独自照合、将来B）を有力案とした。第2版で、Aのうち「利用者ごとの自己発行」と独自照合を採り、NRSD の私設認証局と B・C は採らないこととした（2.1）。

## 調査 I-03：投稿先と Cloud での C2PA の保持

### 1. 確認した事実

|サービス|C2PA・EXIFの扱い|出典|
|---|---|---|
|Instagram・Facebook・Threads|アップロード時にC2PAを読み「AI info」表示に使い、配信・再ダウンロードされるファイルからはEXIFもC2PAも除去|［S1］［S2］|
|X|EXIFとC2PAを除去。来歴の表示なし|［S1］［S2］|
|TikTok|C2PAを読んで自動表示。AIコンテンツに独自の透かしを付与|［S1］［S2］|
|LinkedIn|C2PAを読み、CRアイコンと来歴パネルを表示。ファイルとしての保持は確実でない|［S1］［S2］|
|YouTube|動画は再エンコードで埋め込み情報が消える|［S1］|
|WhatsApp|通常送信は全メタデータを除去。「ファイルとして送信」は元のバイトを保持|［S1］［S2］|
|Pinterest|IPTCを読みAI表示。保持は未公表|［S2］|
|微博|単一画像30MB超は原図指定でも圧縮。画像形式を最適化（ファイルサイズが大きく減る）。EXIFについて公式ヘルプに記載なし。報道・解説ではEXIFは除去されるとされる|［S3］［S4］|
|小紅書|アップロード画像のEXIFを読み（スクリーンショット判定等）に使う。配信ファイルでの保持は公開情報なし|［S5］|
|Patreon|投稿画像は複数の解像度の版を配信（再エンコードの可能性）。添付ファイル（attachments）は作成者がアップロードした元の形式で配信|［S6］|
|Google Drive|ダウンロードは元のファイルを変更せずに返す。フォルダーのzipも中身を変えない（二次情報）。Google フォトは共有リンクでGPSを除去することがある（Driveとは別）|［S7］［S8］|

### 2. 設計への帰結

- 主要なSNS（Instagram、Facebook、X、TikTok、YouTube、微博）では、投稿した画像のC2PAは残らないものとして設計する。SNS用の流れは可視署名と不可視透かしで守る（設計計画書7.4と一致）。
- LinkedInは表示するが保持は確実でない。本システムの対象の投稿先としては重要度が低い。
- Patreonは「投稿画像」と「添付ファイル」で扱いが違う可能性が高い。受け渡しにPatreonの添付を使う場合は、元のバイトが保持される想定を置く。このため、実際にアップロードして確かめる（送受信しないと分からない。想定：添付は保持、投稿画像は保持しない）。
- 本表の出典はすべて二次（解説記事・利用者の報告）であり、各サービスの公式の文書に C2PA の扱いの記載は確認できなかった。
- Google Driveは、元のバイトを返すという二次情報が複数ある。このため、NRSD の Drive に上げて取り出し、SHA-256 を比べて確定する（想定：保持する）。
- 透かしの強度は、上記SNSの再エンコード（縮小・JPEG再圧縮・WebP化）に耐える必要がある（第3章の要件）。

## 調査 I-04・I-05 ほか：GitHub の制限、中国本土からの接続、コード署名（2026-09-29、2026-09-30 改訂）

- 本資料の一部は設計計画書 第1版の段階（privateリポジトリに画像と証拠を置き、アプリが REST API で書き込む構成）で調べた。設計計画書 第2版（2026-09-29）で privateリポジトリを設けず、記録と証拠を利用者の端末に置くこととした（D-12-1「公開リポジトリを設ける。privateリポジトリは設けない」、D-12-3「権利者情報、署名鍵、作品データ、台帳および証拠は利用者の端末に置き、NRSDは収集しない」）。このため、2 の REST API・個人アクセストークンの事実と、画像と証拠を1つのリポジトリに蓄積する構成への帰結は、今の設計では使わない（記録として残す）。各節の末尾に第2版での置き換えを書く。

### 1. 中国本土からの GitHub（I-04）

- GreatFire の観測では、2026年8月3日時点で https://github.com は中国本土で60%妨害（直近35回の判定のうち60%で干渉）。［S1］
- raw.githubusercontent.com は一部のISPで遮断・DNS汚染。大きなファイルやバイナリのリリースのダウンロードは遅い。HTTPS が失敗しても SSH の git は通ることがある。［S1］［S2］［S3］
- 設計への帰結（第1版の段階）：中国本土の利用者は、GitHub からの入手・更新・登録を安定して行えない前提で設計する（「登録」は第2版でなくなった。次の項）。代替の経路を第8章・第9章で定める。代替経路の実効性は、中国本土の回線から実際に取得して確かめる（送受信しないと分からない。想定：GitHub 単独では不十分）。
- 第2版での置き換え：代替の経路は香港の地域のオブジェクトストレージ（阿里云の OSS。ICP 備案が要らない）とし、更新と参照情報の取得と、README の中国語の節からの直接の入手に使う（基本設計 第8章 DD-8-5「中国本土向けに香港のミラーを置く」、第9章 5「入手経路」）。第1版の段階で挙げた「登録」（アプリが GitHub に書き込むこと）は、第2版で登録が端末の中で完結するため、なくなった。

### 2. GitHub の制限（第8章）

- リポジトリの大きさ：理想は1GB未満、5GB未満を強く推奨。［S4］
- ファイルの大きさ：50MiB超で警告、100MiB超は拒否。ブラウザからは25MiBまで。1回の push は2GBまで。1ディレクトリ3,000項目、深さ50まで。［S4］［S5］
- Git LFS：Free・Pro は保存10GiB・転送10GiB、Team・Enterprise は各250GiBが含まれる。超過は従量課金。［S6］
- GitHub Actions：Free の組織は private リポジトリで月2,000分・成果物500MB、Team は月3,000分・2GB。public リポジトリの標準ランナーは無料。［S7］
- REST API：個人アクセストークン・GitHub App のインストールトークンは毎時5,000リクエスト。Actions の GITHUB_TOKEN はリポジトリごと毎時1,000。内容を作るリクエストは毎分80・毎時500まで（二次制限）。［S8］
- 細粒度の個人アクセストークン：特定のリポジトリに限定でき、権限を細かく付与できる。組織は承認を必須にでき、最長の有効期限を課せる。［S9］
- リリース：1つのリリースのファイルは1,000まで、各ファイルは2GiB 未満。リリースの合計の大きさと転送量に上限はない。［S14］
- 改変できないリリース（immutable releases）：公開の後、配布物とタグを変更・削除できない（題と説明は変えられる）。リリースの証明（タグ、コミット、配布物）が自動で作られる。［S15］
- GitHub Pages：公開するサイトは1GB まで、転送量の目安は月100GB（超えるとの知らせがあり得る）。［S16］
- 第1版の段階の帰結（記録）：画像と証拠を1つのリポジトリに蓄積し続ける構成は、容量の推奨（1〜5GB）にすぐ当たる。
- 第2版での置き換え：公開リポジトリにはソース、リリース（配布物）、公開ページ、参照情報だけを置き、利用者の画像と証拠は置かない（基本設計 第8章 3「公開リポジトリ」）。REST API と個人アクセストークンは使わない。配布物はリリース（各約200〜300MB。上限2GiB の内）に、参照情報と更新の案内は公開ページ（1GB の内）に置く。

### 3. コード署名（I-05）

- macOS：Apple Developer Program は年99ドル。App Store 外の配布は Developer ID 証明書と公証（notarization）による。［S10］macOS Sequoia 以降、未署名・未公証のアプリは Control クリックで開けず、システム設定の「プライバシーとセキュリティ」から許可する必要がある。［S11］
- Windows：Azure Artifact Signing（旧 Trusted Signing）は月9.99ドルで5,000回まで。組織の公的信頼の証明書は日本を含む国で利用可。個人は米国・カナダのみ。有料の Azure サブスクリプションが必要。EV 証明書は発行しない。SmartScreen の警告は、署名済みでもダウンロードの実績が積もるまで出る。［S12］［S13］
- 設計への帰結：NRSD（日本の法人）は Artifact Signing を組織として利用できる。macOS は Developer Program が必要。Linux は OS の署名の仕組みがないため、配布物の署名（別途の検証手段）を第9章で定める。SmartScreen は初期に警告が出ることを前提に、初回の案内（第10章）で説明する。

## 調査：署名処理の技術要素（第3章の前提）（2026-09-29、2026-09-30 改訂）

- 2026-09-30 の改訂：外部の監査を受け、c2pa.metadata の記述、PDQ の文、時刻証明の信頼の扱いを改めた。採った設計は基本設計 第3章「署名処理」に置く。

### 1. C2PA のアサーション（仕様2.4）［S1］

- 内容の結び付け（ハードバインディング）：c2pa.hash.data、c2pa.hash.boxes、c2pa.hash.bmff.v3
- ソフトバインディング：c2pa.soft-binding（透かし・指紋の識別子）
- 操作の履歴：c2pa.actions.v2。c2pa.created または c2pa.opened が必須。ほかに c2pa.edited、c2pa.watermarked、c2pa.resized、c2pa.published、c2pa.placed、c2pa.converted 等
- 素材：c2pa.ingredient.v3。メタデータ：c2pa.metadata は、仕様 2.x では付録 B.2 の許された項目（撮影の日時、機器、位置等の固定の項目）に限られ、著作者名・著作権・利用条件の項目を持てない。これらは CAWG の `cawg.metadata` に置く（基本設計 第3章 3.1「記録する項目」）。サムネイル：c2pa.thumbnail.claim（出力の縮小）。時刻：c2pa.time-stamp
- 2.4で追加：c2pa.repository-receipt、c2pa.ai-disclosure 等
- 仕様は、来歴データのどれを含めるかを作成者が制御できるようにすることを強く推奨している（個人情報の配慮）。
- 最新版は2.4（設計計画書 第17章で確認済み）。

### 2. 不可視透かし（TrustMark）［S2］［S3］［S4］［S5］

- ペイロードは100ビット。誤り訂正の方式ごとに使えるデータのビット数：BCH_SUPER 40ビット（8ビットの誤りを訂正）、BCH_5 61ビット（5）、BCH_4 68ビット（4）、BCH_3 75ビット（3）。［S3：datalayer.py］
- C2PA の承認済みソフトバインディング一覧に TrustMark の variant Q・C・P が載る（B は載らない）。［S5］
- 使い方：ランダムな識別子を透かしに入れ、同じ識別子を C2PA のソフトバインディング・アサーションに記録する。C2PA が失われても、透かしの識別子を鍵にマニフェストの写しを引ける（Durable Content Credentials）。［S4］
- Rust 版：全 variant の2値モードの埋め込み・読み出しに対応。テキストモードと透かしの除去は未実装。ONNX ランタイム（ort）を使い、モデルは別に取得。対応環境：Windows 10/11、glibc 2.35以上（Ubuntu 22.04以降等）、macOS 10.15以上。［S6］
- ライセンス：MIT（コードとモデル）。［S2］
- 例の画像で PSNR 約50.4dB。［S2］
- 実行速度・再圧縮への耐性の数値は公開の README にない。このため、対象の画像（数千万画素）と対象の SNS の再圧縮で実測して判断する（コードを動かさないと分からない。想定：CPU で1枚あたり数秒以内、SNS の縮小・再圧縮後も BCH_5 で読める）。

### 3. 照合用ハッシュ（PDQ）［S7］［S8］

- pdqhash（Rust、Apache-2.0、純 Rust）、pdq-rs（本家 C++ を包む）、yume-pdq（速度優先）がある。
- PDQ の一致判定の目安はハミング距離31ビット以下（256ビット中）。［S8］
- PDQ は切り抜き・回転に弱い（アルゴリズムの性質。本家文書 hashing.pdf［企画草案の参考文献12］）。切り抜きへの耐性は透かしで補う。90度ずつの回転と反転は、8通りのハッシュを計算して照らすことで扱える（基本設計 第3章 6「照合用ハッシュ」）。

### 4. 時刻証明（RFC 3161）

- 無料の TSA：DigiCert（timestamp.digicert.com）、GlobalSign、FreeTSA（保証なし）。［S9］
- SSL.com の C2PA 無料枠に年2,500回の時刻証明が含まれる。［設計への注記：調査資料「C2PA証明書と本人性」の S4］
- C2PA は TSA の信頼リストを別に持つ。検証者は、TSA の信頼リストにたどれる時刻証明により、証明書の失効・期限切れ後も署名時点の有効性を確かめられる。［調査資料「C2PA証明書と本人性」の S2］ただし上の無料の TSA（DigiCert の一般用、GlobalSign、FreeTSA）は C2PA の TSA 信頼リストに載らず、C2PA 2.x の検証器はその時刻証明を無視して、確かめた時点の時刻で証明書の期限を見る（仕様 2.4 の 15.8.2。2026-09-30 に原文で確かめた）。このため、証明書の有効期間を長く取る（基本設計 第2章 DD-2-11「証明書の有効期間は、どの画像も署名から20年は有効と示される長さとする」）。
- 中国：联合信任时间戳服务中心（国家授时中心と联合信任が構築、RFC 3161・GB/T 20520-2006）。可信时间戳を証拠とした裁判文書は2025年4月時点で10万件超、1,221の法院。［S10］
- 日本：総務大臣によるタイムスタンプ認定制度（2021年開始）。アマノタイムスタンプサービス3161が2023年2月に初の認定、2025年2月に更新。［S11］
- 料金：联合信任、日本の認定事業者とも公開情報で価格を確認できない。このため、見積もりを取得して判断（想定：有料。登録（証拠保全）時の時刻証明のみに使い、署名時は無料のTSAを使う構成を検討）。

### 5. 自己更新（Tauri を採る場合）［S12］

- 更新の署名検証は必須で無効にできない。公開鍵をアプリに埋め込み、秘密鍵で成果物に署名する。秘密鍵を失うと既存の利用者に更新を配れない。
- 更新の取得先を複数指定でき、2xx 以外の応答なら次に進む（代替経路を持てる）。
- GitHub Releases に置く静的 JSON に対応。
