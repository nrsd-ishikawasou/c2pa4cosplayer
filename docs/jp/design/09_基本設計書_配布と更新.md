## 1. 設計上の決定の一覧

|番号|決定|理由|退けた案|
|---|---|---|---|
|DD-9-1|配布物は OS ごとに1つ：Windows は NSIS のインストーラ（利用者ごとの導入。Artifact Signing でコード署名）、macOS は Apple の CPU 向けの1つの DMG（Developer ID でコード署名し公証）、Linux は AppImage（更新の電子署名の鍵による更新の電子署名を付随ファイルで付ける）。Flatpak は Flathub の仕組みで配る別の経路とし（2.1）、本決定の「1つ」は NRSD が自ら配る配布物を指す|非技術者が1回の操作で入れられる形式。各 OS の警告を最小にする（調査 I-05「コード署名」）。ONNX ランタイムが Intel の macOS 向けの配布をやめたため、macOS は Apple の CPU のみとする（第11章 3.1「対応する OS の下限」）|Linux を deb・rpm で分ける案（非技術者向けには1形式で足りる）。macOS を Intel と Apple の両方を含む形（Universal）にする案（第2稿。Intel 向けの ONNX ランタイムがない）。MSI（利用者ごとの導入の設定がなく、版の番号の主の値が255までで「年.月.連番」と合わない）|
|DD-9-2|自己更新は Tauri の更新の仕組みを使い、更新の案内を「公開ページ（GitHub Pages）の `update/latest.json`」、次に「香港のミラーの `update/latest.json`」の順に取得する。配布物は、GitHub の案内では GitHub のリリースから、ミラーの案内ではミラーから取る。更新の電子署名の検証は無効にできない。更新の電子署名に版を入れ（`tauri signer sign --app-version`）、更新の部品の `requireSignedVersion` を真にして、案内の版と電子署名の版が一致しない更新を拒む。これに加えて、案内と配布物のハッシュを TUF のメタデータ（4.3）で検証してから Tauri の仕組みに渡す（凍結・版の戻し・組み合わせの偽りへの備え）|更新の電子署名の検証が必須（調査 署名処理 第5節）。取得先を複数持てる（中国本土）。更新の案内（JSON）には電子署名がなく、書き換えられる者は過去の正しく署名された配布物に大きな版の番号を付けて配れる。`requireSignedVersion` を偽のままにすると、版の記録のない電子署名では照合が飛ばされる（tauri-plugin-updater の updater.rs の verify_signed_version、tauri-cli の signer sign の `--app-version`。2026-09-30 に確かめた）|更新を利用者に手で入れさせる案。案内の版だけを信じる案（古い版を入れさせられ、DD-9-6「版を戻す更新は配らない」が守れない）|
|DD-9-3|公式版の見分け方は、OS のコード署名の発行元名（株式会社流山ソフトウェア開発）と、README・公開ページに載せる配布物の SHA-256 で示す。アプリの中の G-23「このアプリについて」に、自身のコード署名の発行元と版を示す|偽アプリ（T-3「偽のアプリを配る」）への備え。利用者が確かめられる手段を用意する|—|
|DD-9-4|更新の電子署名の鍵は Tauri の署名の鍵（`tauri signer generate` で作る鍵のファイル。合言葉で暗号化）とし、ネットにつながない運営者の PC に置き、紙の控えを金庫に置く。更新の電子署名はその PC の運営者ツールで付ける。CI は更新用の配布物を作らない（`createUpdaterArtifacts` を偽にする）。macOS の更新用の `.app.tar.gz` は、CI が公証まで終えた `.app` から運営者の PC で作り、電子署名を付ける（6.1）。コード署名の資格は、Windows はクラウドのコード署名の事業（Artifact Signing）、macOS は Developer ID とし、CI の秘密に置く。コード署名の資格が CI にあることによる危険は、第8章 3.5 の脅威 T-22「CI・GitHub の組織を奪って、正しくコード署名された偽の配布物を公式のリリースに置く」と第13章 H-44「CI・GitHub の組織が乗っ取られると、正しくコード署名された偽の配布物を公式のリリースに置かれ得る」 で扱う|更新経路の乗っ取り（第8章 3.4 の脅威 T-7「偽の参照情報・更新を配る」）への備え。Tauri の更新の電子署名は無効にできず、鍵を失うと更新を配れない（Tauri の更新の仕組みの公式の案内）。Tauri の署名の鍵は鍵のファイルで扱う作りであり、ハードウェアトークンの中で使う仕組みは確かめられなかった|ハードウェアトークンに置く案（第1稿。Tauri の署名の鍵の扱いと合わない）。CI の秘密に更新の電子署名の鍵を置く案（CI の乗っ取りで偽の更新を配れる）。CI で更新用の配布物を作る案（`createUpdaterArtifacts` を真にするとビルドの時に `TAURI_SIGNING_PRIVATE_KEY` が要り、無いとビルドが止まる。tauri-cli の bundle.rs）|
|DD-9-5|更新は裏で取得して検証し、入れ替えは利用者がアプリを閉じる時、または利用者が「今すぐ再起動して更新」を押した時に行う。一括処理・登録・控えの作成の途中では入れ替えない|Windows では入れ替えの段でアプリが自動で終了する（Tauri の更新の仕組みの公式の案内）。編集の途中で終了させない。入れ替えの前に作業の保存を終える（第4章 11「作業（編集の途中の状態）」）|取得したらすぐ入れ替える案（編集の途中で終了する）|
|DD-9-6|版を戻す更新は配らない。誤りのある版を出した場合は、直した新しい版を出す（前に進めて直す）。まだ入れていない利用者への広がりは、更新の案内を1つ前の版に戻し、誤りのある配布物を除いた新しい `targets.json`（TUF は版を戻せない。6.5）を出して止める|記録の形式の版が上がった後に古い版に戻すと、古い版が新しい記録を読めない（4.4）。Tauri は既定で新しい版だけを入れる|版の戻しを許す案（記録の形式の不整合）|
|DD-9-7|端末の記録を消す操作は、アプリの設定（G-20「設定」）に置き、OS の鍵保管の署名鍵も含めて消す。Windows のアンインストーラの「データを削除する」の欄は、文を差し替えて、証拠が消え戻せないことが分かるようにする|macOS の DMG と Linux の AppImage にはアンインストーラがない。Windows のアンインストーラの既定の欄の名前（「アプリケーションデータを削除する」）では、証拠が消えることが伝わらず、署名鍵（資格情報マネージャー）は消えない（Tauri の NSIS のひな形）|アンインストーラだけに任せる案（macOS・Linux で消せず、Windows でも署名鍵が残る）|
|DD-9-8|Linux の AppImage の実行部（ビルドの時に取得される type2-runtime）と linuxdeploy のプラグインは、取得したもののハッシュをリリースの記録と部品表に残す|Tauri は実行部を版の固定なしに取得する（2026-09 の報告）。何が入ったかを後から確かめられるようにする|何もしない案（配布物に入った実行部を後から特定できない）|

### 2.1 OS ごとの配布物

|OS|形式|CPU|導入の場所・権限|前提の部品|初回の警告と案内|
|---|---|---|---|---|---|
|Windows 10/11|NSIS のインストーラ（`.exe`）。installMode は currentUser（Tauri の既定）。インストーラの言語は日本語・簡体字中国語・英語（NSIS の `languages`。OS の言語に合わせ、選ばせない）|x86_64 で x86-64-v3 に対応するもの（第11章 3.1「対応する OS の下限」）。ARM の Windows は x64 の変換で動かす（［要実測］Snapdragon の Windows 11 での起動と透かし。x64 の変換が x86-64-v3 の命令を扱えるか）|`%LOCALAPPDATA%\<製品名>`。管理者権限は要らない|WebView2：downloadBootstrapper（Tauri の既定。Windows 10（2018年4月以降）と 11 は OS の一部として持つ。無い時だけネットから入れる）|SmartScreen は、コード署名済みでも評判が積もるまで「認識されないアプリ」の警告を出し得る。発行元名が表示されるので、README と初回の案内（第10章 G-01「ようこそ」の前の README の手順）で「発行元が 株式会社流山ソフトウェア開発 であることを確かめ、［詳細情報］、次に［実行］」を画像で示す|
|macOS 14 以上（同梱の ONNX ランタイムの下限による。第11章 3.1「対応する OS の下限」）|DMG|Apple の CPU（aarch64）のみ。Intel の Mac は対象外（8「本章で宣言する破れ」）|利用者が「アプリケーション」へ引いて入れる|なし|公証済みのため通常の確認のみ。DMG から直接起動した場合（書き込めない場所）は、更新ができないため、起動の時に「アプリケーション」へ移すよう示す（［要実測］判定の方法）|
|Linux（glibc 2.35 以上。Ubuntu 22.04 以降、Debian 12 以降）|AppImage|x86_64 で x86-64-v3 に対応するもの（ARM は ARM の機械でしか作れないため初版は出さない）|利用者が置いた場所。実行の権限を付ける|なし。AppImage は依存する共有の部品（WebKitGTK 4.1、GTK、GLib 等。LGPL）を同梱する（Tauri の AppImage の案内「bundles all dependencies」）。同梱する部品は第11章 5.1「許可するライセンス」 の例外と 6.2 のライセンス表記の対象とする。FUSE 2 を要しない実行部を使う（tauri-bundler 2.6.0 以降。出典は「should remove」という見込みの書き方であり、［要実測］Ubuntu 24.04 の新規の環境で起動すること）|OS の警告なし。実行の権限の付け方を README で示す|

- 対応の下限は、TrustMark、ort、ONNX ランタイムの対応のうち最も厳しいものに合わせる（第11章 3.1「対応する OS の下限」）。Linux の配布物は、下限の OS（Ubuntu 22.04）でビルドする（Tauri の案内：対応したい最も古い OS でビルドする）。
- ブラウザの拡張「証拠を残す」（Chrome の系統と Firefox）は公開の拡張の店に置き、ソースは公開リポジトリの `extension/`。版はアプリと別に付け、拡張の店の審査を経る。拡張は設定も記録も持たず、更新は店の仕組みによる（第6章 2.2.2）（2026-09-30 NRSD の要求）。
- Linux は AppImage に加えて Flatpak を Flathub に置く（Tauri の公式の案内による。Linux のデスクトップの事実上の標準の配布の場）。実行環境は `org.gnome.Platform` の Flathub が勧める版、許可は `--share=network` とポータルだけ（`--filesystem` は付けない）。ファイルの選択・既定のブラウザ・通知は xdg-desktop-portal 経由（tauri-plugin-dialog・opener・notification が対応）。更新は Flathub の仕組みに任せ、Tauri の更新は Flatpak の版では切る。砂箱の許可は網と利用者が選んだファイルだけ。AppImage は Flatpak を使わない環境のために残す（2026-10-01 NRSD の要求）。
- 配布物の大きさ：アプリ本体、Linux では同梱の WebKitGTK 等（約70MB 以上。［要実測］）、ONNX ランタイム（約14MB 以上。第11章 4.3「素材」）、TrustMark のモデル（約65MB）、u2netp（約4.6MB）、フォント（約71MB。第11章 4.3「素材」の同梱のフォント約52MB と画面の文字のフォント約18MB の和。絵文字 25.3MB を含む）。［要実測］合計。想定：各 OS とも200MB 前後。判定：300MB 以下。
- ネットにつながない PC：インストーラは WebView2 を除いて自己完結する。WebView2 を持たない Windows（企業の固定の版等）でネットにつながない場合は入れられない（8「本章で宣言する破れ」）。
- 危険：配布物が大きい（フォント約71MB、モデル約70MB（TrustMark 約65MB、u2netp 約4.6MB）、ONNX ランタイム）。影響：入手に時間がかかる。備え：LXGW WenKai は Lite 版を採った（第4章 6.1「同梱のフォント」）。判定300MB 以下（第9章 2.1「OS ごとの配布物」）

### 2.2 アンインストールと端末の記録

|OS|アプリの消し方|消えないもの（既定）|記録を消す方法|
|---|---|---|---|
|Windows|「設定、次にアプリ」から、または導入の場所のアンインストーラ|`%LOCALAPPDATA%\<識別子>` の記録（アプリのデータ、縮小の画像、操作の記録）、資格情報マネージャーの署名鍵|アンインストールの前に G-20「設定」の「この端末の記録を消す」。またはアンインストーラの欄（2.3）を選ぶ（この場合、署名鍵は残る）|
|macOS|「アプリケーション」から `.app` をゴミ箱へ|`~/Library/Application Support/<識別子>` の記録、キーチェーンの署名鍵|アンインストールの前に G-20「設定」の「この端末の記録を消す」|
|Linux|AppImage のファイルを消す|`~/.local/share/<識別子>` の記録、Secret Service の署名鍵（または鍵のファイル）|アンインストールの前に G-20「設定」の「この端末の記録を消す」|

- 既定では記録を残す。記録はこの端末にしかなく（第8章「リポジトリとデータ管理」）、入れ直した時にそのまま使える。
- README の「アプリの消し方」に、上の表と「記録を消すにはアプリの中で先に消す」を3言語で書く。

### 2.3 「この端末の記録を消す」の手順

1. G-20「設定」の「データ」の区分に置く。押すと確かめの窓を出す。
2. 窓は、消えるもの（署名の情報と署名鍵、作品データ、事件記録と証拠、テンプレート、作業、設定、操作の記録）と、消えないもの（利用者が書き出した画像と控えのファイル、利用者の写真の原本）を並べる。最後の控えの日時を示し、控えがない、または最後の控えの後に記録が増えた場合は「控えを作る」を先に示す。
3. 利用者が確認の語（画面の言語の「消す」）を入力して初めて実行できる。既定のボタンは「やめる」とする。
4. 実行：先にリンクした端末（第8章 5.4）へ「この端末を外した」の行を送る（届かなければ他の端末で手で外す。中継の登録は端末の鍵が無くなれば無効）、次に OS の鍵保管の署名鍵と端末の鍵を消す、次にアプリのデータの場所（app_local_data_dir。Windows では WebView2 のデータ `EBWebView/` を含む）を消す、次に縮小の画像の場所（app_cache_dir）を消す、次に操作の記録の場所（app_log_dir）を消す、次に macOS では WKWebView のデータ（`~/Library/WebKit/<識別子>`）を消す（第1章 9.1「OS ごとの置き場所」、第8章 2.1「配置」。macOS はそれぞれ ~/Library/Application Support、~/Library/Caches、~/Library/Logs の下。Windows と Linux の操作の記録はアプリのデータの場所の下の `logs/`）。途中で失敗した項目は一覧で示す。
5. 実行の後はアプリを終了する。次の起動は初回と同じ（G-01「ようこそ」）。
- Windows のアンインストーラの欄の文は、Tauri の言語ファイルを差し替えて、「記録（作品・事件・証拠・テンプレート）を消す。控えがなければ戻せません。署名鍵は残ります。署名鍵も消すには、先にアプリの設定で消してください」の意味の文にする（日・英・中）。Tauri の NSIS の設定 `customLanguageFiles`（言語ごとに Tauri の独自の文を入れた `.nsh` のファイルを指定する。言語は `languages` にも入れる）で差し替える。この欄の文は `.nsh` の `deleteAppData` の文である（Tauri の config.rs と installer.nsi・言語ファイル、2026-09-30 に確かめた）。

|macOS|Developer ID Application の証明書と公証（notarization）|Apple Developer Program（年99ドル）|`.app` の中の実行ファイル・動的ライブラリ（ONNX ランタイムを含む）をすべて署名し、Hardened Runtime を有効にして公証し、DMG に公証の記録を付ける（staple）。［要実測］ONNX ランタイムの動的ライブラリを読み込めること（ライブラリの検証）|

- 取得の前提（2026-09-30 に各社の案内で確かめた）：
  - Artifact Signing の組織の本人確認は、法人のサイトの URL、法人が持つドメインの電子メール（主と副）、事業者の番号、所在地、代表者の個人の本人確認を求め、追加の書類（登記、ドメインの登録の証明等）を求めることがある（Microsoft「Quickstart: Set up Artifact Signing」）。有料の Azure の契約が要る（無料・試用の契約は使えない。同 FAQ）。発行される証明書は短い期間で入れ替わり（ELAM の案内では3日）、署名に時刻印（timestamp.acs.microsoft.com）を付ける（同 FAQ）。証明書の名前（CN・O）は検証された法人名で、変えられない。
  - Apple Developer Program の組織の登録は、D-U-N-S 番号、公開され機能する法人のサイト（法人のドメイン）、そのドメインの業務の電子メールを求める（Apple「Enrollment」）。
  - このため、NRSD の法人のサイトとドメイン（nrsd.jp。株式会社流山ソフトウェア開発のサイトであることを 2026-09-30 に確かめた）と、そのドメインの電子メールを前提とする。公開ページ（GitHub Pages の github.io）はこの前提を満たさない。
  - 発行元名が漢字か英字かは、取得の後に記す（証明書の名前は登記の法人名による）。
- SmartScreen の評判は、発行元の証明書とファイルのハッシュの2つで積もる。同じ発行元の証明書で署名し続ければ、新しい版も証明書の評判を受け継ぎ得る（Microsoft「SmartScreen reputation for Windows app developers」）。このため、発行元（法人名）を変えない。
- Windows 11 の Smart App Control は未署名の実行ファイルを止めるため、インストーラの中の実行ファイル・DLL もすべて署名する。
- 危険：コード署名の評判（Windows の SmartScreen）。影響：初めの頃に警告が出る。備え：案内（第9章）

### 3.2 見分け方

- DD-9-3「公式版はコード署名の発行元と SHA-256 で見分ける」。README と公開ページには、各配布物の SHA-256、コード署名の発行元名、Developer ID のチーム名を載せる。
- 公式の入手先は公開リポジトリの README とし、README に載せた入手先（GitHub のリリース、README の中国語の節に載せる NRSD の香港のミラー、Linux の Flathub（2.1）の3つ）だけを公式とする（5）。README に「公式の入手先は、GitHub のリリース、ここに載せた NRSD のミラー、Flathub の3つです。他のサイトで配られているものは公式ではありません」と明記する。GitHub とミラーの配布物は、同じ SHA-256 とコード署名の発行元で見分けられる。Flathub の版は Flathub の仕組み（NRSD の manifest から Flathub の CI がビルドし、Flathub が署名する）で見分け、README に Flathub のアプリの識別子を載せる。
- 配布物は再現可能に作る（Reproducible Builds：`SOURCE_DATE_EPOCH` を版のコミットの日時に固定、`--remap-path-prefix`、Cargo.lock と package-lock の固定、ビルドの環境を記録）。CI で2回別の環境で作り、署名を外した中身の SHA-256 が一致しなければリリースを止める。README に第三者が同じ配布物を作って照らす手順を載せる。attestations は SLSA Build Level 3 の来歴として出す（2026-10-01 NRSD の要求）。
- リリースに使う鍵（R-9-2-2）：DD-9-4「更新の電子署名の鍵は CI の外に置き、コード署名の資格は CI の秘密に置く」。更新の電子署名の鍵は Tauri の署名の鍵（失うと既存の利用者へ更新を配れない）であり、ネットにつながない運営者の PC の中の鍵のファイル（合言葉で暗号化）と、紙の控え（金庫）で二重に保管する。
- 秘密：アプリの更新の電子署名の鍵。置き場：Tauri の署名の鍵のファイル（合言葉で暗号化）を、ネットにつながない運営者の PC に置く。紙の控えを金庫に置く（第9章 DD-9-4「更新の電子署名の鍵は CI の外に置き、コード署名の資格は CI の秘密に置く」）。漏れた時：偽の更新を配られ得る。失うと更新を配れない（第9章）

## 4. 更新

### 4.1 流れと状態

|段|すること|利用者に見えること|失敗した時|
|---|---|---|---|
|1 確かめる|起動の時と、起動中は24時間ごとに、更新の案内（4.3）を GitHub、次にミラーから取得する|なし|次の確かめの時に試す|
|2 取得する|新しい版があれば、配布物を裏で取得する（一時の場所）|G-21「お知らせ」に「更新を準備しています」|取得に失敗した場合（応答がない、途中で切れる、2xx でない）は、第1章 4.2 末尾の共通の再試行（3回、その後は回線の復帰と1時間ごと）に従い、次からミラーを先にした取得先の並びにする（4.3）。ミラーでも3回続けて失敗したら利用者に知らせ、手動の入れ直しを案内する|
|3 検証する|TUF のメタデータ（4.3）を tough で検証し、次に更新の電子署名をアプリに埋め込んだ公開鍵で検証する|なし|検証に通らなければ捨てる。操作の記録に残し、利用者に「更新を検証できませんでした」と知らせる|
|4 待つ|入れ替えの準備ができた状態で待つ|G-21「お知らせ」 と画面の上端に「更新の準備ができました。閉じる時に更新します」と「今すぐ再起動して更新」|—|
|5 入れ替える|アプリを閉じる時、または「今すぐ再起動して更新」を押した時。一括処理・登録・控えの作成の途中は押せない。入れ替えの前に作業の保存を終える|Windows：進みの小窓（passive）。macOS・Linux：再起動|古い版のまま起動する（4.5）|
|6 始める|新しい版の初回の起動で、記録の形式の移行（4.4）を行い、変更点を G-21「お知らせ」 に示す|変更点の要約（3言語）|4.4 の戻し|

- 利用者の操作は要らない（R-9-3-1）。入れ替えの時期だけを利用者の操作に合わせる（DD-9-5「入れ替えは閉じる時か利用者が押した時」）。
- 更新の確かめで送るのは取得の要求のみであり、相手に IP アドレスが見える。要求の User-Agent は更新の部品の名前と版（`tauri-plugin-updater/<版>`）であり、アプリの版は送らない（tauri-plugin-updater の updater.rs）（第12章 5.2「端末の外への送信の一覧」）。
- OS のシャットダウン・ログオフ（Windows の `WM_QUERYENDSESSION`、macOS の `applicationShouldTerminate`、Tauri の `ExitRequested`）では入れ替えを始めず、作業の保存だけを行い、`state/update-pending` の印を置く。次の起動で、画面を出す前に検証済みの配布物で入れ替える（Firefox の staged update が次の起動で適用されるのと同じ）。利用者の操作で閉じた時だけ、その場で入れ替える（DD-9-5）。
- 配布物の一時の置き場は Tauri の更新の部品の一時の場所（OS の一時のフォルダー）とし、取得の前に空きが配布物の大きさの2倍あることを確かめる（足りなければ次の確かめで試し、G-21 に1行）。

### 4.2 古い版の利用者（更新の強制）

- 版の比較は SemVer の順序による。プレビュー版（5.1）は先行の版の印を除いた本体の版で比べる。
- 参照情報の `minimum-version.json`（`app`（SemVer）、`reason`（3言語）、`date`）に「最低限の版」を持たせ、それより古い版は C2PA署名・登録を止めて更新を求める（記録の形式や参照情報の形式の変更に追従させるため）。閲覧（確かめる画面）、証拠一式の取り出し、控えの作成は古い版でも使える（利用者の記録を取り出せなくしないため）。
- 最低限の版を上げるのは、①記録や参照情報の形式を古い版が正しく扱えない場合、②古い版に利用者の記録を損なう誤りや脆弱性がある場合、に限る。
- 同じ値を更新の案内の TUF のメタデータ（委任 `release` の targets の custom）にも持たせ、規約に同意せず参照情報を取らない利用者（第12章 DD-12-3）にも、更新の案内の経路で届くようにする。

### 4.3 更新の案内（静的な JSON）の形

- Tauri の更新の仕組みの静的な JSON の形に従う（Tauri の公式の案内）。

|項目|中身|
|---|---|
|`version`|正しい SemVer（6.4 の版の番号）|
|`notes`|変更の要点（3言語の文を1つにまとめる）|
|`pub_date`|RFC 3339 の日時|
|`platforms.windows-x86_64`|`signature`（`.exe.sig` の中身）と `url`（NSIS のインストーラ）|
|`platforms.darwin-aarch64`|`.app.tar.gz` と、その `.sig` の中身。`darwin-x86_64` は載せない（Intel の Mac は対象外）|
|`platforms.linux-x86_64`|`.AppImage` と、その `.sig` の中身|

- 案内は2つ置く。GitHub の案内は配布物の URL が GitHub のリリースを指し、ミラーの案内は URL がミラーを指す。版と更新の電子署名は同じである（第2稿の「同じ JSON」を改めた。GitHub を指す URL は中国本土で取得できないことがある）。
- 置き場：GitHub 用の案内は公開ページの `update/latest.json`（改変できないリリースの外。第8章 3.1「構成」、3.5「GitHub のアカウントとリポジトリの守り」）、ミラー用の案内はミラーの `update/latest.json`。配布物と更新の電子署名は GitHub のリリース（改変できない）とミラーに置く。
- Tauri は、応答が成功（2xx）でない時だけ次の取得先に進む（公式の案内）。GitHub が成功を返しても中身が壊れていれば、更新の電子署名の検証に通らず適用しない。Tauri が取得先を次へ進めるのは案内の取得の段だけであり、配布物は案内の `url` から取るため、中国本土で案内は届き配布物が遮られる場合に備えて、取得先の並びはアプリの側で決めて更新の部品の `endpoints` で渡す（tauri-plugin-updater の updater.rs）。並びと失敗した取得先を後ろに回す規則は第1章 4.2「外部とのやり取り」による。
- Windows の入れ方は passive（進みの小窓のみ。操作は要らない。公式の既定）。
- 版の照合：更新の部品の設定 `plugins.updater.requireSignedVersion` を真にする。更新の電子署名は運営者の PC で `tauri signer sign --app-version <版>` により付け、電子署名の信頼された注記（trusted comment）に版を入れる。案内の `version` と電子署名の版が一致しない更新は適用しない（DD-9-2「更新は Tauri の仕組みで取得し、案内と電子署名の版を照らす」）。
- 更新の案内と参照情報の包みは、The Update Framework（TUF）の仕様の形のメタデータ（`root.json`：NRSD の鍵を役割に分ける。`targets.json`：配布物と参照情報の各ファイルのハッシュと大きさ。`snapshot.json`。`timestamp.json`：期限7日（初期値））で配り、アプリは tough（Rust の TUF の実装）で検証してから Tauri の更新の仕組みに配布物を渡す。凍結は timestamp の期限、戻しは版の番号、組み合わせの偽りは snapshot で検出する。鍵の入れ替えは root の版で行い、アプリの更新を待たない（第1章 18.3 の手順を置き換える。第8章 3.4 の包みの検証と一本化する）。役割の鍵と期限：root は2本（更新の電子署名の鍵と同じネットにつながない PC の鍵と、参照情報のハードウェアトークン）でしきい値1、期限1年（PEP 458 は3本のしきい値2を勧めるが、NRSD は1人のため、鍵を別の場所に置く2本で紛失に備える）。top-level targets はオフラインの PC の鍵、期限6か月。委任 `reference`（`reference/*`）は主・予備の2本のハードウェアトークンの鍵でしきい値1、期限120日（包みの期限）。委任 `release`（`dist/*`）はオフラインの PC の鍵、期限6か月。snapshot・timestamp は `tuf-online` の鍵、期限7日（2026-10-01 NRSD の要求）。委任のメタデータのファイル名は TUF の規則どおり役割の名前（`reference.json`・`release.json`。第8章 3.3）であり、本書と他の章で「委任 `release` の `targets.json`」と書くのは `release.json` を指す。メタデータの置き場は公開ページの `tuf/`（第8章 3.3）と香港のミラーの同じ経路。`tuf-online` の CI の仕事は、リリースと参照情報の公開のたびと、それが無くても3日ごと（初期値。期限7日の半分）に `snapshot.json`・`timestamp.json` を署名し直し、公開ページとミラーの両方へ自動で置く（第8章 3.6）。CI が止まって timestamp が切れた時は、アプリは取得の失敗として扱い手元の版を使い続ける（第8章 3.4 の表の5）。
- Flatpak の版（2.1）も同じ `root.json` を埋め込み、参照情報の検証と最低限の版の扱いは同じ。最低限の版を下回った時の案内だけ「Flathub で更新」に替える。root の鍵の入れ替えは root の版の連なりで届きアプリの版に依らず、しきい値を割るまで root の鍵を失った場合だけ Flathub 経由の新しい版が要る。
- 秘密：TUF の鍵（root・targets はオフライン：更新の電子署名の鍵・参照情報の電子署名の鍵と同じ置き場。snapshot・timestamp はオンライン：CI の別の環境 `tuf-online`。第11章 DD-11-13、8.3）。置き場：上に同じ。漏れた時：root・targets の漏れは偽の配布物・参照情報に至る（H-22 と同じ手順）。snapshot・timestamp の漏れは偽の中身を作れず、凍結・混ぜ合わせだけ。鍵を替えて root の版を上げる

### 4.4 記録の形式の移行

- 記録の `schema` の版が上がる更新では、新しい版の初回の起動で移行を行う。
- 手順：①移行の前に、形式の変わる記録（証拠のファイルは形式が変わらないため除く）を同じ場所の `migration-backup/<元の版>/` に写す。写す前に空きの容量を確かめ、足りなければ移行を始めずに知らせる（第8章 6.1「端末の容量の目安」） ②移行を行う ③移行の後の記録を検証する（記録の電子署名、件数、`schema` の版） ④成功したら写しを30日（初期値）残して消す。
- 失敗した場合：写しに戻し、「更新の後の準備に失敗しました。記録は元のままです」と示す。新しい版は記録を読み取り専用で開いて（書き込みをしない）起動し、指摘の送り方（第10章 9「指摘の受け口」）を示す。古い版の再導入は案内しない（版の戻しは行わない。DD-9-6「版を戻す更新は配らない」）。

### 4.5 失敗と乗っ取り

- 入れ替えの途中で止まった場合：Windows の NSIS は古いファイルを残したまま止まり得る。次の起動で古い版が起動すれば、4.1 の2から試し直す。起動しない場合は README の入れ直しの手順による（記録は消えない。2.2）。
- 更新経路の乗っ取り（R-9-3-3）：更新の電子署名の鍵がリポジトリの外にあるため、公開リポジトリのアカウントを奪われても、正しい更新の電子署名のない更新は適用されない。鍵そのものが漏れた場合は、新しい鍵を入れた版を README から手動で入れ直してもらう（Tauri の更新の公開鍵はアプリに埋め込まれているため、自動では入れ替えられない。第13章 H-22「NRSD の鍵（更新・参照情報）が盗まれた場合、偽の更新・参照情報を配られ得る」）。
- 更新の配布物をファイルから手で適用する入口を G-20「設定」に置く（持ち出しキット。5）。500MB まで（第1章 4.2 の取得の上限と同じ）。キットに入れた TUF のメタデータ（4.3）、コード署名、更新の電子署名のすべてを検証する（2026-09-30 NRSD の要求）。

## 5. 入手経路

- README（日・中・英）：①何ができるか（1段落）、②ダウンロード（OS ごとのボタン状のリンク。Linux は AppImage と Flathub の2つ）、③入れ方（OS ごとに画像3枚まで。Windows は SmartScreen の画面、macOS は「アプリケーション」へ引く画面、Linux は実行の権限）、④公式版の見分け方（発行元名、SHA-256、その確かめ方）、⑤照合の手順（画像の署名者と告知コードの確かめ方）、⑥アプリの消し方と記録の扱い（2.2）、⑦原作の権利に関与しないこと・利用者の情報を集めないこと。GitHub の画面の他の部分を見なくて済むよう、README の先頭にこれだけを置く。
- 中国本土：README の中国語の節に、香港のミラーの最新版の配布物への直接のリンクと、その SHA-256 を載せる。リンクは GitHub の README の中にあるため、設計計画書 D-12-6「GitHubのリンクから配布し、READMEをわかりやすく記載する」の範囲に収まる。ミラーは更新の取得（4）と初回の入手の両方に使う。
  - 理由：中国本土では github.com への接続が妨げられることが多く、リリースの大きなファイルの取得は遅い（調査資料「GitHubと配布」）。設計計画書は中国の利用者を主な対象の1つとし、概要設計書 R-8-5-2を満たすには、初回の入手にも GitHub の外の経路が要る。
  - 先例：TrafficMonitor の README は「国内用户如果遇到Github下载缓慢的问题，可以点击此处」として国内向けの写し（Gitee）へ案内する（2026-09-30 に確かめた）。Pot の公式のサイトは、初回のダウンロードから自前の中継（dl.pot-app.com）を使う。
  - 告知の文例と同封文書には、ミラーの URL を載せず、README（公開リポジトリ）を指す。ミラーの古い版は消える（第8章 3.6）ため、長く残る文に版の URL を載せない。
  - 香港の Alibaba Cloud OSS の既定のドメインは、配布物（実行形式・DMG・AppImage）をダウンロードとして返すため、直接のリンクには使える。HTML の案内の頁は置かない。Alibaba Cloud 自身が、中国本土から国外の区画への接続は不安定になり得ると案内しており、到達は保証されない（第13章 H-17「中国本土では README に届かないことがある」）。
- ［要実測］中国本土から GitHub の README・リリースとミラーに到達できるか（第8章 6.2「中国本土」）。README（GitHub）に届かない利用者は入手できない（8「本章で宣言する破れ」、第13章 H-17「中国本土では README に届かないことがある」）。大学のミラー（TUNA、USTC、SDU の github-release）が本システムを写した場合は、README の中国語の節で「第三者のミラーであり、SHA-256 を確かめること」と添えて紹介する（Flutter の案内と同じ扱い）。

- 「持ち出しキット」：G-20「設定」から、アプリの配布物（コード署名・更新の電子署名つき）と最新の参照情報の包みを1つのフォルダー（`c2pa4cosplayer-kit/README.txt`（3言語）、`dist/<版>/<OS>/` に配布物と `.sig`、`reference/` に包みと TUF のメタデータ、`SHA256SUMS`）に書き出せる。配布物は、更新で取得して検証した写しをキャッシュの場所の `kits/` に1版だけ残しておき、それを使う。無ければ公開リポジトリ・ミラーから取得して検証してから作る。USB で運び、届かない環境の別の利用者が導入と更新を行える。検証は通常の入手・更新と同じ（2026-09-30 NRSD の要求）。

### 5.1 プレビュー版（利用者の試行のための版）

- 利用者の試行（第10章 2.4「判定」）は、動く版で行う。そのための版を「プレビュー版」とし、公式の配布（README と更新の案内）には載せず、試行の参加者にだけ渡す。
- プレビュー版も公式版と同じ手順でコード署名し、C2PA署名と記録の形式は本番と同じにする（試行で作った画像と記録を、正式の版でもそのまま使える）。版の番号は `年.月.連番-preview.連番`（SemVer の先行の版の形。例：`2026.11.1-preview.1`）とし、正式の版より前の版として扱われる。
- プレビュー版の更新の案内は、公式の案内とは別の URL に置き、試行の参加者のアプリだけがそこを見る。更新の電子署名の鍵は正式版と同じとし、プレビュー版の配布物も `dist/<版>/` に置いて委任 `release` の `targets.json` に載せる（TUF の検証は正式版と同じ。4.3）。試行の後に正式の版が出たら、プレビュー版のアプリは正式の案内へ自動で移る（2026-09-30 NRSD の要求）。

## 6. リリース

### 6.1 手順

1. 版番号を決める（6.4）。輸出管理の条件（6.3）を確かめる。
2. Actions で3つの OS の成果物を作る。Linux は Ubuntu 22.04 の環境でビルドし、AppImage の実行部のハッシュを記録する（DD-9-8「AppImage の実行部のハッシュを残す」）。ライセンスの一覧（第11章 DD-11-9「ライセンスの一覧を自動で同梱する」）と部品表（SBOM）を作る。
3. Windows・macOS のコード署名と公証を CI で行う。CI は `createUpdaterArtifacts` を偽にしてビルドし、更新用の配布物と更新の電子署名を作らない。
4. 担当者が成果物を運営者の PC に移し、ハッシュを確かめる。macOS は、公証を付けた `.app` を `.app.tar.gz` に固める（Tauri が作る更新用の配布物と同じ形）。各 OS の更新用の配布物（Windows の `.exe`、macOS の `.app.tar.gz`、Linux の `.AppImage`）に、更新の電子署名の鍵で `tauri signer sign --app-version <版>` により更新の電子署名を付ける（DD-9-4「更新の電子署名の鍵は CI の外に置き、コード署名の資格は CI の秘密に置く」）。同じ PC で、TUF の委任 `release` の `targets.json` に各配布物のハッシュと大きさを載せて署名する（4.3）。
5. 下限の OS の新規の環境（Windows 10、macOS 14 の Apple の CPU の機械、Ubuntu 22.04 と 24.04）で、①新規の導入、②1つ前の版からの更新、③記録の移行、④起動と書き出し、を確かめる（［要見積］仮想の機械の用意）。試験の中身は試験の文書で定める。
6. GitHub のリリースに置き、香港のミラーに写す。Linux の AppImage に同梱した LGPL の共有の部品（WebKitGTK、GTK、GLib 等）の対応するソースの包み（ビルドに使った Ubuntu 22.04 の版のもの）を、同じリリースとミラーに置く（第11章 5.1「許可するライセンス」の例外。LGPL-2.1 の第4節・第6節(d)）。README の SHA-256、中国語の節のミラーへの直接のリンク、変更点（3言語）を更新する。更新の案内（GitHub 用は公開ページの `update/`、ミラー用はミラー。第8章 3.1「構成」）を最後に置き換える（案内が配布物より先に出ないようにする。案内は改変できないリリースの外に置くため、差し替えられる）。署名した `targets.json` を公開ページの `tuf/` に置くと、CI の `tuf-online` が `snapshot.json`・`timestamp.json` を署名し直して公開ページとミラーに置く（4.3、第8章 3.6）。アプリは TUF の検証が通るまで新しい配布物を取らない。 公開ページの `/rights/` と規約の頁は CI が参照情報の原稿から生成し、差分を引き込みの要求で確かめてから公開する（第8章 3.3）。 Flatpak の manifest を Flathub のリポジトリに引き込みの要求で出す（ビルドは Flathub の CI）。
7. 参照情報の「最低限の版」を必要に応じて上げる（4.2）。
8. ブラウザの拡張との互換の表（第6章 2.2.2）を確かめる。拡張の版は SemVer で独立に付け、`extension/CHANGELOG.md` を持つ。店への提出（Chrome Web Store・AMO の審査）は `tools/` の手順書による。

### 6.2 同梱するライセンス表記

- 第三者の構成要素（Tauri、c2pa-rs、trustmark とモデル、ort と ONNX ランタイム、pdqhash、image、u2netp、フォント、AppImage の実行部、AppImage に同梱する OS 由来の共有の部品（WebKitGTK、GTK、GLib 等。LGPL。第11章 5.1「許可するライセンス」 の例外））のライセンス文書と著作権表示。LGPL の部品は、あわせて対応するソースを配布物と同じ場所に置く（6.1 の6）（設計計画書 第17章「第三者の権利およびライセンス」、第11章 4「部品の一覧」）。
- OFL のフォントは、著作権の表示、ライセンスの告知、ライセンスの本文を同梱する（法務調査 L-19「フォントのライセンス」）。

### 6.3 暗号を含むソフトの輸出管理

- 本システムの暗号の用途は、C2PA署名と記録の電子署名（ECDSA P-256）、ハッシュ（SHA-256。直接の接続のファイルの転送は BLAKE3）、控えのファイルの暗号化（age の形式：scrypt、ChaCha20-Poly1305、HMAC-SHA-256。回復の鍵の X25519）、更新の電子署名（Ed25519。Tauri の署名の鍵の形式）、TUF のメタデータの署名（Ed25519）、直接の接続（iroh：QUIC の TLS 1.3、Ed25519 の端末の鍵、合い言葉から鍵を導く Argon2id、合い言葉による鍵の合意 SPAKE2（RFC 9382）、安全番号の SHA-512）、通信（TLS）であり（2026-10-01 に全部を列挙し直した）、いずれも公開の標準の暗号である。独自の暗号を実装しない（第12章 DD-12-8「公開の標準の暗号のみを使い、公開・無償で配る」）。
- 日本（NRSD の所在地）：ソースコードを公開したプログラムの提供は、貿易関係貿易外取引等に関する省令 第9条第2項第九号ニにより許可を要しない。配布物（実行形式）は、購入に制限がなく無償で提供し、技術支援を要しないように設計したものとして、同項第十四号イにも当たり得る。
- 米国：公開の暗号のソースコードは EAR の対象外であり、通知は「標準でない暗号」を実装する場合に限る（15 CFR 742.15(b)。2021年3月29日の改正）。本システムは通知を要しない。
- リリースの手順（6.1 の1）で、次を毎回確かめる。①新しく加えた部品に、標準でない暗号を実装するものがないこと（部品表 SBOM と部品の説明で確かめる）②その版のソースコードが公開リポジトリで公開されていること ③配布物を制限なく無償で配ること。1つでも満たさない場合は、リリースを止めて法務調査 L-14「暗号を含むソフトの輸出管理（日・米）」 を見直す。

### 6.4 版の付け方

- 「年.月.連番」とする（例：2026年10月の1つ目は `2026.10.1`）。形は Semantic Versioning 2.0.0 に合う。変更の記録は Keep a Changelog の形（版ごとに Added・Changed・Fixed・Security の見出し。3言語）で `CHANGELOG.md` に書き、更新の案内の `notes` と G-21「お知らせ」 の変更点はここから作る（2026-10-01 NRSD の要求）。SemVer は数字の先頭に0を置けないため、月は `9` と書き `09` と書かない。同じ月の2つ目は `2026.10.2`。
- 記録の形式の互換は、版の番号ではなく記録の `schema` の版で表す（第1章 8.3「形式と版」）。
- MSI を加える場合は、MSI の版の番号の上限（主・副の値が255まで）に当たるため、版の付け方を見直す（Microsoft「ProductVersion property」）。

### 6.5 誤りのある版を出した時

|段|すること|期限（初期値）|
|---|---|---|
|1|更新の案内（GitHub 用とミラー用）を1つ前の版に戻し、まだ入れていない利用者への広がりを止める。TUF は版を戻せないため、誤りのある配布物を除いた新しい `targets.json`（委任 `release`。版は1つ上げる）をオフラインの PC の鍵で署名して置き、`tuf-online` が `snapshot`・`timestamp` を署名し直す（4.3）。誤りのある版のハッシュが `targets.json` から消えるため、案内が残っていてもアプリは取らない|気付いてから1時間以内|
|2|誤りのある版を入れた利用者への影響を調べ、公開ページと参照情報（G-21「お知らせ」）で知らせる|24時間以内|
|3|直した版を出す（版の番号は誤りのある版より大きくする。DD-9-6「版を戻す更新は配らない」）|誤りの重さによる|
|4|記録を損なう誤りの場合は、参照情報の最低限の版を直した版に上げる（4.2）|直した版と同時|

- GitHub のリリースの誤りのある版は消さず、「使わないでください」を題に付ける（入手済みの利用者が SHA-256 を確かめられるように残す）。
