## 本書の位置付け

- 概要設計書 第4章を詳細化する。本章は、写真に名前やクレジットを描き込む機能（可視署名）の中身、テンプレート、編集の操作、取り消しとやり直し、作業（編集の途中の状態）の保存、一括適用、書き出しを定める。画面の見た目と配置は第10章「画面とデザイン」で定める。
- 本章は検討メモ「第4章 画像編集と一括適用の検討」（NRSD の内部の検討の記録であり、本書とともには配らない。設計の根拠となる事実は、本書の各節に出典とともに書いた）に基づく。同種のソフトの調査、部品の事実と出典は検討メモに置く。
- 受ける決定は次の表のとおりである。設計計画書の決定・要調査・未決の文は第13章 1.2「設計計画書の決定から概要設計書・基本設計への対応」と概要設計書の行き先表による（本章には写さず、番号と項目割りの抜けだけを載せる）。

|番号|種類|内容|
|---|---|---|
|A-11|項目割りで見つけた抜け|フォントのライセンス|

- 用語：本章で「作業」とは、編集の途中の状態をまとめたもの（他のソフトでいうプロジェクト）をいう。「まとまり」とは、配置の単位となる層の集まりをいう。「層」とは、文字または画像の1つの要素をいう。

## 2. 可視署名の範囲

- 可視署名は、写真の画素に名前やクレジットを描き込むものである。SNS 用の画像には必ず描き込み、受け渡し用の画像に描き込むかはテンプレートごとに決める（第3章 DD-3-6「受け渡し用画像の可視署名はテンプレートごとに決める」。O-11「受け渡し用画像への可視署名」はこれで解消する）。
- 描き込むのは書き出しの時である。原本は変えない（DD-4-14「編集は非破壊とする」）。
- 利用者がこれまで画像編集の道具（GIMP 等）で行ってきた、名前やクレジットを写真に重ねる作業を、本アプリで行えるようにする。本アプリで行うことと、利用者の現像・レタッチの道具に任せることの境は、次の表のとおりとする。

|本アプリで行うこと|利用者の現像・レタッチの道具に任せること|理由|
|---|---|---|
|文字の層と画像の層を重ね、まとまりにし、位置・大きさ・回転・重なりの順・表示・固定・不透明度を決める|ブラシ・消しゴムによる手描き|手描きのサインは、紙に書いて取り込むか、他の道具で作った透過の画像として取り込む（5）|
|文字の書式（フォント、大きさ、色、揃え、行間、字間、縁取り、影、背景の板、縦書き）|選択範囲、切り抜き、明るさ・色の補正、レタッチ|写真の加工は現像・レタッチの道具の役目であり、本システムの範囲はライセンスの表示である（設計計画書 D-2-2「本システムの範囲はライセンスの適用とする」）|
|画像の層（ロゴ、手書きのサインの画像）の大きさ・回転・不透明度・塗り替え|写真どうしの合成|同上|
|写真ごとに、まとまりの位置・大きさ・回転を直し、層を隠し、色を変え、その写真だけの層を加える|—|—|
|投稿先ごとの大きさ・形式・色空間での書き出し|縦横比を変える切り抜き|切り抜きは写真の構図の判断であり、利用者の道具で行う。Instagram の縦横比の範囲の外の写真は書き出しの前に知らせる（14.1）|

## 3. 文字の層

### 3.1 中身と差し込み

- 文字の層の中身は、自由な文字と、差し込み（写真ごとに変わる値）の組み合わせである。複数行を書ける。
- 差し込みは、編集の画面の「差し込み」の一覧から選んで入れる。保存の形式では `{名前}` の形で持つ（15.1）。利用者が中括弧そのものを書く場合は `{{` `}}` と重ねる。

|差し込み|保存の形式|中身|値がない場合|
|---|---|---|---|
|ハンドルネーム|`{handle}`|署名の情報のハンドルネーム（第2章 2「C2PA署名のための情報の入力」）|—（必ずある）|
|共同の権利者|`{coholder}`|取り込んだ共同の権利の書面の相手のハンドルネーム（第2章 5「承認と共同の権利」）。作業ごとに選んだ1人の相手（第10章 G-08「書き出し：写真と用途」で選ぶ。15.2 の `coholder`）|その行を描かない|
|共同の権利者の役割|`{coholder_role}`|共同の権利の書面の相手の役割（撮影者・コスプレイヤー）。画面の言語で書く|その行を描かない|
|主たる権利者|`{grantor}`|取り込んだ承認書の発行者（主たる権利者）のハンドルネーム（第2章 5.1「承認書」）。役割が「承認を受けた者」の利用者が、承認書を選んで書き出す時に使う|その行を描かない|
|告知先アカウント|`{account}`|署名の情報の告知先アカウントのうち、テンプレートで選んだもの|その行を描かない|
|撮影日|`{shot_date}`|写真の撮影情報の撮影日時の日付。書式はテンプレートで選ぶ（2026-09-29、2026年9月29日、Sep 29, 2026）|その行を描かない|
|書き出しの日|`{export_date}`|書き出した日。書式は撮影日と同じ|—|
|識別番号|`{work_id}`|書き出す作品の識別番号（第3章 7.1「識別番号」）|—（書き出しの時に決まる。プレビューでは見本の番号を示す）|
|撮影の名前|`{shoot}`|作業で入れた撮影の名前（第10章 G-08「書き出し：写真と用途」）|その行を描かない|
|許可範囲の短い表記|`{license}`|書き出しの許可範囲の短い表記（第5章 2.1「選択肢」の `P1`・`P2+A1+A2` の形）|—|

- 「その行を描かない」の扱い（行を抜いて詰める）は 3.5「描画」による。
- プレビューの見本の識別番号は固定値 `00000-00000-000`（検査の4ビットが合わず、実在しない）。
- テンプレートは `{account}` の告知先アカウントを URL で持つ。渡した相手に同じ URL が無ければ、その行は描かない（`{coholder}` と同じ扱い）。
- 退けた案：撮影情報のすべて（機種、レンズ、ISO、位置情報等）を差し込めるようにする案。クレジットの目的に要らない。位置情報は第3章で出力から除くものであり、描き込むと除いた意味がなくなる（第3章 8.4「撮影情報の除去」）。

### 3.2 書式

|項目|内容|範囲|既定（初期値）|
|---|---|---|---|
|フォント|主のフォントと代わりのフォントの並び（6）|同梱と持ち込みのフォント|6.2 の既定の並び|
|太さ|フォントが持つ太さから選ぶ|フォントによる|フォントの標準|
|大きさ|字の大きさ（写真の短辺に対する割合）|0.5%〜20%|3.0%|
|色|文字の色、または「自動（白か黒）」|—|自動|
|揃え|行頭・中央・行末（縦書きでは上・中央・下）|—|行頭|
|行間|字の大きさに対する倍率|0.8〜3.0|1.3|
|字間|字の大きさに対する割合で増減|−10%〜+50%|0|
|縁取り|外側のみ。太さ（字の大きさに対する割合）、色（任意、または「文字の色の反対」）|0〜30%|6%、文字の色の反対|
|影|角度、距離（字の大きさに対する割合）、ぼかし（同）、色、不透明度|距離0〜50%、ぼかし0〜50%|なし|
|背景の板|文字の後ろに敷く角丸の四角。色、不透明度、角の丸み、内側の余白|—|なし|
|書く向き|横書き・縦書き|—|横書き|
|回転|層の回転（度）|−180〜180|0|
|不透明度|層全体の不透明度|0〜100%|100%|

- 縁取りを外側のみとした理由：手書き風の細いフォントに内側・中央の縁取りをすると字がつぶれる。Photoshop の縁取りは外側・内側・中央を持つが採らない。
- 「文字の色の反対」は、文字が白なら黒、黒なら白、それ以外は明るさの反対の白か黒とする。
- 色の選び方（縁取り・影・背景の板の色も同じ）：色の面と色相の帯、16進の入力（例：`#FFFFFF`）、写真から拾う（スポイト。写真の上の1点の色を取る。3×3画素の平均）、最近使った色（8つまで。設定に保存）、テンプレートの色（テンプレートで使っている色の一覧）。色は sRGB の値で持つ（DD-4-12「色は sRGB に変換し、sRGB の ICC を埋め込む」）。
- 文字の色の「自動」：置いた所の背景（まとまりの枠の中の写真の画素）の平均の色と、白・黒それぞれのコントラスト比（WCAG の式）を計算し、比の大きい方を選ぶ。相対輝度でいえば約0.179 を境に、それ以上なら黒、未満なら白になる（WCAG の相対輝度 L で、(1.05)/(L+0.05) と (L+0.05)/(0.05) が等しくなる点）。第2稿の「0.5 を境」は、0.18〜0.5 の背景で比の小さい白を選んでしまうため改めた。
- 読みやすさの確かめ：文字の色と背景の平均の色のコントラスト比（WCAG の式）が3:1（初期値）未満なら、縁取りを自動で付け、格子に「読みにくい」の印を付ける。

### 3.3 縦書き

- 日本語・中国語の縦組みを行う。行を上から下へ組み、行を右から左へ並べる。
- 字形は HarfRust の上から下への方向で組み、フォントの縦書きの字形（`vert`。句読点、括弧、長音、小書きのかなの縦の形）と縦の寸法（vhea・vmtx）を使う。
- 縦の中の英数字は、既定では語ごとに90度右に回す。2桁までの数字は縦中横（1文字の枠に横に並べる）を選べる。
- 縦書きの字形を持たないフォント（Caveat）は、縦書きの層の主のフォントに選べない。代わりのフォントとして英字にだけ使う。
- 縦書きの組版の部品は既成のものがないため自作する（DD-4-5「文字の組み立てと描画はプレビューも書き出しも同じ Rust の仕組みで行う」）。
- ［要実測］Klee One・Yomogi・LXGW WenKai Lite（縦書きの字形を持つ同梱の3つのフォント）で、縦書きの句読点・括弧・長音・小書きのかなが縦の形になること。判定：各フォントで試験の文（「「撮影：ー、。」ぁぃっ」を含む）を描き、目で確かめる。LXGW WenKai は `vrt2` を持たず `vert` のみを持つが、`vert` で足りる見込み。
- 危険：縦書きの組版を自作する。影響：作る量が増え、誤りが出やすい。備え：試験の文を決めて確かめる（第4章 3.3「縦書き」）

### 3.4 足りない字

- 文字ごとに、主のフォントから順に代わりのフォントを探し、字形のある最初のフォントで描く。
- どのフォントにもない字は、編集の画面で、その字の下に印を付けて知らせる。書き出しの前に、足りない字のある写真の一覧を示し、確かめを求める。四角（いわゆる豆腐）のまま書き出さない。

### 3.5 描画

- 描画の順（1つの文字の層）：背景の板、影、縁取り、文字の塗り。文字は字素（UAX #29 の grapheme cluster）ごとに代わりのフォントを探し、行の中の向きは UAX #9（双方向）で決める。自動の折り返しはしない（行は利用者が分ける）。差し込み（3.1）を含む行の差し込みが空の場合は、その行ごと描かず、残る行をまとまりの基準点の側に詰める。縁取りの角と端は丸（round join・cap）。回転の中心はまとまりの中心。
- 影は、文字と縁取りの形を塗った画像をぼかし（ガウスのぼかし。σ＝ぼかしの値の半分。CSS の box-shadow の blur radius と σ の関係と同じ）、角度と距離だけずらして描く。
- 描画は tiny-skia で行い、字の輪郭は skrifa で取り出す。絵文字（Noto Color Emoji）は COLRv1（ベクターの色つきの字形）の塗りの命令を skrifa で取り出し、tiny-skia で描く（6.3）。
- 描画の精度：1画素を1/4画素の単位で位置を合わせ、字の縁は滑らかにする（tiny-skia のアンチエイリアス）。
- 描き込みの色とビット数：可視署名は tiny-skia で8ビットの RGBA（sRGB の値）の透過の画像として描く（tiny-skia は RGBA の8ビットだけを扱う。tiny-skia の README）。写真が sRGB でない、または16ビットの場合（受け渡し用の原寸の TIFF 等）は、描いた透過の画像を moxcms で写真の色空間に変換し、写真のビット数に広げてから重ねる。可視署名の色は sRGB の値で持つ（3.2）ため、どの色空間の写真にも同じ見た目の色で入る。［要実測］Adobe RGB の16ビットの TIFF に白・黒・原色の文字を重ね、sRGB の値との色差（ΔE2000）が1未満であること。
- ［要実測］同じ入力で Windows・macOS・Linux の描画の結果が一致するか。判定：試験の画像50枚で、画素の値の差がすべて1以内。満たさない場合は、差の出る処理を特定して直す。

## 4. まとまりと層

### 4.1 構造

- テンプレートは1つ以上のまとまりからなり、まとまりは1つ以上の層からなる。
- 層の位置はまとまりの中の相対の位置（まとまりの左上からの位置。写真の短辺に対する割合）で持つ。
- まとまりの大きさは、中の層を囲む最小の四角とする。まとまりの大きさを変えると、中の層の大きさと相対の位置が同じ倍率で変わる。

### 4.2 層の操作

|操作|内容|
|---|---|
|加える|文字の層、画像の層を、選んでいるまとまりに加える|
|複製|層を写して、同じまとまりの一番上に置く|
|削除|層を消す|
|名前|層の一覧での名前（既定は文字の最初の10文字、または画像のファイル名）|
|重なりの順|層の一覧の中でドラッグして順を変える。一覧の上ほど手前に描く|
|表示・非表示|層を隠す。隠した層は書き出しにも描かない|
|固定|写真の上で選べず、動かないようにする（背景に敷いたロゴを誤って動かさないため）。層の一覧からは選べる|
|不透明度|0%〜100%|
|別のまとまりへ移す|層を他のまとまりへ移す。移した後の位置は、写真の上での見た目の位置を保つ|

### 4.3 まとまりの操作

|操作|内容|
|---|---|
|加える|空のまとまりを加える|
|削除|まとまりと中の層を消す|
|名前|まとまりの名前（既定は「クレジット」「注意書き」等の順の番号つき）|
|基準点・余白|位置（7.1）|
|自動配置の対象|自動配置で動かすか（固定の位置に置くまとまりは外す）|

### 4.4 数の上限

|項目|上限（初期値）|理由|
|---|---|---|
|1つのテンプレートのまとまり|4|クレジット、注意書き、ロゴ、予備の4つで足りる見込み。自動配置の候補の組み合わせの計算の量を抑える|
|1つのテンプレートの層の合計|20|編集の画面の層の一覧で見渡せる数|
|1つの文字の層の文字数|500|—|

## 5. 画像の層

- 取り込める形式は PNG と JPEG に限る。SVG は取り込まない（中に処理の命令を含み得るため）。
- 取り込みの確かめ：1ファイル20MB まで（初期値）、縦横それぞれ8,000画素まで（初期値）。画像の読み込みは第3章と同じ部品で行い、壊れたファイルは取り込まない。
- 取り込んだ画像は、テンプレートの素材として写して保存し、SHA-256 で参照する（元のファイルが消えても描ける）。
- 塗り替え：画像の透過をそのまま使い、色を白・黒・任意の色・自動（背景に合わせて白か黒。文字の色の「自動」と同じ規則（3.2）であり、まとまりの枠で見るため同じまとまりの文字とロゴは同じ色になる）に塗り替えられる。単色のロゴを背景に合わせて白と黒で使い分けるため（設計計画書 3.3.1「利用者の例」）。
- 大きさ・回転・不透明度は文字の層と同じ扱いとする。
- 利用者が取り込む画像の権利は利用者の責任であり、取り込む時に一度その旨を示す（法務調査 L-19「フォントのライセンス」と同じ扱い）。

## 6. フォントと絵文字

### 6.1 同梱のフォント

|フォント|用途|ライセンス|大きさ|かな|日本の漢字（JIS 第1・第2水準）|簡体字（通用规范汉字表 8,105字）|縦書き|
|---|---|---|---|---|---|---|---|
|Caveat|英字の手書き風|OFL 1.1|298KB|なし|なし|なし|なし|
|Klee One|日本語の手書き風（教科書体）|OFL 1.1|8.7MB|全部|全部|4,004字|あり|
|Yomogi|日本語の手書き風|OFL 1.1（派生の名に「よもぎフォント」を使えない）|4.0MB|2字欠け（ゕ、ゖ）|全部|3,507字|あり|
|LXGW WenKai Lite（v1.522、Regular）|中国語（Klee One から派生）|OFL 1.1（予約フォント名あり）|13.9MB|全部|全部|8,105字|あり（vert。vrt2 はない）|

- 出典：各フォントの配布元（検討メモ「第4章 画像編集と一括適用の検討」）。大きさと収録字は2026-09-29に配布物を実測した値。
- 改変しない：字を減らす等の改変をすると、LXGW WenKai は予約フォント名を使えず名前を変えなければならない。そのまま同梱する。
- LXGW WenKai は、作者が配る Lite 版（LXGW WenKai Lite v1.522 の Regular、13.9MB）を採る。完全版（25.6MB）との違いは収める字の数であり、Lite 版は通用规范汉字表の8,105字（一級3,500字、二級3,000字、三級1,605字）をすべて収め、縦書きの字形の切り替え（vert）も持つ（2026-09-30 に配布物の字の表と GSUB の機能の一覧を読み、公開の字表の一覧と照らして確かめた）。Lite 版は作者自身の配布物であり、本システムが字を減らす改変ではないため、予約フォント名の制約に触れない。
- ライセンスの文書は同梱し、第三者のライセンスの一覧（第11章 DD-11-9「ライセンスの一覧を自動で同梱する」）に載せる。

### 6.2 代わりのフォントの並び

- 文字の層ごとに、主のフォントと代わりのフォントの並びを持つ。既定の並び（初期値）：

|書く向き|並び|
|---|---|
|横書き|Caveat、Klee One、LXGW WenKai Lite、Noto Color Emoji|
|縦書き|Klee One、LXGW WenKai Lite、Noto Color Emoji（英字は Caveat を90度回して描く）|

- 中国語の文を主にする層は、主のフォントを LXGW WenKai Lite にする（Klee One の字形は日本の字形であり、簡体字の半分ほどしか持たない）。画面の言語が中国語の場合の既定の並びは LXGW WenKai を先頭にする。

### 6.3 絵文字

- Google Fonts が配る Noto Color Emoji（`NotoColorEmoji-Regular.ttf`、25.3MB、OFL 1.1）を同梱する。この版は COLRv1（ベクターの色つきの字形。表の `COLR` の版1、`CPAL`）と `SVG` の表を持ち、ビットマップ（`CBDT`）を持たない（2026-09-30 に配布物を取得し、表の一覧を読んで確かめた）。ベクターのため、大きく描いてもぼやけない。
- 第2稿の「ビットマップのため大きく描くとぼやける」は、ビットマップの版（noto-emoji の配布の別の版）を前提としていたため改めた。
- ［要実測］COLRv1 の塗りの種類（単色、線形・円形・扇形のグラデーション、変形、合成）を skrifa と tiny-skia ですべて描けること。判定：絵文字の全字を描き、ブラウザ（Chrome）の描画と見比べて形と色が同じこと。描けない塗りがある字は、その字を描かずに「描けない字」の印を付ける（3.4 の足りない字と同じ扱い）。

### 6.4 持ち込みのフォント

- TTF・OTF を取り込める。1ファイル50MB まで（初期値）。読み込めないファイルは取り込まない。
- 取り込んだフォントはアプリのデータの場所に写して保存し（第8章 2.1「配置」）、テンプレートと作業からは名前（フォントのファミリー名）と SHA-256 で参照する。自分の別の端末へは同期（第8章 5.4。素材は iroh-blobs で運ぶ）か控えのファイルで移る。参照するフォントが無い端末では既定の並び（6.2）で描き、層に「フォントが無い」の印を付ける（12.2 の「要手直し」）。
- ライセンスは利用者の責任であり、取り込む時に一度その旨を示す（第1稿の方針を引き継ぐ）。

## 7. 置き方

### 7.1 位置と大きさ

- まとまりの位置は、9点の基準点（左上、上中央、右上、左中央、中央、右中央、左下、下中央、右下）と、基準点から写真の内側への余白（横・縦。写真の短辺に対する割合）で持つ。
- 既定の余白は写真の短辺の3%（初期値）。
- まとまりの大きさは、中の層の大きさ（写真の短辺に対する割合）で決まる。写真の画素数・縦横比が違っても、同じ割合で描く。

### 7.2 自動配置

- 対象：テンプレートで「自動配置の対象」にしたまとまり。
- 手順：

  1. 写真を320×320画素に縮め（縦横比は保たない）、u2netp で目立つ領域の確率の地図（0〜1）を求める。前処理は u2netp の公式の前処理に合わせる（LANCZOS で縮め、平均 (0.485, 0.456, 0.406)・標準偏差 (0.229, 0.224, 0.225) で正規化。U-2-Net の u2net_test.py、rembg の u2netp の処理）。

  2. 確率の地図を写真の縦横比に戻す。

  3. まとまりごとに、候補の位置（9点の基準点に既定の余白を足した位置。縦書きのまとまりは、左右の辺に沿った高さ1/4と3/4の位置（左右で4か所）も加える）で、まとまりの枠の中の確率の合計を計算する。

  4. まとまりが複数あれば、互いに重ならない候補の組み合わせのうち、確率の合計の和が最小のものを選ぶ（まとまりは4まで、候補は最大13か所（9点と縦書きの4か所）であり、組み合わせは総当たりで計算する）。

  5. 同じ値なら、テンプレートで決めた基準点に近い候補を選ぶ。

- 文字の色の「自動」と読みやすさの確かめは 3.2「書式」による。
- 部品：u2netp（Apache-2.0、約4.6MB）を ONNX に変換し、ONNX ランタイム（ort）で動かす（第11章 4.1「Rust の部品」の ort）。公式の ONNX の配布はない。
- ［要実測］500枚の自動配置の時間。判定：第1章 14.1「規模と性能の目安」の PCで1分以内。
- ［要実測］コスプレ写真（背景の多い全身、背景の少ない顔寄り）での当たりの率。判定：利用者の試行で、7割以上の写真で手直しが要らないこと。

### 7.3 収まらない場合

- まとまりが写真の短辺の40%（初期値）を超える場合は、まとまり全体を縮めて収める。
- 字の大きさが写真の短辺の1.5%（初期値）より小さくなる場合は、縮めず、その写真を「要手直し」とする。
- 第1稿の「行を減らす」は採らない。利用者の書いた行を勝手に消すと、意図しないクレジットになるため。

### 7.4 敷き詰め

- まとまりの置き方として、9点の基準点に置く「1か所」のほかに、まとまりを写真の全体に繰り返して置く「敷き詰め」を選べる。同種の道具（watermarkly 等）は、1か所に置く方式と並べて、縦横または斜めに繰り返す方式を持つ。切り抜きで消しにくく、販売の見本の画像に使われる（watermarkly の「Tile mode」の案内等）。

|項目|範囲|既定（初期値）|
|---|---|---|
|並べ方|縦横、斜め（市松）|斜め|
|角度|−45°〜45°|−30°|
|間隔（横・縦）|写真の短辺に対する割合 10%〜60%|25%|
|不透明度|10%〜100%|20%|

- 敷き詰めのまとまりは自動配置の対象にしない（7.2）。写真の端で切れる繰り返しも描く。
- 敷き詰めは写真の見え方を大きく損なうため、テンプレートの既定の置き方は「1か所」とし、敷き詰めは利用者が選んだ場合のみとする。
- 描く時は、繰り返しの1つ分を一度だけ描いて、その画素を写真の範囲に並べる（まとまりを繰り返し組み立てない。9.4「プレビュー」の時間に響かせない）。

## 8. テンプレート

### 8.1 管理

|操作|内容|
|---|---|
|新しく作る|空から、または既定のテンプレートから作る|
|写して作る|既にあるテンプレートを写す|
|名前を変える|—|
|消す|消しても、そのテンプレートから作った作業は自分の写しを持つため影響しない（DD-4-10「作業はテンプレートの写しを持つ」）。その旨を示してから消す|
|並べ替え|一覧の順を変える|
|書き出す・取り込む|8.3|

- 数の上限はない。一覧は最近使った順に並べる。

### 8.2 版

- テンプレートは保存のたびに版の番号を1つ上げる。
- 作業は、どのテンプレートのどの版を写したかを持つ（15.2）。元のテンプレートの版が新しくなれば、作業の画面で「テンプレートに新しい版があります」と示し、「取り込む」を押した時だけ取り込む。取り込みは取り消せる（10）。
- テンプレートの編集中の変更は下書きとして自動で保存し（11.3 と同じ方法）、「保存」で確定して版を上げる。確定するまで、他の作業の「新しい版」には出ない。
- 別の端末・控えとの揃え（第8章 5.3・5.4 から呼ばれる）：番号が同じテンプレート・作業は、端末の番号と単調な番号（テンプレートは版、作業は保存の連番）で新しい方を採り、古い方を版の控え（11.4）に残す。両方が変わっていれば両方を残して示す。

### 8.3 受け渡し（書き出しと取り込み）

- テンプレートを1つのファイルにして相手に渡せる（撮影者とコスプレイヤーが同じ型を使うため）。
- ファイルの中身：テンプレートの JSON（15.1）と、画像の層の画像。形式は ZIP とし、拡張子は `.nrsdtpl`、名前は `<テンプレートの名前の安全な形>-<id の先頭8文字>.nrsdtpl` とする。
- 同梱のフォントは入れない（相手のアプリにもある）。利用者が持ち込んだフォントは既定で入れない。入れる場合は、ライセンスが再配布を許すことを利用者が確かめる旨を示す。
- 取り込みの確かめ：ZIP の共通の確かめ（第1章 10.2「保存」）に加え、中のファイルの数（50まで）、合計の大きさ（100MB まで）、ファイル名（決まった名前のみ）、JSON の形式（15.1 の形に合わないものは取り込まない）、画像は 5 の確かめを行う。いずれも初期値。
- 差し込みは相手の署名の情報で描かれる（ハンドルネーム等は相手のものになる）。
- 同じ `id` のテンプレートの取り込み：版が同じか古ければ取り込まない（既にある）。版が新しければ新しい版として取り込む（8.2 の「新しい版があります」と同じ扱い）。版が同じで中身が違えば、新しい `id` で「〈名前〉（取り込み）」として取り込み、両方を残す（第8章 5.4 のテンプレートの規則と同じ）。
- 確認済みの相手（第2章 5.5）には `.nrsdtpl` を直接送れる。受け取る側は上の取り込みの確かめを通る。形式は変えない（Lightroom のプリセットのファイルの共有と同じ）（2026-10-01 NRSD の要求）。

### 8.4 既定のテンプレート

|名前|まとまりと層|
|---|---|
|名前だけ|右下：`{handle}`|
|撮影とコスプレイヤー|右下：`{handle}` の行と、`{coholder_role}：{coholder}` の行|
|名前と無断転載禁止|右下：`{handle}`。左上：「無断転載禁止 / Do not repost / 禁止转载」|

- 識別番号を描き込むかは利用者が選ぶ。既定のテンプレートには入れず、差し込みの一覧から `{work_id}` を加えられるようにする。第1稿の「識別番号を既定で入れる」は改める。
- 見た目（フォント・色）は第10章 2「デザイン」の方向に合わせ、担当開発者が仕上げる（第10章 DD-10-2「デザインは NRSD の担当開発者が行い、自ら判定する」）。

|表示を動かす|スペースキーを押しながらドラッグ|
|前後の比較|可視署名のある表示とない表示を、キー（\。日本語の配列の Mac では Option と ¥ で入る）を押す間、または画面の「前後を比べる」のボタンを押す間だけ切り替える|
|見本の写真を替える|テンプレートの編集では、明るい写真、暗い写真、縦長、横長の見本（利用者が選んだ自分の写真）に替えて見え方を確かめる。見本の写真の場所は、テンプレートとは別の端末の設定（`templates/<番号>/local.json`）に置き、テンプレートの受け渡しのファイル（`.nrsdtpl`。8.3）には入れない（写真の場所のパスに利用者の名前が入ることがあるため）|

### 9.3 キーの割り当ての一覧

|操作|Windows・Linux|macOS|
|---|---|---|
|取り消し|Ctrl+Z|Command+Z|
|やり直し|Ctrl+Shift+Z、Ctrl+Y|Command+Shift+Z|
|保存（名前を付けて確定）|Ctrl+S|Command+S|
|写す・貼る|Ctrl+C・Ctrl+V|Command+C・Command+V|
|複製|Ctrl+D|Command+D|
|全部を選ぶ|Ctrl+A|Command+A|
|選択を外す|Esc|Esc|

- 各 OS の慣習に合わせた。画面の文字の入力中（文字の層の中身の編集中）は、文字の入力のキーを優先する。

### 9.4 プレビュー

- 写真は、画面の大きさに合わせて縮めたプレビューの画像（14.3「縮小・色の変換・JPEG の書き出し」）として1度だけ画面に送り、画面に表示する。Windows の WebView2 と macOS の WKWebView は sRGB の画像を画面の色の設定に合わせて表示する。Linux の WebKitGTK は画面の色の設定を反映せず sRGB のまま出す（WebKit の不具合 177185 の修正の記録）ため、広い色域の画面では写真の色が正しく見えない（第13章 H-48「Linux では、プレビューの写真の色が画面の色の設定を反映しない」）。このため Linux では、画面の ICC を取り（14.3）、プレビューの画像を sRGB でなく画面の色空間に変換して送る（2026-10-01 NRSD の要求）。
- 拡大が縮めた画像の倍率を超えた場合（等倍の表示を含む）は、見えている範囲だけを原寸の写真から切り出し、可視署名とともに描き直して送る。細い縁取りは等倍で確かめられる。
- 可視署名は、まとまりごとに、まとまりの枠の大きさだけの透過の画像を Rust で描き（DD-4-5「文字の組み立てと描画はプレビューも書き出しも同じ Rust の仕組みで行う」）、画面に送る。送る方法は Tauri の2進のデータの返し方（`tauri::ipc::Response`）とする。画面は写真の上にこの画像を重ねる。
- ドラッグ・矢印キーで動かす間は、送った画像を画面の上で動かすだけで描き直さない。大きさ・回転・書式・中身を変えた時に描き直す。
- ［要実測］まとまり1つを描いて画面に出すまでの時間。判定：100ms 以内（初期値）。
- プレビューと書き出しの一致：同じ描画の仕組みで描くため、プレビューの倍率で見た見た目と書き出しの見た目は一致する。細い縁取りは等倍の表示（Ctrl+1。原寸から描き直す）で確かめる。

- 上のキーは OS が予約するキー（Alt+F4、Command+Q・W・H・M・Tab、Alt+Tab、Super）と重ならない。WebView の組み込みの加速キー（F5・Ctrl+R の再読み込み、F12・Ctrl+Shift+I、Ctrl+F・F3、Ctrl+P、Ctrl+U、Ctrl+＋・−）は Windows で WebView2 の `AreBrowserAcceleratorKeysEnabled` を偽にし、3つの OS で tauri-plugin-prevent-default で止める。macOS の Command+W は窓を閉じる操作として受け、「閉じる時」の保存と更新（第9章 4.1）を通す。

## 10. 取り消しとやり直し

### 10.1 履歴の単位

- 作業ごとに1本の履歴を持つ（DD-4-9「取り消しとやり直しは作業ごとの履歴で行う」）。写真をまたいで順に戻る。
- テンプレートの編集（画像編集の画面の「テンプレートを直す」の状態。13.1）は、テンプレートごとに別の履歴を持つ。画像編集の画面の「作業を直す」の状態では、その作業の履歴を使う（一括適用の画面と同じ1本の履歴）。

### 10.2 1段の決め方

|操作|1段の単位|
|---|---|
|ドラッグ（動かす、大きさ、回転）|マウスを離した時点で1段|
|矢印キーで動かす|キーを離してから1秒（初期値）で1段にまとめる|
|文字の中身の入力|入力が止まってから1秒（初期値）で1段|
|書式の変更（スライダー）|スライダーを離した時点で1段|
|一括の操作（全部を自動で置き直す、選んだ写真に当てる）|操作全体で1段|
|テンプレートの新しい版の取り込み|1段|

### 10.3 履歴の中身

- 各段は、変更の前後の差分（JSON の差分の形式。RFC 6902 の JSON Patch）、時刻、「何を・どの写真に」の説明の文（例：「写真 IMG_0123：クレジットを右下から左下へ」）を持つ。
- 取り消しは前への差分を、やり直しは後への差分を当てる。取り消した後に新しい操作をすると、やり直しの分は消える。

### 10.4 段の数と記憶

- 既定は200段（初期値）。Photoshop の既定は50段、上限は1,000段であり、GIMP は最少の段数と記憶の上限を持つ。本アプリの1段は差分の文書（画素を含まない）で小さく、数十枚の手直しを越えて戻せるよう、Photoshop の既定より多くする。
- 設定で50〜1,000段を選べる。段数を超えたら古い段から消す。

### 10.5 履歴の一覧

- 編集の画面に履歴の一覧を置き、各段の説明の文を新しい順に並べる。段を押すと、その時点まで戻る（その間の段は取り消した状態になる）。

### 10.6 保存

- 履歴は作業とともに保存し（11）、作業を開き直しても取り消せる。

## 11. 作業（編集の途中の状態）

### 11.1 作業の単位

- 書き出しの1回（第10章 G-08「書き出し：写真と用途」で写真を選んでから、G-11「書き出し：実行と結果」で書き出すまで）を1つの作業とする。
- 画像編集の画面（第10章 G-25「画像編集」）で写真1枚を開いて描き込む場合も、1つの作業とする。
- 作業は何個でも持てる。ホーム（第10章 G-07「ホーム」）の「途中の作業」に最近の順で並べる。

### 11.2 作業の中身

- 作業の名前、作った日時、最後に直した日時。
- テンプレートの写し（どのテンプレートのどの版か。DD-4-10「作業はテンプレートの写しを持つ」）。
- 写真の一覧（15.2）。
- 写真ごとの手直し（まとまりの基準点・余白・大きさ・回転、層の表示・色、その写真だけの層）と状態（12.2）。
- 書き出しの型（複数。14.1）と、型ごとの書き出しの済み・未の記録。ファイル名に識別番号を付けるか（15.2 の `id_in_filename`）。
- 許可範囲の選択（第5章）、共同の権利者の選択。
- 今の段（写真の選択、一括適用、許可範囲、書き出し）。
- 取り消しの履歴（10）。
- 参照情報の版と、使う文言のファイルの写し（第5章 4）（2026-09-30 NRSD の要求）。
- 写真は複製しない。写真の場所、SHA-256、大きさ、変更の日時、縦横の画素を記録する。

### 11.3 保存の方法

- 自動の保存：変更のたびに、操作が止まってから2秒（初期値）で保存する。画面を移る時、アプリを閉じる時にも保存する。Photoshop の自動の復旧は既定10分であるが、作業のファイルは画素を含まず小さいため、2秒ごとに保存しても負担にならない。
- 画面の上端に「保存済み」と保存の時刻を示す。保存に失敗したら、上端を注意の色にし、理由を示す。
- 利用者が「保存」を押した場合は、作業に名前を付けて確定する（自動の保存と中身は同じ）。
- 作業の持ち方：`work.json`（ヘッダ：名前、日時、テンプレートの写し、型、段、参照情報の写し、共同の権利者、許可範囲）、`photos/<写真の番号>.json`（写真ごとの記録：場所、SHA-256、大きさ、状態、手直し、書き出しの済み）、`history.log`（追記のみの履歴。1段1行）、`snapshot.json`（一覧の索引。無ければ作り直せる）に分け、自動の保存は変わった写真のファイルと履歴の追記だけを書く（書く量は変更の量に比例し、写真の数に比例しない）。一覧の読み込みは索引だけを読み、写真ごとの記録は格子に見えた時に読む（2026-09-30 NRSD の要求）。
- `history.log` の行が段数の上限（10.4）の2倍を超えたら、作業を開く時に上限の分だけを残して書き直す（一時のファイルと置き換え）。
- 書き込みは第1章 10.2「保存」の手順（一時のファイルと置き換え）による。

### 11.4 版の控え

- 保存のたびに、直前の版を控えとして残す。控えは5つ（初期値）まで残し、古いものから消す。
- 作業を開く時に作業のファイルが壊れていれば（JSON として読めない、形式に合わない）、知らせて、新しい控えから順に開ける版で開く。

### 11.5 異常終了の後

- アプリが正しく閉じられたかは、起動の時に使用中の印（第8章 2.1「配置」の `state/running`）で確かめる（第1章 7.8「異常終了の後の起動」）。
- 前回が正しく閉じられていなければ、起動の時にホーム（第10章 G-07「ホーム」）の上端に「前回は正しく終わりませんでした」の知らせを出し、最後に保存した作業と、確定していないテンプレートの下書き（8.2）を並べて「続きから開く」を示す（第10章 3.7「知らせの一覧」）。自動の保存が2秒ごとのため、失うのは最後の2秒の操作までである。

### 11.6 写真の差し替え・移動

|事象|判定|扱い|
|---|---|---|
|写真が記録の場所にない|—|作業を開く時に知らせ、場所を選び直してもらう。SHA-256 が一致するものだけ受け付ける。フォルダーを選べば、中の写真を SHA-256 でまとめて探す|
|写真の中身が変わった（現像し直した）|SHA-256 が違う|縦横の画素が同じなら、手直しを保ったまま使い、SHA-256 を更新する。違う場合は、手直しの位置が割合で持つため使えるが、「位置を見直す」の印を付ける|
|写真が消えた|—|その写真を作業から除けるようにする（手直しの記録は消す）|

### 11.7 同時に開く

- アプリは1台で1つだけ起動する（第1章 DD-1-11「アプリは1台で1つだけ起動する」）。使用中の印は、それが働かなかった場合の備えとする。
- 作業ごとの使用中の印は、作業のフォルダーの `lock`（第1章 10.2「保存」のフォルダーの使用中の印）。
- 2つ目のアプリで同じ作業を開くと、読むだけで開き、その旨を示す。
- 鍵が取れれば（持ち主が終わっていれば）そのまま開く。

### 11.8 置き場

- アプリのデータの場所の `sessions/<作業の番号>/`（第8章 2.1「配置」）。

|ファイル|中身|
|---|---|
|`work.json`|作業のヘッダ（15.2、11.3）|
|`photos/<写真の番号>.json`|写真ごとの記録（11.3）|
|`history.log`|追記のみの履歴（10、11.3）|
|`snapshot.json`|一覧の索引（作り直せる。11.3）|
|`versions/`|控え（11.4）|
|`lock`|使用中の印（11.7）|

- 写真の縮小の画像は、作り直せるため OS のキャッシュの場所（第1章 9.1「OS ごとの置き場所」）に置き、控えのファイルに含めない。名前は写真の SHA-256 とし、作業をまたいで共有する（2026-09-30 NRSD の要求）。
- 写真のフォルダーには何も書かない。
- 作業は控えのファイル（第8章 5「控えのファイル」）に含む。

### 11.9 書き出しの後

- 書き出しを終えた作業は「書き出し済み」として残し、開き直して、直した版を書き出せる。直した版の出力は新しい識別番号を持つ（第3章 7.1「識別番号」）。
- 作業は利用者が消すまで消さない。

## 12. 一括適用

### 12.1 流れ

1. 写真（フォルダー、または複数の写真）とテンプレートを選ぶ（第10章 G-08「書き出し：写真と用途」）。
2. 写真の縮小の画像（14.3「縮小・色の変換・JPEG の書き出し」）を作り、全部の写真に自動配置（7.2）を行う。
3. 写真の一覧（格子）に、可視署名を重ねた縮小の画像と状態（12.2）を示す（第10章 G-09「書き出し：一括適用」）。
4. 直したい写真を開いて手直しする（9 の操作）。複数の写真を選んでまとめて直せる（12.3）。
5. 許可範囲（受け渡し用のみ。第5章）を選び、書き出す（14）。
- 途中でやめても作業は保存されている（11）。

### 12.2 写真の状態

|状態|意味|付く時|
|---|---|---|
|自動|自動配置のまま|自動配置の後|
|手直し済み|利用者が直した|手直しの後|
|要手直し|収まらない、字がない、読みにくい|7.3、3.4、7.2 の確かめ|
|位置を見直す|写真が差し替わった|11.6|
|読めない|写真を読めない|読み込みの失敗|

- 状態で絞り込んで表示できる。「要手直し」の写真が残っていれば、書き出しの前に知らせる（書き出しは止めない。利用者が選ぶ）。
- 状態の移り：「自動」は自動配置の直後。手直しで「手直し済み」、7.3・3.4・7.2 の確かめに当たれば「要手直し」（手直しで解けば「手直し済み」）。写真の差し替えで縦横が変われば「位置を見直す」（手直しで「手直し済み」）。読めなければ「読めない」（差し替えて読めれば「自動」に戻し、置き直す）。テンプレートの新しい版を取り込んだ写真は「自動」に戻る（手直しは残す）。書き出しの済みは状態と別に型ごとに持つ（11.2）。

### 12.3 まとめての手直し

|操作|内容|
|---|---|
|基準点を変える|選んだ写真のまとまりの基準点を一度に変える|
|層を隠す・出す|選んだ写真で、ある層を隠す・出す|
|色を変える|選んだ写真で、層の色を変える（自動・白・黒・任意）|
|自動で置き直す|選んだ写真（または全部）を自動配置し直す。手直しは消えるため、確かめてから行う|
|手直しを消す|選んだ写真をテンプレートのままに戻す|

- それぞれ履歴の1段になる（10.2）。

### 12.4 大量の写真

- 縮小の画像の置き場は 11.8「置き場」による。次に開く時は作り直さない（消えていれば作り直す）。
- 格子は見えている分だけ描く（第10章 3.4「大量の一覧の表示」）。
- 枚数の上限を設けない（第3章 9）。
- ［要実測］500枚の縮小の画像の作成と自動配置の時間（7.2 と合わせて）。

### 14.1 書き出しの型

|自分で決める|長辺を指定、または原寸|JPEG・PNG|—|—|

- 1つの作業に複数の型を持てる（DD-4-11「書き出しは投稿先ごとの型から選ぶ」）。型ごとに書き出しの済み・未を記録する。
- 長辺2048画素を SNS の既定とする理由：原寸を SNS に出すと、販売の画像（原寸）の代わりになる（企画草案第1節：写真は権利者の収入源）。2048は表示に足りると判断した初期値であり、公式の根拠はない。X の4096画素の上限は公式の記載を確認できなかった。
- ［要実測］各投稿先に実際に上げて、表示の大きさと再圧縮の有無を確かめる。

### 14.2 処理

- 処理の順序は第3章 8「処理の順序と系統」に従う。本章が受け持つのは、可視署名の描き込み、縮小、色空間の変換である。縮小・色空間の変換・8ビットへの変換は SNS 用の書き出しだけで行い、受け渡し用は原寸・元の色空間・元のビット数を保つ（第3章 8.2「系統の差」、8.5「受け渡し用の書き出しの品質」）。
- 縮小と色の変換の方法は 14.3「縮小・色の変換・JPEG の書き出し」による。
- 可視署名は、縮小の後の画像に、その大きさで描く（縮小の前に描いて縮めると、細い縁取りがつぶれるため）。描いた透過の画像を写真に重ねる時の色空間とビット数の扱いは 3.5「描画」による。

### 14.3 縮小・色の変換・JPEG の書き出し

- 縮小：fast_image_resize の Lanczos3。透過のある画像は透過を掛けてから縮め、戻す（fast_image_resize の既定）。
- 色（SNS 用）：元の画像の埋め込みの ICC（ISO 15076-1。v2・v4）から sRGB（IEC 61966-2-1）に変換する（DD-4-12「色は sRGB に変換し、sRGB の ICC を埋め込む」）。変換は moxcms で行う。ICC がない画像は sRGB とみなす。［要実測］Adobe RGB・Display P3 の試験の画像で、moxcms と lcms2 の変換の差。判定：色差（ΔE2000）の最大が1未満。満たさない場合は lcms2 を使う。
- 16ビットの画像（SNS 用）は16ビットのまま縮め、描き込みの後に8ビットにする。
- プレビューの画像：JPEG、品質85、長辺2560画素まで（初期値）。写真の ICC から sRGB に変換する（画面の部品の色の扱いの違いを避ける）。画面の ICC が渡された時（Linux。9.4「プレビュー」）はその色空間に変換する（moxcms。darktable・GIMP・Krita と同じ経路）。
- 画面の ICC の取得（Linux）：Wayland は色管理の規約 `wp_color_management_v1` の出力の ICC、X11 は root の `_ICC_PROFILE` 属性（ICC Profiles In X Specification）、どちらも無ければ colord に問い合わせる。無ければ sRGB のまま（2026-10-01 NRSD の要求）。
- 縮小の画像：短辺512画素（初期値）。名前は写真の SHA-256。置き場は呼ぶ側が渡す（11.8「置き場」）。
- 危険：moxcms の色の正確さ。影響：色がずれる。備え：lcms2 と比べ、`ColorEngine` の切り替えで差し替える（14.3、全体実装設計書 2.1）
- 部品：jpeg-encoder（品質、色の間引き、段階表示、ICC の埋め込みを持つ）。image の JPEG の書き出しは色の間引きと段階表示を選べないため使わない。
- 品質92（初期値）、色の間引きなし（4:4:4）、段階表示あり。SNS は受け取った画像を再圧縮するため、書き出しの段階で色を間引いて劣化を重ねない。
- sRGB の ICC を埋め込む。

### 14.4 大きな画像と並行の処理

- 扱う写真は1億画素・1枚200MB まで（第1章 14.1「規模と性能の目安」）。これを超える写真は取り込まない。1枚の記憶の見積もりと読み込みの上限は第3章 2「入力」による。
- 同時に処理する枚数は、「CPU の論理コアの数」と「空いている記憶の半分を1枚あたりの見積もり（縦×横×1画素のバイト数×3。1画素のバイト数は8ビットの RGBA で4、16ビットの RGBA で8。読み込み、縮小、描き込みの3つの画像）で割った数」の小さい方とする。最低1。
- 透かしと自動配置のモデルは同時に持たず、使う方だけを読み、記憶の使用量を操作の記録に残す（第3章 5、第11章 7.1）。

### 14.5 置き場と名前

- 置き場：利用者が選ぶフォルダーの下に、第3章 10.1「名前と構成」のフォルダーを作る。
- 名前：第3章 10.1「名前と構成」による。同じ名前のファイルがあれば上書きせず、名前の後ろに番号を付ける。
- 書きかけのファイルは一時の名前で書き、完了で名前を変える。途中で止まっても書きかけのファイルは残さない。
- 原本と同じフォルダーは書き出し先に選べない（原本の上書きの事故を防ぐ）。
- 書き出しの前に、書き出し先の空きの容量を見積もり（1枚あたりの見積もりの大きさ×枚数）、足りなければ始めない。

### 14.6 中断と再開

- 書き出しの途中でアプリが終わった場合、書き出し済みの写真は作業に記録されている。作業を開き、「続きから書き出す」で残りだけを書き出す。
- 中断・再開はアプリや OS の再起動をまたいでも同じ（写真ごとの記録に済みが残る）。書き出しは待ち行列で複数を予約でき、動くのは1つ（第3章 9）（2026-09-30 NRSD の要求）。

## 15. データの形式

### 15.1 テンプレート（`schema: nrsd.template/2`）

|項目|型|内容|
|---|---|---|
|`id`|文字列（UUID v7）|テンプレートの番号|
|`name`|文字列|名前|
|`version`|整数|版の番号（8.2）|
|`created_at`、`updated_at`|日時（RFC 3339）|—|
|`delivery_too`|真偽|受け渡し用にも描き込むか（2）|
|`blocks`|まとまりの並び|まとまり（下の表）|
|`assets`|素材の並び|画像の層の画像と持ち込みのフォントの SHA-256 と種類|

まとまり：

|項目|型|内容|
|---|---|---|
|`id`、`name`|文字列|—|
|`anchor`|9点のいずれか|基準点（7.1）|
|`inset`|2つの数（割合）|基準点からの余白|
|`rotation`|数（度）|—|
|`auto_place`|真偽|自動配置の対象か|
|`placement`|`single`・`tile`|置き方（7.4「敷き詰め」）|
|`tile`|並べ方（`grid`・`diagonal`）、角度、間隔（2つの数。割合）、不透明度|`placement` が `tile` の場合のみ|
|`layers`|層の並び|手前から奥の順|

層（共通）：`id`、`name`、`kind`（`text`・`image`）、`visible`、`locked`、`opacity`、`offset`（まとまりの中の位置。割合）、`rotation`。

文字の層：`content`（差し込みを含む文字）、`style`（3.2 の書式の各項目）、`date_format`。

画像の層：`asset`（SHA-256）、`width`（割合）、`recolor`（なし・白・黒・色・自動）。

値の形：`anchor` は `top-left`・`top`・`top-right`・`left`・`center`・`right`・`bottom-left`・`bottom`・`bottom-right`。割合は 0〜1 の数。色は `#RRGGBB`（不透明度は別の項目）または `auto`。`date_format` は `iso`（2026-09-29）・`ja`（2026年9月29日）・`en`（Sep 29, 2026）。フォントの参照は `{name, sha256}`（同梱は `sha256` を省く）。`kind` は `text`・`image`。`placement` は `single`・`tile`、`tile.pattern` は `grid`・`diagonal`。JSON Schema（第1章 8.3）はこの列挙で書く。

### 15.2 作業（`schema: nrsd.session/1`）

|項目|型|内容|
|---|---|---|
|`id`|文字列（UUID v7）|作業の番号|
|`name`|文字列|作業の名前|
|`created_at`、`updated_at`|日時|—|
|`stage`|段|今の段（11.2）|
|`template`|テンプレート|写し（15.1 の形のまま）と、元の `id` と `version`|
|`photos`|写真の並び|`path`、`sha256`、`bytes`、`mtime`、`width`、`height`、`status`（12.2）、`overrides`（まとまりごとの `anchor`・`inset`・`scale`・`rotation`、層ごとの `visible`・`color`、`extra_layers`）、`exports`（型ごとの書き出しの記録）|
|`export_presets`|型の並び|14.1 の型と、利用者の変更|
|`id_in_filename`|真偽|SNS 用の出力のファイル名に識別番号を付けるか（第3章 7.1「識別番号」。初期値は設定 `export.id_in_filename`（第10章 10）、以後は前回の選択）|
|`rights`|許可範囲の選択|第5章|
|`coholder`|共同の権利者の選択（作業ごとに1人、または無し）|第2章 5「承認と共同の権利」、第10章 G-08「書き出し：写真と用途」|
|`history`|履歴|段の並び（10.3）と今の位置|

- 15.2 の項目は 11.3 の分け方（ヘッダ、写真ごとの記録、履歴、索引）で持つ。`photos` は写真ごとのファイル、`history` は追記の記録である。
- 形式の版（`schema`）が上がった場合、古い形式の作業は開く時に新しい形式に移す。移す前の作業は控え（11.4）に残す。

## 16. 失敗の扱い

|事象|知らせ方|利用者がすること|作業の状態|
|---|---|---|---|
|写真が読めない（壊れている、対応しない形式）|格子に「読めない」と理由|除くか、差し替える|他の写真は続けられる|
|字がどのフォントにもない|編集の画面で、その字に印。書き出しの前に一覧|フォントを変える、または字を変える|書き出しの前に確かめを求める|
|可視署名が収まらない|格子に「要手直し」|大きさ・余白・行を直す|—|
|背景と文字の区別がつきにくい|格子に「読みにくい」（縁取りは自動で付く）|色・縁取り・背景の板を直す|—|
|書き出し先の空きが足りない|書き出しの前に見積もりを示し、始めない|空きを作る、別の場所を選ぶ|—|
|書き出しの途中の失敗|失敗した写真と理由の一覧（第10章 DD-10-8「エラーの表示の型をそろえる」 の型）|直して「続きから書き出す」|書き出し済みは記録済み|
|容量の上限を超える（X の5MB 等）|品質を下げても収まらない写真の一覧|大きさを下げる|—|
|作業のファイルが壊れた|開く時に知らせる|控えの版で開く|—|
|写真が見つからない|作業を開く時に知らせる|場所を選び直す|—|
|作業の保存に失敗（空きがない、書き込めない）|画面の上端を注意の色にし、理由を示す|空きを作る|次の保存で再び試す|
|テンプレート・画像・フォントの取り込みで不正なファイル|取り込まずに理由を示す|—|—|
|同じ作業を2つのアプリで開いた（単一起動（第1章 DD-1-11「アプリは1台で1つだけ起動する」）が働かなかった場合の備え）|2つ目は読むだけで開く旨を示す|—|—|
