## 本書の位置付け

- 概要設計書 第11章を詳細化する。本章は、画面と処理の枠組み、部品（依存）の一覧と方針、リポジトリの構成、ビルドと継続的なビルド（CI）、部品表（SBOM）と出どころの証明、書き方の取り決め、版の付け方、部品の保守が止まった時の備え、NRSD のライセンス（Apache-2.0 に決定）を定める。
- 本章は検討メモ「第11章 開発基盤の検討」（NRSD の内部の検討の記録であり、本書とともには配らない。設計の根拠となる事実は、本書の各節に出典とともに書いた）に基づく。第3稿で、ONNX ランタイムの対応の OS と CPU の下限、ONNX ランタイムの入手、c2pa-rs の暗号の実装の選び方を、調べた事実に合わせて改めた（検討メモの第2巡の節）。
- 受ける決定は次の表のとおりである。設計計画書の決定・要調査・未決の文は第13章 1.2「設計計画書の決定から概要設計書・基本設計への対応」と概要設計書の行き先表による（本章には写さず、番号と項目割りの抜けだけを載せる）。

## 2. 選定の根拠（設計計画書 6.2 の条件）

|条件（設計計画書 6.2「開発基盤」）|Tauri 2 での満たし方|
|---|---|
|3つの OS で動作すること|Windows（WebView2）、macOS（WKWebView）、Linux（webkit2gtk 4.1）で動く（Tauri の公式の前提の案内）|
|見た目を自由に作れること|画面を HTML・CSS で作る（第10章）|
|画像編集を扱いやすいこと|描画は Rust で行い、画面は表示だけを受け持つ（第1章 DD-1-8「画面は表示と入力だけを受け持ち、処理は Rust の中心で行う」、第4章 DD-4-5「文字の組み立てと描画はプレビューも書き出しも同じ Rust の仕組みで行う」）|
|C2PA署名、不可視透かしおよび照合用ハッシュを扱えること|c2pa-rs、trustmark、pdqhash を Rust から直接使う|
|自己更新の仕組みを備え、または組み込めること|Tauri の更新の仕組み（更新の電子署名の検証を無効にできない。第9章）|

- 配布物の大きさの比較（Electron は Chromium と Node.js を同梱し80〜150MB、Tauri は10MB 未満）は第三者の記事によるもので、公式の数値ではない。本システムの配布物の大きさはフォントとモデルで決まる（4.3「素材」）。

|項目|版・内容|
|---|---|
|Rust|安定版を `rust-toolchain.toml` で特定の版に固定し、3か月ごと（初期値）に上げる。c2pa の crate が Rust 1.96.0 以上を求める（c2pa-rs の README）。trustmark は1.88 以上。Windows は MSVC の Rust|

|macOS のビルドの前提|Xcode|

|画面|Node.js の長期の支援の版、Vite、TypeScript、Svelte 5。依存は package-lock で固定|

### 3.1 対応する OS の下限

|OS|下限|CPU|根拠|
|---|---|---|---|
|Windows|Windows 10|x86_64 で x86-64-v3 に対応するもの（AVX2 等を持つもの。Intel は Haswell（2013年）以降の Core 等。ただし2013年以降の Pentium・Celeron の一部は持たない。AMD は Excavator 以降）|TrustMark の Rust 版の対応（調査資料「署名処理の技術要素」第2節）。ort の組み済みの x86_64 の部品は x86-64-v3 を下限とする（ort の2.0.0-rc.11 の案内）|
|macOS|macOS 14 以上（同梱する ONNX ランタイムの `minos` による。2026-09 時点の ONNX ランタイム 1.27.1 は14.0）|Apple の CPU のみ|ONNX ランタイムは1.24 から Intel の macOS 向けの配布をやめた。ort は2.0.0-rc.11 で Intel の macOS をやめ、macOS の下限を13.4 に上げた。ONNX ランタイム 1.27.1 の部品は macOS 14.0 を下限として作られている（ort の案内、onnxruntime の issue、他の利用者の報告）|
|Linux|glibc 2.35 以上（Ubuntu 22.04 以降、Debian 12 以降）、libstdc++ 12 以上|x86_64 で x86-64-v3 に対応するもの|TrustMark の Rust 版の README、ort の案内|

- TrustMark の Rust 版の README は macOS 10.15 以上とするが、依存する ort の案内（macOS の下限を13.4 に上げ、Intel の macOS をやめた）と食い違う。依存する部品の側の案内を採る。
- Intel の CPU の Mac は対象外とする（14「本章で宣言する破れ」）。ONNX ランタイム 1.23 系に留めれば Intel の Mac でも動き得るが、その系は新しい修正を受けないため採らない。
- ［要実測］x86-64-v3 に対応しない CPU の PC でアプリが起動の時に落ちないこと。落ちる前に CPU の対応を確かめ、「この PC の CPU には対応していません」と示す（起動の時に CPU の機能を調べる）。

### 4.4 TrustMark の取り込み

- 事実（2026-09-30 に確かめた）：crates.io の trustmark の最新は 0.2.2（2025-09-17）であり、ort を 2.0.0-rc.8（ONNX ランタイム 1.19.2）に固定する。rc.8 の組み済みの部品の取得先（parcel.pyke.io の 1.19.2）のうち、Windows（x86_64・aarch64）と Intel の macOS の部品は応答しない（404）。Linux と Apple の CPU の macOS の部品は取得できる。Windows は対象の OS であるため、0.2.2 はそのままでは使えない。上流の変更の記録も、0.3.0 の項で「0.2.2 はもう組み立てられない（ort-sys 2.0.0-rc.8 が取得する組み済みの部品が置かれていない）ことの修正」と書く（adobe/trustmark の rust/CHANGELOG.md）。0.3.0 は GitHub の main（rust/Cargo.toml）にのみある。
- 決定：実装を始める時点で crates.io に 0.3.0 以降があれば、それを採る。なければ、TrustMark の Rust の実装（MIT。adobe/trustmark の rust/）の必要な部分（前処理、推論の呼び出し、BCH の符号）を、出典のコミットの番号と MIT の表記を添えて本システムのリポジトリに取り込み、crates.io の最新の ort で動かす。取り込んだ源は本システムの源として CI の検査と審査を受ける。git の直接の参照は使わない（5.2）。
- 理由：0.2.2 は組み済みの部品の取得先がなく、2024年の ONNX ランタイムを自ら作る必要がある。取り込みは MIT が許し、取得元の方針（5.2）の趣旨（審査されない源を持ち込まない）を保つ。crates.io に公開されたら、取り込んだ源を crates.io の版に置き換える。
- 対応する OS の下限（3.1）は、どちらの場合も最新の ort の組み済みの部品による。

- 素材の出典・版・ハッシュ・ライセンスは `assets/manifest.json` に置く（6）。
- 出典：フォントの大きさは第4章の調査の実測。ONNX ランタイムの大きさは microsoft/onnxruntime の issue の報告（版1.18で14MB）。

- 上の表は配布物に入る部品（Rust と画面の依存、同梱の素材）に適用する。配布物に入らない CI・開発の道具（XLIFF の変換の translate-toolkit（GPL-2.0）、veraPDF、reuse 等）は対象の外とし、4.1 に「CI の道具」と明記して持つ。
- cargo-deny のライセンスの確かめで、上の表の外の部品が入ったら CI を止める。AppImage の同梱の部品は cargo-deny の対象の外であり、リリースの時に AppImage の中の共有の部品の一覧とライセンスを部品表とライセンスの一覧に載せる（第9章 6.2「同梱するライセンス表記」）。

### 5.2 取得元と禁止

- 取得元は crates.io と npm の公式の登録に限る。git の直接の参照、個人の配布の場所からの取得は禁じる（cargo-deny の取得元の確かめ）。
- 例外（部品の登録の外から取得するもの。いずれも取得したものの SHA-256 を記録する）：①ONNX ランタイムの組み済みの部品（pyke の配布。ort-sys が版ごとに URL と SHA-256 を持つ。DD-11-14「ONNX ランタイムの部品のハッシュと下限を確かめる」）②TrustMark のモデル（Adobe の配布元。取得の命令はハッシュを確かめないため、SHA-256 を記録してリポジトリに置く。4.3）③AppImage の実行部と linuxdeploy のプラグイン（Tauri のビルドの部品が取得する。版を固定できないため、取得したものの SHA-256 を記録する。第9章 DD-9-8「AppImage の実行部のハッシュを残す」）④TrustMark の Rust の実装の取り込み（4.4。源として取り込む）。
- 同じ部品の複数の版が入ることは警告にとどめる（部品の依存の都合で避けられないことがある）。

### 5.3 脆弱性

- CI で、変更のたびに cargo-deny（脆弱性の勧告）と npm audit を行う。
- 重大（CVSS 7以上。初期値）の脆弱性がある部品が入っていれば、リリースを止める。それより低いものは、次の定期の更新で直す。
- 公表された脆弱性の知らせを受けたら、配布物の SBOM（6）で影響を確かめ、影響があれば修正の版を出す。
- 影響の有無は OASIS CSAF 2.0 の VEX（または CycloneDX の VEX。not_affected・affected・fixed・under_investigation と理由）として公開ページに置き、SBOM と結び、参照情報の包みに入れて G-21「お知らせ」 で知らせる（2026-10-01 NRSD の要求）。

### 5.4 更新

- 月1回（初期値）と、脆弱性の知らせの時に更新する。更新は1つずつ行い、ビルドと主な動作を確かめる。
- 描画・色・透かしの部品（harfrust、tiny-skia、moxcms、trustmark）は、出力が変わり得るため、更新の前後で試験の画像の出力を比べる（第4章 3.5「描画」）。
- 危険：HarfRust、krilla、moxcms 等の部品が若い。影響：版の上げで壊れる。備え：版を固定し、上げる時に試す（第11章）

## 6. 部品表と出どころの証明

- 部品表：リリースごとに CycloneDX の形式の SBOM を作り、配布物に添える。Rust は cargo-cyclonedx（Cargo.lock と cargo metadata から作る）、画面は npm の依存から作る。CycloneDX 1.6 は Ecma の規格である。
- 取り込んだ TrustMark の源（4.4「TrustMark の取り込み」）は Cargo.lock に現れないため、cargo-cyclonedx の部品表、cargo-auditable、cargo audit のどれにも載らない。素材の目録（下）に載せて部品表に自動で加え（名前、出典のコミットの番号、MIT）、上流（adobe/trustmark）の勧告と変更を NRSD が四半期ごとに確かめる。
- 素材の目録：取り込んだ源（TrustMark）と同梱の素材（フォント、モデル、合言葉の一覧、ONNX ランタイムの部品、AppImage の実行部）の出典・版・ハッシュ・ライセンスを、リポジトリの1つの目録（`assets/manifest.json`）に置き、CI がそこから部品表とライセンスの一覧に自動で加える。部品表を手で触らない（2026-09-30 NRSD の要求）。
- リポジトリは REUSE Specification 3.3（FSFE）に準拠する：全ファイルに `SPDX-License-Identifier` と `SPDX-FileCopyrightText` の見出し、画像・フォント・モデルは `REUSE.toml` で示す、`LICENSES/` に SPDX の名前でライセンスの本文、CI で `reuse lint`。素材の目録は `REUSE.toml` に統合する（2026-10-01 NRSD の要求）。
- 実行物への埋め込み：cargo-auditable で依存の一覧を実行物に埋め込む。配布の後でも、cargo audit・trivy 等で実行物から依存を読める。
- 出どころの証明：GitHub の artifact attestations で、配布物が公開リポジトリのどのソースから、どの CI で作られたかの証明を付ける。利用者・専門家は `gh attestation verify` で確かめられる（README に手順を載せる。第9章）。
- u2netp の変換：`tools/models/` に PyTorch → ONNX の変換の手順（`torch.onnx.export`、opset を固定、出典のコミット）を置き、変換したモデルの SHA-256 と出典を素材の目録に載せる。変換は担当開発者が1度行い、CI は同梱のハッシュだけを確かめる。

### 8.3 秘密の扱い

- 秘密ごとの置き場は第1章 8.5「秘密情報の一覧」による（本章には写さない）。CI の秘密に置くのはコード署名の資格（Windows・macOS）、公証の資格、TUF の snapshot・timestamp の鍵、ミラーの `tuf/` にだけ書ける鍵（第8章 3.6）だけで、更新の電子署名の鍵・参照情報の電子署名の鍵・TUF の root・targets の鍵・ミラーの配布物と包みの書き込みの鍵は CI に置かない（DD-11-13、第9章 DD-9-4）。
- CI の秘密は、`v*` のタグを付けた時に動くリリースの CI の環境（GitHub の environment）でのみ使える設定とする。TUF の snapshot・timestamp の鍵だけは、上の表のとおり別の環境 `tuf-online` に置く。タグの作成は所有者に限る（第8章 3.5「GitHub のアカウントとリポジトリの守り」）。
- CI の秘密が漏れる、または CI・GitHub の組織が乗っ取られると、正しくコード署名された偽の配布物を作られ得る（第8章 3.5 の脅威 T-22「CI・GitHub の組織を奪って、正しくコード署名された偽の配布物を公式のリリースに置く」、第13章 H-44「CI・GitHub の組織が乗っ取られると、正しくコード署名された偽の配布物を公式のリリースに置かれ得る」）。
- 秘密：コード署名の資格（Windows）。置き場：Artifact Signing の署名の権限（Azure の Artifact Signing の署名者の役割を持つ資格。CI の秘密、リリースの環境に限る。第11章 8.3「秘密の扱い」）。証明書そのものはサービスの中にあり、NRSD には渡らない。漏れた時：正しくコード署名された偽の配布物を作られ得る。資格を無効にし、Artifact Signing の窓口に届ける（第13章 H-44「CI・GitHub の組織が乗っ取られると、正しくコード署名された偽の配布物を公式のリリースに置かれ得る」）
- 秘密：コード署名の資格（macOS）。置き場：Developer ID Application の証明書と秘密鍵（.p12 とその合言葉）、公証に使う App Store Connect の API の鍵。CI の秘密（リリースの環境に限る）。原本は運営者の管理用 PC。漏れた時：正しく署名・公証された偽の配布物を作られ得る。Apple に証明書の失効を求める（第13章 H-44「CI・GitHub の組織が乗っ取られると、正しくコード署名された偽の配布物を公式のリリースに置かれ得る」）

## 9. NRSD のライセンス（O-09 の決定）

- 決定（2026-09-30、NRSD）：本システムのソースコードとプログラムのライセンスは Apache-2.0 とする。依存する部品はすべて 5.1「許可するライセンス」の許可したライセンス（MIT、Apache-2.0、BSD、ISC、Zlib、Unicode-3.0、IJG、OFL 等）であり（Linux の AppImage が同梱する OS 由来の LGPL の共有の部品は、動的リンクのまま同梱する例外）、両立する。
- 趣旨：NRSD は本システムで利用料を取らず、販売もしない。著作権とライセンスは放棄しないが、自由に使ってもらうことを目的とする。販売の場（Patreon 等）が本システムの照合の手段や作りをそのまま取り込めるくらいに開いておくことを目指す。改造版を閉じたまま配ることも妨げない（設計計画書 D-2-5「販売管理は扱わない。必要とする者はForkして改造するものとし、その結果についてNRSDは関知しない」、D-12-2「ソフトウェアは公開し、持ち出されることを妨げない」）。

|比べた候補|持ち出し・改造|名前の扱い|特許|採否|
|---|---|---|---|---|
|MIT|妨げない。改造版を閉じたまま配れる|定めがない|明示の許諾なし|採らない（名前・特許の定めがない）|
|Apache-2.0|妨げない。改造版を閉じたまま配れる。変更の明示が要る|第6条で商標（名前・標章）の使用を許さないと明記され、改造版が「公式」を名乗ることを抑える根拠の1つになる|明示の許諾あり|採る|
|GPLv3・AGPL-3.0|改造版を配る者にソースの公開を求める。販売管理を加えた改造を閉じたまま配れない|定めがない|明示の許諾あり|採らない（D-2-5「販売管理は扱わない。必要とする者はForkして改造するものとし、その結果についてNRSDは関知しない」・D-12-2「ソフトウェアは公開し、持ち出されることを妨げない」 と食い違う）|

- 理由：①Fork と改造を妨げない計画書の方針に合う。②告知コードの計算や照合の手順を、投稿先・検証サイト・他のソフトが製品に取り込みやすく、照合できる場所が増える。③第6条で名前の使用を許さないことが明記される（第9章 DD-9-3「公式版はコード署名の発行元と SHA-256 で見分ける」を補う。名前の保護は商標の法による）。④c2pa-rs、Tauri 等の周りの部品と同じ系統である。
- 表記：リポジトリの最上位に `LICENSE`（Apache-2.0 の本文）と `NOTICE`（著作権の表示：© 2026 株式会社流山ソフトウェア開発）を置き、配布物とアプリ（G-23「このアプリについて」）に同じものを含める。
- 寄付・支援：受けない（2026-09-30 時点）。受ける場合は、第7章の法的対応ガイダンスが無償で提供されることを非弁行為に当たらない整理の前提としているため（法務調査 L-10「法律事務の取扱い（非弁行為）（日）」：「利用料等一切の利益供与を受けることなく」）、寄付がこの前提に触れないかを専門家に確かめてから受ける。
- 輸出管理（法務調査 L-14「暗号を含むソフトの輸出管理（日・米）」）：公開の標準の暗号のみを使い、ソースを公開し、無償で配ることで、日本では許可を要しない取引、米国では通知を要しないものとして扱う。条件はリリースの都度確かめる（第9章 6.3「暗号を含むソフトの輸出管理」）。

## 10. 版の付け方と枝の運用

- アプリの版は「年.月.連番」（例：`2026.10.1`）とする。この形は Semantic Versioning の形（主.副.修正）に合い、Tauri の更新の仕組みの求め（正しい SemVer）を満たす（第9章 6.4「版の付け方」）。記録の形式の互換は、アプリの版ではなく記録の形式の版（`schema`）で表す。
- 記録の形式の版（`schema`）、C2PA の仕様の版、参照情報の版はアプリの版と別に持つ（第1章 10.9「版の互換性」）。
- main の枝への直接の反映を禁じ、引き込みの要求（pull request）と CI の検査を経る（第8章 3.5「GitHub のアカウントとリポジトリの守り」）。開発者が1人の間は、レビューは開発者自身の確かめとする。コミットに電子署名を付ける。
- リリースは版の印（タグ）を付けた時に CI が作る。
